# 05 - 协作与工程纪律

> 这一篇是给**同时有多个代理/多个人在改同一个仓库**时用的。里面每一条都对应一次真实损失
> （整轮验证作废、代码被改坏、存档报废、静默失效）。
> 素材来源：源仓库 `bettergold` 的协作事故记录【记录】
> （`docs/构建与跑测注意事项.md` §二/§三、`docs/创造页分区栏目-参考实现/02` §7/§8/§10）
> + 本仓库 `AGENTS.md` 已经写死的红线。

## 1. 共享资源**必须串行**，并且要有唯一持有者

### 1.1 `run\` 目录是独占资源

**症状**（源仓库实测/记录）：

- 同时跑两个客户端（或客户端 + 服务端）：**卡在 100% 加载不动**，或
  `Unable to delete file ... latest.log`（另一个进程握着 `run\logs\latest.log`）；
- `run\world\session.lock` 与 `run\saves\*\session.lock` 被占用 ⇒ 新进程起不来，
  日志看起来像"改动没生效"。

**规矩**：

1. **同一时刻只允许一个游戏进程**（`runServer` 或 `runClient` 二选一）。
2. 跑之前删 `session.lock`；跑之前清掉上次残留的**游戏** java 进程。
3. **杀进程要精准**：只杀命令行里含 `forgeclientdev` / `forgeserverdev` 的 java；
   **不要** `Get-Process java | Stop-Process -Force` —— 会连带杀掉 Gradle daemon，
   写坏配置缓存（症状：`Could not load compiled classes for build file ... from cache`；
   修法：`gradlew --stop` + 删 `.gradle/configuration-cache`）。
4. **申请制**：由协调方（主代理/人）**逐个发放 `run\` 许可**，不要指望两边自己打招呼。
   源仓库为此白跑过一轮：> 多个人（或多个子代理）协作时，**由协调方逐个发放 run\ 许可**。

### 1.2 其它共享资源

| 资源 | 冲突后果 | 纪律 |
|---|---|---|
| `run\logs\latest.log` | 日志被覆盖/删掉，取证消失 | 探针输出**重定向到自己的文件**：`build\probe-<你的名字>.log` |
| `run\world` / `run\saves` | 存档损坏、锁冲突 | 不用同一个世界做两个实验 |
| `build\` 里的取证产物 | 互相覆盖 | 文件名带用途与轮次（本仓库现有习惯：`build/patch/w3-user-checklist.md`、`p3z-EVIDENCE.txt`） |
| Gradle daemon / 配置缓存 | 被强杀后构建全崩 | 只用 `gradlew --stop`，不要 `Stop-Process` |
| `run\*-probe.enabled` 之类的开关文件 | 开关留在那儿，别人的流程被触发 | 收尾**连开关文件一起删** |

### 1.3 日志的读法也要串行化

`build/` 被 git 忽略、可以随便写；但**同一个文件名不要被两个代理写**。
本仓库 `AGENTS.md` 已经因为"日志被覆盖/编码误读"误判过事实（把「@Mod 构造器已跑」误判成「没跑」），
所以：**日志文件名里带轮次/用途，读日志时显式指定编码。**

## 2. 一个文件，同一时间**只能有一个代理改**

**为什么不能靠"改的地方不一样"来避免冲突**：Gradle 与 IDE 都是按**文件**整写；
两个代理各改一半，后写的那个会静默覆盖前一个（没有冲突提示）。

**规矩**：

1. 动手**之前**先声明："本机要改的文件清单"（一句话即可）。
2. 清单里的文件，别人**只读**，不改；要改就等对方说完成或放弃。
3. 特别容易撞车的文件（本仓库实际的高频冲突点）：
   - 注册表聚合文件：`CoeItems.java` / `CoeBlocks.java` / `CoeBlockEntityTypes.java`
     （还有各层 `common/registry/**` 的 `register()` 入口）
   - 语言文件与其 provider：`data/lang/{ChineseLangProvider,EnglishLangProvider}.java`
     （`AGENTS.md` 记过「中英键集必须对齐」，两边同时改必冲突）
   - `AGENTS.md`（**指令预算 ≤ 40,000 B**，两个人同时追加必然超预算）
   - 根 `build.gradle` / `settings.gradle`（依赖接线，改错就是 `duplicate_mod` / `ResolutionException`）
   - 分层工具 `tools/check-layering.ps1` 与 `tools/layer-usage.ps1`（**两者的 `Get-FileLayer` 必须逐字一致**，
     一个人改一个没跟着改 = 静默逃逸）
4. **不要在别人正在跑的 `run\` 上做实验**（§1.1）。

## 3. 接口要**定死后不许单方面改**

### 3.1 本仓库已经写死的红线（照抄，不许动）

来源：本仓库 `AGENTS.md`「🚩 红线」。

| 不许改 | 后果 |
|---|---|
| 注册命名空间 `createoreexpansion`（类引用走 `CoeCore.REGISTRY_NAMESPACE`，`modLoc` 走 `CoeCore.modLoc`） | 所有 id 全变 ⇒ **老存档报废** |
| `@Mod` / `@EventBusSubscriber` 上的 `MOD_ID`（可以且必须与命名空间分家） | 事件订阅**静默失效**（无警告、无报错） |
| 配置键 / 容器名 | 文件名一变（如 `coe_core-common.toml`）⇒ **老玩家设置静默丢失** |
| 语言键 | 玩家看到原始键名 |
| 数据包路径 | 数据静默不加载 |
| 某个 Java 包的归属模块（JPMS） | 启动期 `java.lang.module.ResolutionException`（**只有真发布 jar 进游戏能验**） |

### 3.2 容易被忽视的"隐性接口"

比类名/方法名更容易被忽略，同样**必须冻结**：

1. **枚举声明顺序**。本仓库 `AllTiers` 的值被 `CoeItems` 逐件引用；
   `ArmorItem.Type` 的 `ordinal()` 被 `CoeArmorMaterials.java:140-145` 当作护甲值数组的下标。
   **往枚举中间插一个值 = 护甲值整体错位，且没有任何报错。**
2. **注册顺序**。`AGENTS.md` 明确写着「注册触发顺序必须在 `CreateOreExpansion` / `IntegrationBootstrap`
   里显式写死（没有兜底）」；也有「配方类型展开序列 == 6 元素表，顺序是玩法不变量」这类冻结断言。
3. **`DeferredHolder` 的身份**。`MedallionEffectHandler.java:78` 依赖
   「施放侧塞进 `MobEffectInstance` 的就是那个 `DeferredHolder` 本身」来做 `==` 比较。
   如果哪天改成 `effect.getDelegate()` 或重新 `Holder.direct`，这条判定就**静默恒 false**。
4. **工具返回值的语义**。例如 `Tier.getUses()` 是"最终耐久"而不是"基数"（`01` §7.1）；
   `MobEffect.applyEffectTick` 返回 `false` 会**移除效果**而不是"跳过"（`03` §2.1）。
   这类语义一旦被某个分支代码"顺手改了"，另一个分支就会静默错。

### 3.3 改接口的正确流程

1. 先写清楚：**谁依赖它、依赖的具体表达是什么**（grep 出调用点）；
2. 在会话里**广播**，等所有相关代理确认"我不在改这段"；
3. 改完**立刻**跑对应的断言关卡（本仓库：`tools/check-layering.ps1`、
   `check-package-overlap.ps1`、`check-module-selfsufficiency.ps1`、`check-asset-attribution.ps1`
   等，见 `AGENTS.md`「工具」一节）；
4. 把「为什么改、影响了谁」写进交接说明。

## 4. 改动面尽量压到最小：用**别名 / 适配层**

原则：**让"变的东西"停在边界上，不要渗进核心。**

本仓库已经有两个现成范式，优先复用而不是自创：

- **可选依赖隔离**：`compat/` 层 + `ModList.isLoaded` + 反射/`Class.forName`。
  `AGENTS.md` 红线：「`content/` 包不得 import 任何可选模组类」（Curios 只允许出现在 `compat/curios`）。
  这样做的好处是"没装那个模组也能加载"，而不是让每个调用点各判一次。
- **共享库 `core`**：全模组共用的契约住 `core`，各层往上引用（`CORE` 是各层都能引用的底层）。

**反例（不要做）**：

- 为了一个小需求去改公共枚举/公共方法签名；
- 在 `content/**` 里直接 `import` 可选模组的类；
- 为了"统一风格"把已经验证通过的一大片代码重写（源仓库的教训是：重构面越大，
  "全绿但坏掉"的概率越高 —— 本仓库 `AGENTS.md` 记过**六次"全绿但坏掉"**）。

**判据**：如果这个改动会影响超过 3 个文件，先停下来问"能不能做成别名/适配层"。

## 5. 文件与编码（会浪费你半天时间的那类问题）

1. **一律无 BOM。** PowerShell 5.1 的 `Set-Content -Encoding UTF8` **会写 BOM**；
   JSON 与 `.java` 都可能因此出问题。
2. **不要用 `Get-Content` / `Set-Content` 做文本替换。**
   源仓库中过两次（中文注释变乱码，只能靠 git 恢复）；
   本仓库 `AGENTS.md` 记过更严重的一次：用 `Get-Content | -replace | Set-Content` 改
   `SkillerIntegration.java`，**改到语法崩掉（48 个编译错误）**，只能 `git checkout --` 重做。
   **正确做法**：用编辑工具（`write`/`edit`），或
   `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`
   + `ReadAllText` 配对使用。
3. **行尾要明确。** 本仓库 `.java` 多为 CRLF，而**本 `docs/共享经验-盔甲与材料集/` 下的 Markdown 统一 LF**。
   用字符串拼多行锚点时注意 `` "`r`n" ``。
4. **删代码块按「标记 + 锚点」成对定位**，不要用行数算术。
   源仓库曾多切 4 行，切出多余右括号导致构建失败。
5. **PS 5.1 读无 BOM 的 UTF-8 `.ps1` 会按 ANSI 解码**：脚本里的中文注释可能吞掉引号 ⇒ ParserError。
   **一次性脚本一律写纯 ASCII**（中文用 `[regex]::Unescape('\uXXXX')` 拼）。
6. **`Select-String` 匹配中文必须显式 `-Encoding Default`**；
   本仓库曾因此把「@Mod 构造器已跑」误判成「没跑」。
7. **临时文件写 `%TEMP%` 或 `build/`（已忽略），别落进仓库**——`git add -A` 会把它带进去。
8. 本仓 `grep` 会漏文件（`AGENTS.md` 有记录：实测只扫出 71 行而实际更多）⇒
   全库文字盘点用 `Select-String`，并接受"它也可能漏"的结论不确定性。

## 6. 构建判读：别被 PowerShell 骗了

**症状**：`.\gradlew.bat build ... 2>&1 | Tee-Object ...`（或任何让 stderr 进 PowerShell 错误流的写法）之后，
pwsh 打印红色的

```
.\gradlew.bat : 注: 某些输入文件使用或覆盖了已过时的 API。
    + FullyQualifiedErrorId : NativeCommandError
```

看起来构建失败，**但 Gradle 其实是成功的**。

**根因**：javac 的提示（弃用 API 之类）写在 **stderr**；PowerShell 把原生命令写进 stderr 的内容一律记成
`NativeCommandError`。这与 Gradle 的退出码无关。

**正确做法**：

1. 判断成败**只看** Gradle 输出的 `BUILD SUCCESSFUL` / `BUILD FAILED`，或 `$LASTEXITCODE`；
2. 想让日志干净：`2>build\x.err` 单独重定向，或 `--console=plain` 只看 stdout；
3. 同理：`git push` 的进度信息也走 stderr，出现红字不代表失败。

> 本仓库 `AGENTS.md` 还有一条更严的：`.\gradlew ... 2>&1 | Select-Object` 会把 javac 的 **GBK 诊断解成乱码**，
> 要 `cmd /c "... > file 2>&1"` + `-Encoding Default` 读。**沿用本仓库的做法，不要引入新写法。**

## 7. 临时探针：**整块删除**，并且绝不能把"能关掉别人游戏"的能力留在生产代码里

这一条在源仓库造成过一次**整轮验证作废**的事故，原文照抄【记录】：

> 曾经有一个临时探针在别人客户端进世界时触发 `halt`，直接把对方正在跑的集成服务器关掉，
> 整轮验证作废。探针收尾必须**整块删除**（不是注释掉），并给出 grep 证据。

**规矩**：

1. **`server.halt(...)` / `stopServer()` / `System.exit(...)` 绝不允许进入生产代码**，
   只允许出现在同一轮就要删掉的探针块里。
2. 需要自动退出时用**开关文件**保护（`run\xxx-probe.enabled` 存在才动作），收尾时开关文件一起删。
3. **探针关服只能调一次 `halt(false)`**。先 `stopServer()` 再 `halt(false)` 会走**两遍**关闭流程，
   日志停在存盘循环里看起来像卡死/存不住盘（`03`/`04` 有机制解释）。
4. 探针输出中文转 `\uXXXX`（见 `04` §1.3）。
5. **收尾给证据**：

```powershell
# 应当零命中（按本仓库的探针前缀调整）
Select-String -Path (Get-ChildItem -Recurse src,coe,cews,core -Filter *.java).FullName `
  -Pattern 'TEMP-|PROBE|probe\.|halt\(|stopServer\(|System\.exit\('
Remove-Item -Force run\*-probe.enabled -ErrorAction SilentlyContinue
```

> 注意：**探针收尾异常会让 `runServer` 以非零码结束**，所以看到 `BUILD FAILED ... non-zero exit value -1`
> 且日志里**没有** `Stopping server` 时，**先怀疑探针收尾，不要先怀疑业务代码**。

## 8. 跨项目"只报告不改"的纪律

本次任务属于这一类：读别人的仓库、写文档、**不改它的源码/构建脚本/资源文件**。

**规矩**：

1. 只**新建文档**；不改任何已有文件（哪怕只是一行注释）。
2. 报告里每条问题给 `文件:行` + 现象 + 根因 + 建议 + **怎么验证**，
   并明确标出「实测 / 读源码 / 推断」。
3. **不为凑数编问题**；没发现问题的位置就写"这几处我核对过是对的 + 依据"。
4. 不确定的写不确定，并给出"怎么才能确认"。

## 9. 一页协作契约（多代理会话开头可以直接贴）

```
本会话的协作契约：
1. run\ 独占：同一时刻只有一个游戏进程；跑前由协调方发放许可；跑前删 session.lock。
2. 一文件一代理：动手前声明文件清单；清单里的文件别人只读。
3. 接口冻结：注册命名空间/配置键/语言键/数据包路径/modid 归属、枚举声明顺序、注册顺序 都不许单方面改。
4. 改动面：能用别名/适配层解决就不改核心；单次改动超过 3 个文件先停下来说明。
5. 编码：无 BOM；新文档 LF；不用 Get-Content|Set-Content 改文件；一次性 ps1 写纯 ASCII。
6. 构建判读：只看 BUILD SUCCESSFUL / BUILD FAILED，不看 pwsh 红字。
7. 探针：整块删除 + grep 证据；halt 只调一次；关服能力绝不留在生产代码。
8. 汇报：实测 / 编译 / 推断 分开写；只读 JSON 不算验证。
```
