## 1. 效果给的属性修饰符：**必须**用 `addAttributeModifier(...)`

### 1.1 两套写法，只有一套有用

【读源码】`MobEffect.java`：

```java
:131  public MobEffect addAttributeModifier(Holder<Attribute> attribute, ResourceLocation id,
                                              double amount, AttributeModifier.Operation operation)
:143  public MobEffect addAttributeModifier(Holder<Attribute> attribute, ResourceLocation id,
                                              AttributeModifier.Operation operation,
                                              Int2DoubleFunction curve)          // ← NeoForge 的等级曲线重载
:153  public void createModifiers(int amplifier, BiConsumer<Holder<Attribute>, AttributeModifier> output)
:166  public void addAttributeModifiers(AttributeMap attributeMap, int amplifier)   // ← 真正写进实体的那一个
:213      public AttributeModifier create(int level) {
:214          if (curve != null) return new AttributeModifier(this.id, this.curve.apply(level), this.operation);
:217          return new AttributeModifier(this.id, this.amount * (double)(level + 1), this.operation);
```

**结论：覆写 `createModifiers` 不会作用到实体上。** 依据是「谁被调用」：

```java
LivingEntity.onEffectAdded   :1046-1052
    effectInstance.getEffect().value().addAttributeModifiers(this.getAttributes(), amplifier);   // :1049
LivingEntity.onEffectUpdated :1062-1069
    mobeffect.removeAttributeModifiers(this.getAttributes());                                     // :1066
    mobeffect.addAttributeModifiers(this.getAttributes(), amplifier);                             // :1067
```

`addAttributeModifiers` 遍历的是**私有的 `attributeModifiers` map**（只有 `addAttributeModifier` 能往里写），
`createModifiers` 在这条链上**一次都没被调用**（我在 `LivingEntity` 里 grep 过，零命中）。

**源仓库的实测代价**：自定义效果「颤栗」按 `createModifiers` 写了一遍，
`-1 伤害 / -0.1 攻速` 在 tooltip 上显示正常、编译全绿，但**穿上打怪数值没变**；
改成 `addAttributeModifier(...)` 之后才真正生效
【记录】`bettergold/docs/1.4-进度与交接.md` §三第 2 条。

**注意等级系数**：第 :217 行的默认曲线是 `amount * (level + 1)`，
所以 `amplifier = 0`（效果 I 级）就是 **1 倍** amount，`amplifier = 1`（II 级）是 2 倍。
要非线性（例如「每级 −1，最高 −4」）就用 :143 的曲线重载：
`addAttributeModifier(attr, id, Operation.ADD_VALUE, lvl -> -Math.min(lvl + 1, 4))`。

### 1.2 本仓库现状

`coe/.../content/transmuting/effect/TransmutationDisorderEffect.java` 是唯一自定义效果，
它**不使用属性修饰符**（走的是直接 `hurt` + 扣物品），所以没有踩这条。
但注意：`AllTiers` / 盔甲用的是**物品自带的属性修饰符**（`createAttributes`），
那一套机制不同（`ItemAttributeModifiers`，随装备槽位生效），不要和 `MobEffect` 混。

## 2. 周期效果：`shouldApplyEffectTickThisTick` + `applyEffectTick`

### 2.1 调度契约

【读源码】`MobEffectInstance.java:223-230`：

```java
public boolean tick(LivingEntity entity, Runnable onExpirationRunnable) {
    if (this.hasRemainingDuration()) {
        int i = this.isInfiniteDuration() ? entity.tickCount : this.duration;   // ★ 传进去的是「剩余时长」
        if (this.effect.value().shouldApplyEffectTickThisTick(i, this.amplifier)
            && !this.effect.value().applyEffectTick(entity, this.amplifier)) {
            entity.removeEffect(this.effect);                                   // ★ 返回 false = 直接移除整个效果
        }
        this.tickDownDuration();
        ...
```

两条必须记住：

1. **`shouldApplyEffectTickThisTick` 收到的是「剩余时长」**（对无限时长效果才是 `entity.tickCount`），
   而且它是**递减**的。
2. **`applyEffectTick` 返回 `false` 会移除整个效果**（不是"跳过这一次"）。
   如果你要用 `MobEffectEvent.Expired` 做「效果结束时的结算」（见 §4），
   **绝对不能让 `applyEffectTick` 返回 false**，否则 Expired **不会触发**。

### 2.2 原版范式

【读源码】`PoisonMobEffect.java`：

```java
@Override public boolean applyEffectTick(LivingEntity e, int amplifier) {
    if (e.getHealth() > 1.0F) { ... e.hurt(new DamageSource(dType), 1.0F); }
    return true;                       // ★ 恒 true：靠"时长到 0"来结束，不靠返回值
}
@Override public boolean shouldApplyEffectTickThisTick(int duration, int amplifier) {
    int i = 25 >> amplifier;           // 25 / 12 / 6 / 3 / 1
    return i > 0 ? duration % i == 0 : true;
}
```

### 2.3 ★ 陷阱：效果被**每 tick 刷新**时，`duration % N` 会**恒真**

`TransmutationEventHandler` 这类"接触即持续获得效果"的写法是每 tick 都 `addEffect(new MobEffectInstance(effect, 60, level - 1))`
（本仓库 `coe/.../content/transmuting/event/TransmutationEventHandler.java:75` 正是如此）。
因为同效果会被**合并**（`MobEffectInstance.update` 取更长的时长），`duration` **一直停在 60**，
于是 `60 % 20 == 0` **每一 tick 都成立** ⇒ 结算频率放大 20 倍（4 点/秒 变 80 点/秒）。

本仓库的规避写法是**对的**：`TransmutationDisorderEffect.java:37-39` 让
`shouldApplyEffectTickThisTick` 恒返回 `true`，真正的节流放在
`applyEffectTick` 内部用 **`entity.tickCount % 20 == 0`**（`TransmutationDisorderEffect.java:51`）。
`entity.tickCount` 是实体自己的计数器，不受效果刷新影响。

⇒ **通用规则**：
- 效果**不会被每 tick 刷新** ⇒ 用 `duration % N == 0`（原版范式，且能自动跟随时长变化）；
- 效果**会被每 tick 刷新**（接触类、光环类、装备类）⇒ 用 `entity.tickCount % N`，
  或干脆在 `applyEffectTick` 里按 `duration` 的**绝对值**判定（例如 `duration % 20 == 0 && duration > 60 - 20`）。

## 3. 持续伤害与燃烧：两条真实的相互作用（以及一条我**没能确认**的）

### 3.1 自己结算伤害 ⇒ 会占掉无敌帧，从而"吃掉"原版燃烧伤害

【读源码】`LivingEntity.hurt:1142` 起，关键判定在 :1190：

```java
if ((float)this.invulnerableTime > 10.0F && !source.is(DamageTypeTags.BYPASSES_COOLDOWN)) {
    if (amount <= this.lastHurt) { this.damageContainers.pop(); return false; }   // ★ 这次伤害直接不算
    ...
} else {
    this.lastHurt = amount;
    this.invulnerableTime = this.damageContainers.peek().getPostAttackInvulnerabilityTicks();  // 默认 20 tick
    this.actuallyHurt(source, amount);
}
```

而**原版燃烧伤害走的就是 `hurt`**【读源码】`Entity.baseTick:467-468`：

```java
if (this.remainingFireTicks % 20 == 0 && !this.isInLava())
    this.hurt(this.damageSources().onFire(), 1.0F);
```

⇒ **如果你每 tick 自己 `hurt` 一次，那么"每 20 tick 掉 1 点"的燃烧伤害会被无敌帧吞掉**
（因为 `invulnerableTime` 长期 > 10 且 `1.0 <= lastHurt`）。
想两者都生效，要么把燃烧伤害当成你这次结算的一部分（自己加进去），
要么给伤害类型挂 `#minecraft:bypasses_cooldown`（数据包标签，可以自己扩），
要么在 `hurt` 前手动 `entity.invulnerableTime = 0`（探针/测试时常用）。

### 3.2 防火生物：燃烧**永远**挂不上

【读源码】`LivingEntity.baseTick:407-409`：

```java
if (this.fireImmune() || this.level().isClientSide) {
    this.clearFire();
}
```

**每一 tick 都清**。另外 `Entity.baseTick:461-465` 对 `fireImmune` 的生物是每 tick `-4` 燃烧 tick。
⇒ 想做"给目标挂燃烧"的效果，先确认目标不是防火生物（下界生物/岩浆怪/烈焰人…），
否则表现是「特效放了、燃烧条一闪就没」。

### 3.3 我**没能确认**的那一条（诚实记录）

源仓库的笔记里写着「自己结算伤害 + `setRemainingFireTicks` 的相互影响（**hurt 会清燃烧计时**）」
【记录】。我在 1.21.1 的基类里**没有找到"受伤清燃烧计时"这条路径**。
我逐条核对过的所有清火点只有：

| 位置 | 行为 |
|---|---|
| `Entity.clearFire():557-559` | `setRemainingFireTicks(0)`，本身不判断上下文 |
| `LivingEntity.baseTick:407-409` | 防火 **或客户端** ⇒ 每 tick 清 |
| `Entity.baseTick:459` | 客户端每 tick 清 |
| `Entity.baseTick:462-464` | 防火生物每 tick `-4`，减到负数才清 |
| `Entity.baseTick:744` | 粉雪/水/雨 ⇒ 清 |
| `Entity.baseTick:1298` | 入水 ⇒ 清 |
| `Entity.extinguishFire():796-802` | 显式灭火 |
| `Entity.thunderHit:2512-2515` | `setRemainingFireTicks(+1)`；恰好为 0 时 `igniteForSeconds(8)` |

`Entity.hurt(DamageSource, float):1579-1585` 与 `LivingEntity.actuallyHurt:1785-1800` 里**都没有**动燃烧计时的代码。

所以我把它标成 **【未确认】**，并推测源仓库观察到的现象其实是 §3.1 的"无敌帧吃掉燃烧伤害"
（症状很像"燃烧被清了"）。**如果你在游戏里确实观测到燃烧计时被清零**，
请按 `04` 的方式在 hurt 前后各打一次 `getRemainingFireTicks()`，把日志贴出来再定论——
不要照抄一条没被证实的因果。

## 4. 效果结束时的结算：用 `MobEffectEvent.Expired`；别用 `Applicable` 当可取消事件

### 4.1 `Expired`

【读源码】`LivingEntity.tickEffects:800-815`：

```java
if (!mobeffectinstance.tick(this, () -> this.onEffectUpdated(...))) {
    if (!this.level().isClientSide
        && !NeoForge.EVENT_BUS.post(new MobEffectEvent.Expired(this, mobeffectinstance)).isCanceled()) {  // :808
        iterator.remove();
        this.onEffectRemoved(mobeffectinstance);
    }
}
```

- `MobEffectEvent.Expired` **是** `ICancellableEvent`【读源码】`MobEffectEvent.java:212`；
- 它在**服务端**、且**只在 `mobeffectinstance.tick` 返回 false（时长耗尽/被移除）时**触发；
- ⚠️ **`applyEffectTick` 返回 false 导致 `entity.removeEffect(...)`（`MobEffectInstance.java:227`）不走这里**
  ⇒ 依赖 Expired 做结算的效果，`applyEffectTick` 必须恒返回 `true`。

源仓库的「巫毒」就是靠 Expired 结算的：结束时按 `层数 × 0.6% × 最大生命值` 结算魔法伤害
【记录】`bettergold/docs/1.4-进度与交接.md` §一（实测「巫毒 3 级结束掉 0.18 = 3×0.6%×10」）。

### 4.2 `Applicable` **没有**实现 `ICancellableEvent`

【读源码】`MobEffectEvent.java`：

```java
:43   public static class Remove    extends MobEffectEvent implements ICancellableEvent
:94   public static class Applicable extends MobEffectEvent            // ★ 没有 implements ICancellableEvent
:171  public static class Added    extends MobEffectEvent
:212  public static class Expired  extends MobEffectEvent implements ICancellableEvent
```

`Applicable` 用的是 **Result 三态**（`APPLY` / `DEFAULT` / `DO_NOT_APPLY`），
要阻断就 `event.setResult(MobEffectEvent.Applicable.Result.DO_NOT_APPLY)`。
**写 `event.setCanceled(true)` 编不过**；如果曾经用别的方式绕过，症状是「兜底从来没拦下过任何一次」。

**本仓库现状（用法正确）**：`MedallionEffectHandler.java:75-82` 用的就是
`setResult(Applicable.Result.DO_NOT_APPLY)`。

> **本仓库注释里还记着一个更隐蔽的坑，值得所有人知道**：
> 1.21 起 `MobEffectInstance#getEffect()` 返回 `Holder<MobEffect>`，
> 所以拿它跟 `MobEffect` 常量做 `==` **恒为 false**（编译能过，因为 `Holder` 不是 final 类）。
> 正确写法是拿它跟 `DeferredHolder`/`Holder` 比：`event.getEffectInstance().getEffect() == TransmutationEffects.TRANSMUTATION_DISORDER`
> （见 `MedallionEffectHandler.java:78` 与它上方 :47-55 的注释）。

## 5. 减伤 / 免疫：`LivingDamageEvent.Pre` + `setNewDamage`

【读源码】`LivingDamageEvent.java`：

```java
:48  public static class Pre extends LivingDamageEvent {
:81      public void setNewDamage(float newDamage) { container.setNewDamage(newDamage); }
:97  public static class Post extends LivingDamageEvent { ... }   // 只有 getter，没有 setter
```

时机【读源码】`LivingEntity.actuallyHurt:1785-1800`：**护甲减伤与魔法减伤之后、吸收（absorption）之前**。
所以 `Pre` 里设的值就是"真正扣的血"，用它做百分比减伤/免疫最合适（`setNewDamage(0)` = 免疫）。

**源仓库的实现口径**：按装备件数做百分比减伤，实测「穿 0/1/2/3/4 件受 8 点火焰 → 掉血 8.0/6.0/4.0/2.0/0.0」
【记录】`bettergold/docs/1.4-进度与交接.md` §一。

### 5.1 ★ NeoForge 把中毒从 `minecraft:magic` 拆成了 `neoforge:poison`

【读源码】`PoisonMobEffect.java`（原版类，NeoForge 打了补丁）：

```java
// Neo: Replace DamageSources#magic() with neoforge:poison to allow differentiating poison damage.
var dTypeReg = p_296276_.damageSources().damageTypes;
var dType = dTypeReg.getHolder(NeoForgeMod.POISON_DAMAGE)
        .orElse(dTypeReg.getHolderOrThrow(DamageTypes.MAGIC));
p_296276_.hurt(new DamageSource(dType), 1.0F);
```

相关常量与标签：

- `NeoForgeMod.POISON_DAMAGE` = `neoforge:poison`【读源码】`NeoForgeMod.java:498`
- `Tags.DamageTypes.IS_MAGIC` = `#neoforge:is_magic`【读源码】`Tags.java:1327`
- `Tags.DamageTypes.IS_POISON` = `#neoforge:is_poison`【读源码】`Tags.java:1332`
- **`#neoforge:is_magic` 里面包含了 `#neoforge:is_poison` 与 `#neoforge:is_wither`**
  【读源码】`NeoForgeDamageTypeTagsProvider.java:60`：
  `tag(Tags.DamageTypes.IS_MAGIC).addTags(Tags.DamageTypes.IS_POISON, Tags.DamageTypes.IS_WITHER);`

⇒ **做"魔法抗性"时的正确判据**：

| 写法 | 结果 |
|---|---|
| `source.is(DamageTypes.MAGIC)` | ❌ **漏掉中毒**（中毒现在是 `neoforge:poison`） |
| `source.is(DamageTypes.MAGIC) \|\| source.is(Tags.DamageTypes.IS_POISON)` | ✅ 精确 |
| `source.is(Tags.DamageTypes.IS_MAGIC)` | ✅ 最省事（已含 poison / wither），但也会把凋零算进"魔法" |

**源仓库实测发现的就是第一条**：只判 `minecraft:magic` 时，玩家"魔法免疫套"挡不住中毒。
本仓库如果要给"魔法抗性"类效果/装备补这条，请注意 `TransmutationDisorderEffect.java:64`
用的是 `damageSources().magic()` —— 那是**它自己造成的伤害**，不是中毒，所以不受影响；
但将来做"抗性套装"时必须处理 poison。

## 6. 命中附加效果 vs 落雷

### 6.1 命中附加用 `LivingDamageEvent.Post`

`Post` 提供 `getSource()` / `getNewDamage()` / `getEntity()`【读源码】`LivingDamageEvent.java:97-160`，
适合"打中了就给我方/目标加效果"。**判断是不是近战打中**要用 `source.getDirectEntity() instanceof LivingEntity`
或 `source.is(DamageTypeTags.IS_PROJECTILE)` 排除，不要只看 `getEntity()`。

### 6.2 落雷：**直接调 `thunderHit`** 就能复用到原版全部转化

【读源码】`Entity.thunderHit(ServerLevel, LightningBolt):2511-2518`：

```java
public void thunderHit(ServerLevel level, LightningBolt lightning) {
    this.setRemainingFireTicks(this.remainingFireTicks + 1);
    if (this.remainingFireTicks == 0) this.igniteForSeconds(8.0F);
    this.hurt(this.damageSources().lightningBolt(), lightning.getDamage());
}
```

**真正的"转化"都在子类覆写里**，`Entity` 版只给「着火 + 雷击伤害」：

| 生物 | 覆写位置 | 效果 |
|---|---|---|
| 猪 | `Pig.java:211-234` | → 僵尸猪灵（带金剑、继承自定义名/幼年，并走 `canLivingConvert` 钩子） |
| 苦力怕 | `Creeper.java:219-222` | `DATA_IS_POWERED = true` |
| 哞菇 | `MushroomCow.java:73-79` | 红/褐互换（用 `lastLightningBoltUUID` 防重复） |
| 村民 | `Villager.java:820-844` | → 女巫（困难度非和平 + `canLivingConvert`） |

⇒ **想要"不点火、不毁地形，但保留这些转化"**：不要生成真实 `LightningBolt` 让它自然结算，
而是**自己 `target.thunderHit(serverLevel, bolt)`** —— 转化与雷击伤害一起到手，且不会引发方块燃烧
（燃烧来自 `LightningBolt` 自己的 `spawnFire`）。

### 6.3 雷电音效音量要给足

【读源码】`LightningBolt.tick:90-112`：**只在客户端**（`this.level().isClientSide()`）
用 `playLocalSound` 播两段：

```java
SoundEvents.LIGHTNING_BOLT_THUNDER, SoundSource.WEATHER, 10000.0F, 0.8F + rand * 0.2F, false   // :96-100
SoundEvents.LIGHTNING_BOLT_IMPACT,  SoundSource.WEATHER, 2.0F,    0.5F + rand * 0.2F, false   // :107-111
```

**音量 10000.0F 是有意为之**（原版靠它让雷声在极远处也能听见；`SoundSource.WEATHER` 的音量上限由
`SoundSource` 的 `getVolume` 曲线处理）。自己做"引雷"特效时如果只给 1.0F，听起来会像"啪"而不是雷。

### 6.4 ⚠️ `setVisualOnly(true)` 只关掉两件事

【读源码】`LightningBolt.tick`：

```java
:116   this.spawnFire(4);                                   // 内部再判 !visualOnly
:119   this.powerLightningRod();                            // ★ 不受 visualOnly 影响
:120   clearCopperOnLightningStrike(this.level(), ...);     // ★ 不受 visualOnly 影响
:155   } else if (!this.visualOnly) {                       // ★ 只有"对实体结算"受它控制
```

`spawnFire` 内部才是 `if (!this.visualOnly && ...)`。所以「纯视觉闪电」**仍然会**：
激活避雷针、给铜块除锈、抛 `GameEvent.LIGHTNING_STRIKE`。
**本仓库的强化避雷针释放的就是 `visualOnly(true)` 的闪电**
（`coe/.../content/lightning/ReinforcedLightningRodEffects.java:28`），
所以它会顺手激活自己（避雷针 `onLightningStrike`）——如果这不是预期行为，就要另想办法。
**副作用是它对实体不调 `thunderHit`**，`EntityStruckByLightningEvent` 也不会触发（见 `06` 第 2 条）。

## 7. 挖掘掉落改写：掉落事件 + 查熔炼配方表

**正确的入口是 `BlockDropsEvent`**【读源码】`net/neoforged/neoforge/event/level/BlockDropsEvent.java`：

```java
:30  public class BlockDropsEvent extends BlockEvent implements ICancellableEvent
:68  public List<ItemEntity> getDrops()     // ★ 可变，改它就改最终掉落
:76  public BlockEntity getBlockEntity()
:84  public Entity getBreaker()             // 破坏者，可能是 null
:91  public ItemStack getTool()
```

**实现"自动熔炼"的正确姿势**：不要自己写一张"矿石→锭"的表，而是
**拿掉落物去查原版的熔炼/高炉配方表**：

```java
// 骨架/示例：把每个掉落物尝试换成它的熔炼产物
var recipeManager = level.getRecipeManager();
for (ItemEntity drop : event.getDrops()) {
    ItemStack in = drop.getItem();
    recipeManager.getRecipeFor(RecipeType.SMELTING, new SingleRecipeInput(in), level)
        .ifPresent(holder -> drop.setItem(holder.value().getResultItem(level.registryAccess()).copyWithCount(in.getCount())));
}
```

这么做的好处：**自动兼容其它模组新增的熔炼配方**（原木→木炭、沙→玻璃、马铃薯→烤马铃薯、
别的模组加的矿石→锭…），也不用维护第二份配方清单。

⚠️ **源仓库在这一点上留下的教训不是技术性的，是流程性的**：
自动熔炼**实现完了、但从未实机验证**，被明确列进"剩余三件事"
【记录】`bettergold/docs/1.4-进度与交接.md` §二第 2 条。
不要重复这个错——掉落改写必须在 `runServer` 里真的挖一块试（见 `04`）。

## 8. 测试战斗逻辑时的三个"假失败"

以下三条来自源仓库的实测记录【记录】`bettergold/docs/1.4-进度与交接.md` §三：

1. **`FakePlayer` 对绝大多数伤害源无敌** ⇒ 测"抗性/减免"必须用**真实生物**（僵尸可以穿盔甲，
   是最好用的靶子）。
2. **物品受伤后的无敌帧会吃掉第二刀** ⇒ 测"叠加"（例如连打两刀看 buff 是否升级）必须先
   `target.invulnerableTime = 0`，否则第二刀根本不结算（见 §3.1 的同一个判定）。
3. **效果结束结算要在服务端看**：`Expired` 只在服务端 post（`tickEffects:808` 有 `!isClientSide` 判断），
   客户端探针看不到。

另外：`applyEffectTick` 一开始就 `if (entity.level().isClientSide) return true;`（本仓库
`TransmutationDisorderEffect.java:43-44` 就是这么写的）是好习惯——效果 tick 两端都会跑，
不判端会双倍结算。
