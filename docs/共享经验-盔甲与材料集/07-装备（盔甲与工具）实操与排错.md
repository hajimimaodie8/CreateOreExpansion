### 根因（为什么偏偏是翠玉这一套）

**【资源实测 + 推断】** 源压缩包 `矿物扩展双色盔甲.zip` 里，素材名是时间戳 ID，没有语义。
按 ID 从小到大排，三套是「全身画在前、护腿画在后」，**只有翠玉是反的**：

| 套 | 全身画（应作 `_layer_1`） | 护腿画（应作 `_layer_2`） | ID 顺序 |
|---|---|---|---|
| 翠玉 | `1790670229300.png`（1526 B） | `1790668020120.png`（667 B） | **护腿在前** ❌ |
| 宝石 | `1790670637200.png`（1563 B） | `1790670820040.png`（708 B） | 全身在前 ✅ |
| 星界 | `1790676421592.png`（2213 B） | `1790676959906.png`（783 B） | 全身在前 ✅ |

⇒ **按 ID 顺序分配 layer_1/layer_2 的假设，在翠玉这一对上失效了。**
翠玉两张的 ID 间隔约 37 分钟（其余两套只隔 3 / 9 分钟），推测是作者先交了护腿、隔了一会儿才交全身画。
**【推断】** 这正是"三套对、一套错"的成因；**修好后不要再依赖 ID 顺序判层级**，用本文 §7 的脚本判。

### 与作者原话的差异（以证据为准，不迎合）

作者说"**头盔变成了靴子，靴子变成了头盔**"。**像素实测不支持"头盔↔靴子"这一对**：

- 我逐套比对了 8 张层贴图的**逐区域** alpha 掩码，**没有任何一张的"头区"轮廓等于任何一张的"腿区"轮廓**
  （【像素实测】，复现见 §7）。四套（含翠玉那张错名的 `_layer_2`）的"头区"画的都是**头盔**，
  "腿区"画的都是**腿部件**。⇒ 贴图**内部**没有把头盔画到靴子的 UV 区里去。
- 16 张物品图标的 alpha 掩码两两做最近邻：**每个图标的最近邻都是"同部位、别的套"**
  （例：`jade_helmet` ↔ `gem_helmet` 距离 2；`jade_leggings` ↔ `gem_leggings` 距离 0）
  ⇒ **图标层面也没有张冠李戴**【像素实测】。
- 翠玉的实际症状（由 §1 的 UV 模型 + 像素分布推出，**【推断】**，人眼未验）：
  | 槽位 | 读哪张 | 看到什么 |
  |---|---|---|
  | 头盔 HEAD | `_layer_1` | head/hat 区**全透明** ⇒ **头盔完全不显示** |
  | 胸甲 CHEST | `_layer_1` | body 区显示的是**护腿的腰胯画**，arms 区全透明 ⇒ **护臂不显示** |

  ⇒ **真正"互相顶替"的一对是「护腿 ↔ 靴子」**（两个腿部件），不是"头盔 ↔ 靴子"；

## 1. 64×32 装备层贴图 UV 区域表（精确坐标）

### 1.1 为什么是 64×32、不是 64×64

1.21.1 的人形**盔甲模型**不是玩家模型，而是 `HumanoidArmorModel`
【读源码】`net/minecraft/client/model/geom/LayerDefinitions.java:122-124`：

```java
LayerDefinition layerdefinition1 = LayerDefinition.create(HumanoidArmorModel.createBodyLayer(OUTER_ARMOR_DEFORMATION), 64, 32);
LayerDefinition layerdefinition2 = LayerDefinition.create(HumanoidArmorModel.createBodyLayer(new CubeDeformation(1.02F)), 64, 32);
LayerDefinition layerdefinition3 = LayerDefinition.create(HumanoidArmorModel.createBodyLayer(INNER_ARMOR_DEFORMATION), 64, 32);
```

⇒ **画布是 64×32**。用 64×64 也能跑（采样只读 `y=0..31`），但 `y=32..63` 永远读不到，
很容易让人误以为"我明明画了却没效果"（脚本会对 64×64 给一条**提示**）。

### 1.2 区域表（这是本文最该被抄走的一张表）

模型绑定【读源码】：
`HumanoidModel.java:77-115`（head/hat/body/right_arm/left_arm）+
`HumanoidArmorModel.java:19-33`（**覆写**了 right_leg / left_leg）。

| 逻辑部位 | UV 块（x0,y0 ~ x1,y1，含端点） | 块大小 | 采样它的模型盒 | `layer_1` 会渲染？ | `layer_2` 会渲染？ |
|---|---|---|---|---|---|
| **头 head** | `0,0 ~ 31,15` | 32×16 | `head` `texOffs(0,0)`，8×8×8 | ✅ 头盔 | ❌ |
| **帽 hat** | `32,0 ~ 63,15` | 32×16 | `hat` `texOffs(32,0)`，8×8×8，`extend(0.5F)` | ✅ 头盔（外层壳） | ❌ |
| **双腿**（右腿+左腿） | `0,16 ~ 15,31` | 16×16 | `right_leg` / `left_leg` 都是 `texOffs(0,16)`，4×12×4 | ✅ 靴子（也是护腿的腿） | ✅ 护腿 |
| **躯干 body** | `16,16 ~ 39,31` | 24×16 | `body` `texOffs(16,16)`，8×12×4 | ✅ 胸甲躯干 | ✅ 护腿的腰胯 |

> 1.21.1 的盔甲层里**不存在**——只有**一份**臂块、**一份**腿块，左右共用（见 §1.3 的镜像机制）。
> **⚠️ 注意 2：`hat` 区常被漏掉。** `01` §3.1 的区域表里没有它；但它是**会被渲染的**
> 【读源码】`HumanoidArmorLayer.java:110-113`（`case HEAD: model.head.visible = true; model.hat.visible = true;`）。
> 它的盒子被 `extend(0.5F)` 撑大，所以是**头盔外面那层壳**，适合画冠饰/羽饰。

### 1.3 每个块的六个面在哪（盒展开规则）

Minecraft 把一个 `w×h×d` 的盒子摊在 `texOffs(u,v)` 上的规则是固定的
（`CubeListBuilder`，例：`HumanoidModel.java:82` 的 head）；按这个规则可以把 `【像素实测】` 的对错
精确到"哪个面"：

```
            u+d        u+d+w      u+2d+w     u+2d+2w
  v         [ 上 top ] [ 下 bottom]
  v+d       [右 right] [ 前 front] [左 left] [ 后 back]
```

| 块 | 上 top | 下 bottom | 右 right | 前 front | 左 left | 后 back |
|---|---|---|---|---|---|---|
| **head** `(0,0)` 8×8×8 | `8,0` 8×8 | `16,0` 8×8 | `0,8` 8×8 | `8,8` 8×8 | `16,8` 8×8 | `24,8` 8×8 |
| **hat** `(32,0)` 8×8×8 | `40,0` 8×8 | `48,0` 8×8 | `32,8` 8×8 | `40,8` 8×8 | `48,8` 8×8 | `56,8` 8×8 |
| **body** `(16,16)` 8×12×4 | `20,16` 8×4 | `28,16` 8×4 | `16,20` 4×12 | `20,20` 8×12 | `28,20` 4×12 | `32,20` 8×12 |
| **arms** `(40,16)` 4×12×4 | `44,16` 4×4 | `48,16` 4×4 | `40,20` 4×12 | `44,20` 4×12 | `48,20` 4×12 | `52,20` 4×12 |
| **legs** `(0,16)` 4×12×4 | `4,16` 4×4 | `8,16` 4×4 | `0,20` 4×12 | `4,20` 4×12 | `8,20` 4×12 | `12,20` 4×12 |

（`layer_2` 只用到 `body` 与 `legs` 两块，所以护腿画布上 `head`/`hat`/`arms` 三块**永远是纯透明**。）

### 1.4 左右镜像：为什么"只画一只臂"也能正常显示

**机制**【读源码】`HumanoidModel.java:95-112`：

```java
// right_arm
CubeListBuilder.create().texOffs(40, 16).addBox(...)
// left_arm  ← 同一个 texOffs，多了 .mirror()
CubeListBuilder.create().texOffs(40, 16).mirror().addBox(...)
// right_leg / left_leg 同理，都在 HumanoidArmorModel.java:22-31 覆写成 texOffs(0, 16)
```

`.mirror()` 的效果是：**UV 坐标不变，但把该盒子的几何按 X 轴翻转**。
⇒ 左臂/左腿读的是**与右侧完全相同的那些像素**，只是贴到镜像后的几何上。

三条实操推论：

1. **你只画一只臂（或一条腿）就够了，另一侧会自动出现**——这是"左右臂只画一只也能正常显示"
   的原因，**不是漏画**。
2. **反过来：你没法只让一侧显示。** 所以"**单侧缺失**"这类症状**一定不是装备层贴图的问题**
   （见 §5 第 6 行），要去查模型/部件可见性/渲染层冲突。
3. 因为左右共用同一块 UV，**画布上的"臂块"是对称设计的**：画在 `40,16~55,31` 里的图案会
   在左右两臂上各出现一次（互为镜像）。想让左右臂不一样是做不到的（除非改用自定义模型）。

## 2. `layer_1` vs `layer_2`：适用范围，以及用错会看到什么

### 2.1 选层规则（决定读哪张图）

【读源码】`HumanoidArmorLayer.java:80 / 163-165`：

```java
boolean flag = this.usesInnerModel(slot);            // :80
private boolean usesInnerModel(EquipmentSlot slot) { return slot == EquipmentSlot.LEGS; }   // :163-165
```

再经 `ClientHooks.getArmorTexture` → `Layer.resolveTexture`
【读源码】`ClientHooks.java:260-263`、`ArmorMaterial.java:47-50`：

```java
"textures/models/armor/" + <layer 的 path> + "_layer_" + (innerTexture ? 2 : 1) + suffix + ".png"
```

⇒ **规则只有一条**：

| 槽位 | `EquipmentSlot` | 用哪张 |
|---|---|---|
| 头盔 | `HEAD` | `_layer_1` |
| 胸甲 | `CHEST` | `_layer_1` |
| 护腿 | `LEGS` | **`_layer_2`** |
| 靴子 | `FEET` | `_layer_1` |

注意这也是 `CoeArmorItem.java:55` 的写法（`slot == EquipmentSlot.LEGS ? 2 : 1`）——
**行为与原版默认完全一致**（`06` 第三节第 13 条已核）。

### 2.2 参考实现：谁的盒子在哪一层被显示

【读源码】`HumanoidArmorLayer.java:107-128` 的 `setPartVisibility`：

| 槽位 | 打开显示的模型盒 | ⇒ 该层必须画哪几块 UV |
|---|---|---|
| `HEAD` | `head` + `hat` | head、hat |
| `CHEST` | `body` + `rightArm` + `leftArm` | body、arms |
| `LEGS` | `body` + `rightLeg` + `leftLeg` | body、legs |
| `FEET` | `rightLeg` + `leftLeg` | legs |

⇒ **`_layer_1` 要同时容纳"头盔 + 胸甲 + 靴子"三件的画**（这就是它比 `_layer_2` 大得多的原因，
也是**快速肉眼判层级的办法**：源素材里字节数明显更大、有头有臂的那张才是 `layer_1`）。

## 3. 物品图标 vs 装备层贴图：两条完全独立的路径

| | **物品图标** | **装备层贴图** |
|---|---|---|
| 路径 | `assets/<ns>/textures/item/<id>.png` | `assets/<ns>/textures/models/armor/<layerPath>_layer_{1,2}.png` |
| 尺寸 | **16×16** | **64×32** |
| 模型 | 普通 `item/generated`（注册时 `.model((ctx,provider) -> provider.generated(...))`） | 由 `HumanoidArmorLayer` 直接绑到人形模型上，**没有 JSON 模型** |
| 谁决定文件名 | 注册 id：`armor("jade_helmet", ...)` ⇒ `item/jade_helmet.png` | `ArmorMaterial.Layer` 的 `ResourceLocation`：`layerName("jade")` ⇒ `jade_armor` ⇒ `jade_armor_layer_1.png` |
| 出错时 | 图标显示紫黑格 / 显示成别的部位 | **不报错**，穿戴时才看出来（就是本文的主题） |
| 两者关系 | **毫无关系**。改图标不会影响穿戴效果；改层贴图不会影响图标 | 同左 |

**命名规则的关键**：`ArmorMaterial.Layer` **只拿一个名字**，路径是拼出来的
【读源码】`ArmorMaterial.java:47-50`。所以：

```java
new ArmorMaterial.Layer(ResourceLocation.fromNamespaceAndPath("createoreexpansion", "jade_armor"))
        ⇒ assets/createoreexpansion/textures/models/armor/jade_armor_layer_1.png
        ⇒ assets/createoreexpansion/textures/models/armor/jade_armor_layer_2.png
```

COE 的实现见 `CoeArmorMaterials.java:116-118`（`layerName(setName)` = `<setName>_armor`）与
`CoeArmorItems.java:59-69`（`textureBase = "jade_armor"`）。**两处必须拼出同一个名字**，
否则会静默回退到缺失贴图。本仓库两处一致（`06` 第三节第 13 条已核）。

> **本仓库的冗余**：`CoeArmorItem.java:52-59` 覆写了 `getArmorTexture`，拼出的路径与上面的默认
> 完全一样 ⇒ **是冗余的，但行为正确**（`01` §1 末、`06` 第三节第 13 条）。
> 注意 `ArmorItem` 在 1.21.1 **没有**这个方法，`@Override` 能编译是因为
> `Item implements IItemExtension`（NeoForge 扩展接口）【读源码】`IItemExtension.java:331-334`。

## 4. 注册侧要点（含两处"静默错误"的防御写法）

### 4.1 构造与槽位

```java
// CoeArmorItems.java:185-195 的写法（已核，正确）
new CoeArmorItem(material, ArmorItem.Type.HELMET, p.durability(Durability.JADE_HELMET), textureLoc)
                     ↑ Holder<ArmorMaterial>   ↑ 决定槽位 + 贴图层 + 标签
```

`Type` 同时决定**四件事**——写错一件都不会报错，只会静默错：

| `Type` | `EquipmentSlot`（鞘位） | 耐久倍率 | 默认名 | 应挂的标签 |
|---|---|---|---|---|
| `HELMET` | `HEAD` | ×11 | `helmet` | `#minecraft:head_armor` |
| `CHESTPLATE` | `CHEST` | ×16 | `chestplate` | `#minecraft:chest_armor` |
| `LEGGINGS` | `LEGS` | ×15 | `leggings` | `#minecraft:leg_armor` |
| `BOOTS` | `FEET` | ×13 | `boots` | `#minecraft:foot_armor` |
| `BODY` | `BODY` | ×16 | `body` | **原版没有对应标签** |

【读源码】`ArmorItem.java:149-154`（枚举声明序与倍率）、`ArmorItem.java:171-173`（`getSlot()`）。
**耐久**写在 `Item.Properties.durability(n)` 上（`ArmorMaterial` 已无耐久字段）
【读源码】`ArmorItem.java` + `Items.java` 的原版用法；`TieredItem.java:7` 是工具侧的同款写法。

### 4.2 静默错误 ①：用 `Type.ordinal()` 当护甲值数组下标

**现状**`CoeArmorMaterials.java:140-145`：

```java
EnumMap<ArmorItem.Type, Integer> defenseMap = new EnumMap<>(ArmorItem.Type.class);
for (ArmorItem.Type type : ArmorItem.Type.values()) {
    if (type.ordinal() < defense.length) defenseMap.put(type, defense[type.ordinal()]);
}
```

调用点传的是 `new int[] { 2, 6, 5, 2 }`（`CoeArmorMaterials.java:67`），**依赖枚举声明序**。
`BODY`（ordinal 4）被 `ordinal() < 4` 守卫跳过 ⇒ `getDefense(BODY)` 走
`getOrDefault(type, 0)` 返回 0（`ArmorMaterial.java:24-26`）。**当前结果是对的**（`06` R3 同条），
但**数组顺序写错不报错、不崩、只把护甲值配到别的槽位**。

**防御写法**（二选一，建议改）：

```java
// A. 显式命名，让"少写/写错槽位"变成编译期参数缺失
private static DeferredHolder<ArmorMaterial, ArmorMaterial> register(String name,
        int helmet, int chest, int legs, int boots, ...) {
    EnumMap<ArmorItem.Type, Integer> m = new EnumMap<>(ArmorItem.Type.class);
    m.put(ArmorItem.Type.HELMET, helmet);
    m.put(ArmorItem.Type.CHESTPLATE, chest);
    m.put(ArmorItem.Type.LEGGINGS, legs);
    m.put(ArmorItem.Type.BOOTS, boots);
    return ARMOR_MATERIALS.register(name, () -> new ArmorMaterial(m, ...));
}

// B. 保留数组，但把错位变成启动期错误
if (defense.length != 4) throw new IllegalArgumentException("defense 必须恰好 4 个（HELMET/CHESTPLATE/LEGGINGS/BOOTS）");
for (ArmorItem.Type type : ArmorItem.Type.values()) {
    if (type == ArmorItem.Type.BODY) continue;            // 显式跳过，不靠 ordinal 守卫
    int i = type.ordinal();
    if (i < 0 || i >= defense.length) throw new IllegalStateException("未覆盖槽位: " + type);
    defenseMap.put(type, defense[i]);
}
```

### 4.3 静默错误 ②：`default -> ...` 把未知槽位兜到某个标签

**现状**`CoeArmorItems.java:198-206`：

```java
return switch (type) {
    case HELMET -> ItemTags.HEAD_ARMOR;
    case CHESTPLATE -> ItemTags.CHEST_ARMOR;
    case LEGGINGS -> ItemTags.LEG_ARMOR;
    case BOOTS -> ItemTags.FOOT_ARMOR;
    default -> ItemTags.HEAD_ARMOR;      // ← BODY（狼/马甲）本模组不使用
};
```

**`default ->` 的存在把"穷尽性检查"关掉了**：将来加一个 `BODY` 盔甲，它会被**静默塞进
`#minecraft:head_armor`** ⇒ 变成可被头盔类附魔附上，且**不报错**。
（原版也没有 `body_armor` 标签：【资源实测】`data/minecraft/tags/item/` 只有
`head_armor/chest_armor/leg_armor/foot_armor`。）

**防御写法**——**去掉 `default`，让 Java 的穷尽性检查接手**，并对拒绝的槽位抛异常：

```java
private static TagKey<Item> armorTag(ArmorItem.Type type) {
    return switch (type) {
        case HELMET -> ItemTags.HEAD_ARMOR;
        case CHESTPLATE -> ItemTags.CHEST_ARMOR;
        case LEGGINGS -> ItemTags.LEG_ARMOR;
        case BOOTS -> ItemTags.FOOT_ARMOR;
        case BODY -> throw new IllegalArgumentException("COE 不使用 BODY 盔甲槽（原版无 body_armor 标签）");
    };
}
```

> 与 4.2 同一个道理：**能变成编译期/启动期错误的，就不要留给"读注释的人"**。
> 这两条都是 `06` 的 R3 / R5，本文只是把"怎么写对"补上。

### 4.4 贴图缺失时的回退

`getArmorTexture` 返回 `null` 时走 `layer.texture(innerModel)`
【读源码】`ClientHooks.java:260-263`。COE 的覆写**永远返回非 null**，所以
**文件不存在时不会回退，而是直接报缺失贴图（紫黑格）**。新增一套盔甲时，
`_layer_1` 与 `_layer_2` **必须两张都有**——`_layer_2` 漏了就是护腿变紫黑格。

### 6.3 `TieredItem` 与耐久

`TieredItem.java:3-9`：构造器只有一句 `super(properties.durability(tier.getUses()))`，

### 6.4 工具类别标签决定能否附魔（不是附魔值）

链条【资源实测】`01` §4：

## 7. 可复现的检查方法：`tools/armor-layer-check.py`

### 7.1 它做什么

一条命令，扫描 `coe`（存在时的 `cews`）下所有 `textures/models/armor/*_layer_1.png` 与 `*_layer_2.png`：

1. **纯标准库**解码 PNG（`zlib` + `struct`，无第三方依赖、不写临时文件、**只读**）；
2. 按 §1.2 的区域表逐块统计**不透明像素数**（`--verbose` 还会逐面统计）；
3. 按 §1.5 的三条基线**断言**：
   - `layer_1` 允许区 = head / hat / legs / body / arms；`layer_2` 允许区 = **body / legs**；
   - **"不该有内容却有内容"** ⇒ 可疑（`layer_2` 里有 head/hat/arms 像素、`unused` 区有像素 ⇒ 错误）；
   - **"本应有内容却全透明"** ⇒ 可疑（`layer_1` 头/腿/身+臂全空；`layer_2` 腿或身全空）；
4. 打印人类可读表格 + **具体到文件与区域的修法提示**；
5. 附带检查 16 张物品图标：尺寸、不透明数、**alpha 形状指纹**（同一套里两个图标形状完全相同 ⇒ 可疑）。

   §0 那张"各槽位看到什么"、§8.2 的人眼清单都是**由 UV 模型 + 像素分布推出的【推断】**。
   机制层面我逐行核到了源码（行号见 §9.3），所以对结论有信心，但**严格说它不是【实测】**。
2. **作者说的"头盔变成了靴子"我复现不出字面现象。** 证据指向的是
   「头盔与护臂**不渲染**」+「**护腿 ↔ 靴子**互相拿到对方的图案」（§0 末）。
   两种可能：① 作者原话是概括性描述；② 我漏了另一处问题。
   **要区分只需一个实机截图**（戴上翠玉头盔后的第三人称头部）。本文不下断言。
3. **翠玉那两张到底是"操作失误"还是"当年就画成这样"**：我能证明"内容与文件名语义不符"
   以及"源 zip 里就已是这个顺序"，**不能**证明是哪一步的手误。修法相同，但**动不动用户素材必须先问作者**。
4. **配色/造型是否与物品图标一致、是否穿模**：脚本只能看 alpha 形状，**看不了颜色与叠加**。
   `06` §四第 8 条同样列为未确认。这部分只能人眼。
5. **`hat` 区是不是"故意"用来画冠饰**：四套里 `hat` 都有内容（98/40/36/32），我推断是刻意的冠饰，
   但**没有**作者确认，也没有对照过源素材的分层意图。
6. **`cews` 是否将来会加盔甲**：当前没有（【资源实测】），但本文的判据对 `cews` 同样适用（脚本默认扫它）。
7. **脚本的判据是"结构正确"，不是"美术正确"**。一张区域全对但画得很难看的贴图，
   脚本会判它 ✅。**这是设计取舍，不是缺陷**——结构错（层级/区域）能自动化，
   美术错只能人眼，两者别混。
