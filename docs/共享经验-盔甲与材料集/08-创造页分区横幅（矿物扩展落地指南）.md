## 1. 目标形态

`base_tab` 一页，里面三段：**分区横幅行（整行空格子）→ 该区物品 → 分区横幅行 → …**。

```
┌──────────────────────────────────────────────┐  ← 物品格区域：9 列 × 18 = 宽 162
│                                              │  ← 第 0 行：整行空格子 → 在此画「矿物」横幅
│ [矿物 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓]  │
│  翡翠矿石 粗翡翠 翡翠锭 翡翠粒 翡翠板 …        │  ← ① 矿物（76 项）
│  ...                                          │
│                                              │  ← 整行空格子 → 「机械」横幅
│ [机械 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓]  │
│  翡翠机壳 动力角磨床 应力充能器 角磨轮 …       │  ← ② 机械（22 项）
│                                              │  ← 整行空格子 → 「装备」横幅
│ [装备 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓]  │
│  翡翠剑 翡翠镐 … 四套盔甲 … 翠玉之弓           │  ← ③ 装备（48 项）
└──────────────────────────────────────────────┘
```

硬约束三条（后面所有代码都只是为了满足它们）：

1. **列表里必须有「整行空格子」** —— 渲染端只认这个事实（§6.4），不信任行号算术；
2. **横幅是叠加画上去的，不是物品** —— 横幅不进 `displayItems`，由客户端渲染钩子画在最上层；
3. **横幅行 = 该分区第一个物品的上一整行** —— 所以每个分区之后必须「补满当前行 + 再空一整行」。

## 3. 横幅资源（作者提供，已放置）

### 3.1 素材事实（**【像素实测】**，本轮用代码读 PNG 头 + 解压 IDAT 逐像素统计）

| 原始文件 | 字节数 | SHA256（前 16 位） | 尺寸 | 位深/色彩类型 | Alpha 实测 |
|---|---|---|---|---|---|
| `矿物.png` | 1036 | `35BA40D7E06D02D7` | **162×18** | 8bit / colorType 6（RGBA） | min=255 max=255；**全不透明**，0 个半透明、0 个全透明像素 |
| `机械.png` | 1959 | `491584AB4ECC9678` | **162×18** | 8bit / colorType 6（RGBA） | 同上，**全不透明** |
| `装备.png` | 3108 | `930594AD9A065466` | **162×18** | 8bit / colorType 6（RGBA） | 同上，**全不透明** |

- 三个文件的 PNG chunk 序列一致：`IHDR, sRGB, sBIT, pHYs, IDAT, IEND`，无 `tRNS`、无 `iCCP`、无 `APNG`。
- **尺寸恰好 = 参考实现的横幅尺寸**（`03` §步骤 7：横幅宽 = 9 × 18 = 162、高 = 18）——这三张就是为此准备的。
- **图层内容**：三张都是**纯装饰的图案条**，**没有烘焙任何文字**。
  所以「矿物 / 机械 / 装备」三个释词要**由代码画上去**（§5 步骤 6）。
- ⚠ **全不透明**是个必须知道的后果：横幅会**完全盖住它下面那一整行的 9 个格子底图**。
  这正是我们要的效果（那一行本来就没有物品），但意味着**不能**指望「半透明底图透出格子边框」——
  横幅行与相邻行之间的边框接缝要靠像素对齐处理（§5 步骤 7 的 `y` 选择）。
- **归属判定**：文件名与分区名**逐字对应**（矿物 / 机械 / 装备），不需要作者再指认。
  见 `矿物.png` 的画面（灰色石底 + 右侧金色矿粒）、`机械.png`（蓝绿机械格栅）、
  `装备.png`（红紫绿混色织物）。**【推断】**：三张只按文件名对应即可，无需看画面。

### 4.5 【推断】为什么这件事在 COE 比在 `bettergold` 难

`bettergold` 的创造页是**自己写的 `SectionedCreativeTab.builder(...)`**：
生成器里 `displayItems` 的候选集合由它自己给，所以它想怎么排就怎么排。

COE 的 `base_tab` 内容**由事件在 `getDisplayItems()` 之外构造**（§4.1~4.3），
所以 **`withTabFactory` + 覆写 `getDisplayItems()` 这一招单独用是不够的** ——
必须再决定「Registrate 塞进来的那一份顺序怎么办」。三条路：

| 路 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | **顺序由后处理接管**：生成器仍留空（让 Registrate 的事件照旧塞），在**渲染前的最后一刻**按 §5 步骤 3 的规则把真实列表切段、插空行、按分区顺序重排 | 需要一个「拿到真实列表」的时机（`BuildCreativeModeTabContentsEvent` 之后）；对「别的模组也往本页塞东西」最宽容（长度守卫生效即回退） |
| B | **注册期就接管顺序**：在 `EnergyWaveStudyTab` 同级再加一个监听器，对本页 `remove` + 按分区顺序 `accept` 全部 146 项 | 146 项要写死或全靠规则算；`event.accept` 对重复项**会抛**（`already exists in the tab's list`，见 `EnergyWaveStudyTab.java:162-170` 的事故记录），所以必须**先 remove 再 accept**，且每件都要走一遍 |
| C | 改 `LayerCreativeTab.registerAll` 给页加 `.displayItems(...)` | **会和 Registrate 打架**：事件仍会塞 146 项，而 `displayItems` 又塞一遍 ⇒ `IllegalStateException: Accidentally adding the same item stack twice`（`CreativeModeTab.java:396-403`）|

**本文档给出的步骤按 A 写**（§5 步骤 4）。B 是等价可行的退路，C **不要走**。

### 步骤 3 ☐ 排布：`layout()` 与 `SECTION_ROWS`

照抄 `bettergold` 的 `01` §5 / `03` 步骤 3，**三个不能改的地方**：

```java
public static final int ITEMS_PER_ROW = 9;

/** key = "分区key"，value = 该分区【首个物品】所在行（0 基）。横幅行 = 值 − 1。 */
public static final Map<String, Integer> SECTION_ROWS = new LinkedHashMap<>();

public static List<ItemStack> layout(String tabKey, List<Bucket> buckets) {
    List<ItemStack> out = new ArrayList<>();
    SECTION_ROWS.keySet().removeIf(k -> k.startsWith(tabKey + "|"));

    for (int i = 0; i < ITEMS_PER_ROW; i++) out.add(ItemStack.EMPTY);   // ① 开头补一整行（勿删）

    for (int b = 0; b < buckets.size(); b++) {
        Bucket bucket = buckets.get(b);
        SECTION_ROWS.put(tabKey + "|" + bucket.key(), out.size() / ITEMS_PER_ROW);  // ② 取样在加物品【之前】
        out.addAll(bucket.items());
        if (b == buckets.size() - 1) break;                            // 最后一区不补
        int used = bucket.items().size() % ITEMS_PER_ROW;
        int pad = (ITEMS_PER_ROW - used) % ITEMS_PER_ROW + ITEMS_PER_ROW;  // ③ pad 一定 ≥ 9：补满本行 + 再空一整行
        for (int i = 0; i < pad; i++) out.add(ItemStack.EMPTY);
    }
    return out;
}
```

另外两条必须写进代码的纪律：

- **空桶要跳过**（某分区 0 项时不要给它记行号、也不要给它留空行）：否则会画出「横幅下面直接是下一条横幅」。
- **兜底**：三区都没命中的物品（本页按 §8 应为 0 项，但将来可能变）单独收进一个**不加横幅的尾桶**，
  只补行不求释词——**宁可在末尾堆着，也不要让物品凭空消失**（`03` 步骤 2：「一件物品凭空消失是最难查的 bug」）。

**验收点**（不用跑游戏，纸上可算）：对每一区验不变量
`R_{b+1} == ceil((R_b × 9 + n_b) / 9) + 1`（`01` §9 的 I6）。
**不要**用「长度 % 9 == 0」当断言——最后一区不补，长度一般不是 9 的倍数。

### 步骤 7 ☐ 把 `SECTION_ROWS` 映射到屏幕坐标

**三个算式，一个都不能错。**

```
① 首个可见行（照抄原版 ItemPickerMenu#getRowIndexForScroll，CreativeModeInventoryScreen.java:1029-1035）
   rowCount        = positiveCeilDiv(items.size(), 9) - 5      // 可能 ≤ 0，必须先判掉
   firstVisibleRow = max((int)(scrollOffs * rowCount + 0.5), 0) // 注意是 (int) 截断，不是 Math.round

② 记录值 → 可见行
   anchor = SECTION_ROWS.get(key) - firstVisibleRow             // 记录值记的是「首物品行」
                                                                // 减完 0..4 才是可见行；越界就不画

③ 可见行 → 屏幕坐标（8/17/18 的来源见下）
   x = leftPos + 8
   y = topPos + 17 + row * 18
```

```java
private static int firstVisibleRow(ItemPickerMenu menu, float scrollOffs) {
    int rowCount = Mth.positiveCeilDiv(menu.items.size(), ITEMS_PER_ROW) - VISIBLE_ROWS;
    if (rowCount <= 0) return 0;                       // ← 不满 5 行时不能乘出负数
    return Math.max((int) ((double) (scrollOffs * (float) rowCount) + 0.5), 0);
}
```

**`8 / 17 / 18` 是哪来的**（**【读源码】** + 参考实现 **【像素实测】**）：

- 物品槽按 9 列 × 5 行注册，坐标 `9 + 列 × 18, 18 + 行 × 18`（`CreativeModeInventoryScreen.java:1010`）。
  这是**物品（16×16）**的绘制位置（`AbstractContainerScreen#renderSlot` 取 `slot.x/slot.y`）。
- 而**格子底图是 18×18**，左上角比物品坐标各少 1 像素。参考实现直接取客户端 jar 里
  `assets/minecraft/textures/gui/container/creative_inventory/tab_items.png` 读像素核实：
  第一格是 `x = 8..25 / y = 17..34`（正好 18×18），周期 18；格子内部 16×16 从 `(9, 18)` 开始，与槽位坐标严丝合缝
  （`bettergold` 文档 `03` 步骤 7 有逐像素记录）。
- ⇒ **物品区（一整格栅格）左上角 = `(leftPos + 8, topPos + 17)`**；一格 18 像素；
  横幅 162 × 18 正好铺满一整行。

> **一行像素的取舍**：`y = topPos + 17` 让横幅与**格子**严格对齐，代价是横幅最下面一行像素
> 压到了**下一行格子的上边框**（因为横幅不透明，会盖掉它）。
> 若不喜欢这个接缝，可改成 `y = topPos + 18`（与**物品图标**对齐）——但那样横幅的最上一行又会露出上一行的格子底。
> 两种都能用，**必须人眼在 §7.4 里挑一个**。

**然后做自适应判定**（§6.4）：不要直接算 `记录值 − 1`，而是「目标行整行空就画那里，否则看上一行，都不空就不画」。

```java
private static int bannerRow(ItemPickerMenu menu, int anchor) {
    if (isRowEmpty(menu, anchor))     return anchor;      // 记录值本身就是横幅行
    if (isRowEmpty(menu, anchor - 1)) return anchor - 1;  // 记录值是首物品行 ⇒ 上一行是横幅行
    return -1;                                            // 两行都不空 ⇒ 不画
}
private static boolean isRowEmpty(ItemPickerMenu menu, int row) {
    if (row < 0 || row >= VISIBLE_ROWS) return false;
    int first = row * ITEMS_PER_ROW;
    if (first + ITEMS_PER_ROW > menu.slots.size()) return false;
    for (int i = first; i < first + ITEMS_PER_ROW; i++)
        if (menu.getSlot(i).hasItem()) return false;      // 读【槽位】，不读 items 列表
    return true;
}
```

**绘制顺序（与参考实现一致）**：① `blitSprite` 横幅 → ② 在横幅左端画半透明释词底方块 → ③ 写释词文字。

```java
private static void drawBanner(GuiGraphics g, ResourceLocation banner, Component title, int x, int y) {
    g.blitSprite(banner, x, y, BANNER_WIDTH, BANNER_HEIGHT);   // 162×18 = 1:1，不拉伸
    Font font = Minecraft.getInstance().font;
    int w = font.width(title);
    g.fill(x + 3, y + 3, x + w + 3 + 5 + 3, y + BANNER_HEIGHT - 3, 0x90000000);  // 半透明底方块
    g.drawString(font, title, x + 5, y + 5, 0xFFFFFFFF, true);                    // true = 带阴影
}
```

因为三张横幅**全不透明**（§3.1），这个 `0x90000000` 底方块是**必需**的：没有它，
释词会直接压在横幅的花纹上（`装备.png` 是红紫绿混色，白字读数会很难看）。

### 步骤 8 ☐ 先画纯色矩形，再换真贴图

**不要**一步到位。参考实现走过弯路的顺序（`03` 步骤 9）：把
`g.blitSprite(banner, …)` 先临时换成 `g.fill(x, y, x + 162, y + 18, 0xFFFF00FF)`：

- 位置对、滚动跟随 → 坐标算对了 → 再换成真贴图；
- 位置不对 → 是**坐标**问题，跟贴图路径无关。

「横幅不出现」有三种完全不同的原因（坐标错 / 贴图路径错（静默紫黑格）/ 条件没进），
这一步能一次性把第一种排除掉。

## 6. 必须避开的坑（逐条：现象 → 根因 → 修法）

> 本节全部摘自参考实现 `02`，**依据等级标在每条末尾**，并注明在 COE 现状下的适用性。

### 6.1 `output.accept(ItemStack.EMPTY)` **会抛异常**，不是被过滤

- **现象**：想用 `accept(EMPTY)` 插空行 ⇒ 整个页的构建**中断**，`IllegalArgumentException: The stack count must be 1`。
- **根因**：两道一模一样的校验，都要求 `count == 1`，而 `ItemStack.EMPTY.getCount()` 是 **0**。
  ① NeoForge 包装层：`EventHooks.onCreativeModeTabBuildContents` 的 lambda —— `if (stack.getCount() != 1) throw new IllegalArgumentException("The stack count must be 1");`；
  ② 原版：`CreativeModeTab.ItemDisplayBuilder#accept`（`CreativeModeTab.java:392-395`）—— `"Stack size must be exactly 1"`。
- **修法**：**不要在 `Output` 里塞空行**。生成器只 accept 非空格子，空行在 `getDisplayItems()` 里补（§5 步骤 4）。
  这条成立的依据：创造界面读的就是 `getDisplayItems()`（`CreativeModeInventoryScreen.java:643`），
  而且**原版自己也往 `menu.items` 里放 `EMPTY`**（`:635`，快捷栏页的空位）。
- **顺带**：`accept` 还会对**重复 stack** 抛 `IllegalStateException("Accidentally adding the same item stack twice …")`
  （`CreativeModeTab.java:396-403`）⇒ **一件物品只能进一个桶**。
- **COE 适用性**：完全适用。**`EnergyWaveStudyTab.java:162-170` 已经因为「重复添加」崩过一次实测**
  （`already exists in the tab's list`）——同一个家族的问题。
- 【读源码】+【参考实现实测】

### 6.2 GUI 图集只扫 `textures/gui/sprites/`：`blitSprite` 查不到会**静默**退化成紫黑格

- **现象**：贴图放在 `textures/gui/某子目录/`，用 `blitSprite` 画 ⇒ 什么都没画出来（紫黑相间 missing texture 图案），
  **客户端日志一条报错、一条警告都没有**。
- **根因（三层）**：① `GuiGraphics#blitSprite` 只查 GUI 图集（`:681-683` → `this.sprites.getSprite(sprite)`，
  `this.sprites` 是 `minecraft.getGuiSprites()`）；② 该图集**只有一个目录源**
  （`GuiSpriteManager` 把 atlas info 定为 `minecraft:gui` ⇒ `assets/minecraft/atlases/gui.json`，
  里面是 `{"sources":[{"type":"directory","source":"gui/sprites","prefix":""}]}`）；
  ③ 查不到不报错 —— `TextureAtlas#getSprite` 是 `getOrDefault(name, this.missingSprite)`。
- **修法**：**放进 `gui/sprites/` 用 `blitSprite`**（本文采用，资源已就位），或改用 `graphics.blit(...)` 直接 blit。
- **COE 适用性**：这正是 §3.2 选路径的依据。**注意 COE 原来的 `textures/gui/` 下只有 `sprites/` 一个子目录**
  （本轮核实为空目录），所以没有历史包袱。
- 【读源码】+【参考实现实测】

### 6.3 `DeferredHolder` 别名**不能**写成 `= Family.holder`：类初始化循环（NPE）

- **现象**：编译通过，`runServer` 在 mod 构造阶段崩：
  `ExceptionInInitializerError` → `Caused by: NullPointerException`（读一个「还在初始化中」的静态字段）。
- **根因**：JVM **不会重入**正在初始化中的类。链条：
  `AllBlocks.<clinit>` → 读 `AllMetals.X.ingot` → 触发 `AllMetals.<clinit>` → 家族构造器注册物品 →
  触发 `AllItems.<clinit>` → 又要读 `AllMetals.X` → 此时它还没赋值 ⇒ `null` ⇒ NPE。
- **修法**：改用**不参与注册的懒绑定别名**：

```java
public static <T extends Item> DeferredItem<T> item(String path) {
    return DeferredItem.createItem(ResourceLocation.fromNamespaceAndPath(MODID, path));   // 只构造，不查注册表
}
```

  `DeferredHolder(ResourceKey)` 造出来是**未绑定**的，第一次 `get()` 时才现查（`DeferredHolder.java:148-157`）。
- **通用纪律（比坑本身值钱）**：**类初始化期间只能「构造对象」，不能「读取注册项」。**
- **姊妹坑**：注册期不能 `.get()` —— `DeferredHolder.value()` 会抛
  `NullPointerException: Trying to access unbound value: <key>`（`DeferredHolder.java:100-107`）。
  任何「注册名 → 物品」的反查表都必须**懒解析 + 缓存**。
- **COE 适用性**：**高**。COE 有**三个** Registrate 共用同一个命名空间（§4.2），
  又刚做过「每层 Registrate 自持创造页」的拆分；「注册期读注册项」在这里是最容易踩的一类。
  本轮 grep 确认 COE 已有 `CoeItems.register()` ↔ `CoeArmorItems.register()` 这类显式触发顺序
  （`CoeItems.java:1397-1403`、`CreateOreExpansion.java:195-225`）——**新增的分区类不要打破这条顺序线索**。
- 【读源码】+【参考实现实测】（有最小复现 `CycleDemo.java` 与完整栈）

### 6.4 横幅行必须**整行皆空**才画；渲染端不要写死 `−1`

- **现象**：横幅压在物品图标上；或整条横幅不画（行号越界/负数）。
- **根因**：硬编码「横幅行 = 记录值 − 1」只在「列表内容与生成时完全一致」时成立。
  别的模组往本页插/删物品、或你自己改了记录语义，都会失准。
- **修法**：**自适应判定 —— 只认「整行空格子」这个事实**（§5 步骤 7 的 `bannerRow`/`isRowEmpty`）。
  它同时兜住两种记录语义，**从构造上保证绝不会把横幅画到物品上**。代价是每帧多做 9~18 次 `hasItem()`，可忽略。
- **不要**把「整行空」判成「`items` 列表里对应位置是 EMPTY」——
  渲染时应该读**槽位**（`menu.getSlot(i).hasItem()`），因为槽位才是真正被绘制的东西
  （由原版 `scrollTo` 从 `items` 拷来，`:1049-1061`）。
- **COE 适用性**：**必须照做**。COE 用公开 API 与其它模组共存（不是 Mixin 独占），
  而且 `EnergyWaveStudyTab` 就在同一个事件上对本页做 remove/accept —— 说明这个页**确实会被别人动**。
- 【读源码】+【参考实现实测】（有逐可见行 `empty=true/false` 的日志）

### 6.5 创造页排序锚点**不能**选 `HOTBAR / SEARCH / OP_BLOCKS / INVENTORY`

- **现象**：自己的页跑到创造界面的**第二页**，或顺序莫名其妙。
- **语义**：`withTabsBefore(X)` = 「X 在本页**之前**」（本页排在 X 后面）；
  `withTabsAfter(X)` = 「X 在本页**之后**」（本页排在 X 前面）。**两者读起来都容易反。**
- **根因**：`CreativeModeTabRegistry.recalculateItemCreativeModeTabs()` 里，
  `DEFAULT_TABS` 的四页被排除在排序图的**节点**之外，但**边**没有做同样的排除；
  Guava 的 `putEdge` 在端点不存在时会**自动补上节点**。
  ⇒ 你只要 `withTabsBefore(CreativeModeTabs.HOTBAR)`，HOTBAR 就被这条边拉回排序图，
  把原本「不参与排序」的原版页插到不该出现的位置。
- **正解**：整条链锚在**普通原版页**的末尾（`CreativeModeTabs.SPAWN_EGGS`），页与页之间用 `withTabsAfter` 串链。
  **每页都至少要有**一条 `withTabsBefore` 或 `withTabsAfter`，不要依赖「没写就连在最后」那条分支。
- **COE 适用性**：**已合规，别改坏**。`CoeCreativeTabs.java:27-31` 现在锚的是
  `LayerCreativeTab.ENERGY_WAVE_STUDY_TAB_ID`（= CEWS 的页，本站的普通页），
  顺序 = 矿物拓展 → 能量波阵学 → Create 调色板。**分区化不改这个锚**。
  另外 NeoForge 硬编码了 `int vanillaTabs = 10;`（假定注册顺序里前 10 个非默认页就是原版页），
  别的模组在你之前注册额外页时这个 10 会失准 —— 结论不变：自己的页一律显式写锚。
- 【读源码】（机制）+【记录】（「原版页被挤到第二页」的现象，那轮日志未留档）

### 6.6 卷动跟随：`scrollOffs` → 首个可见行 必须用原版公式

- **现象**：横幅不跟着滚（一直画在同一行）；或滚动时跳一格/差一行；或某些滚动位置横幅消失。
- **公式（`CreativeModeInventoryScreen.java:1029-1035`）**：

```java
protected int calculateRowCount()          { return Mth.positiveCeilDiv(this.items.size(), 9) - 5; }
protected int getRowIndexForScroll(float s){ return Math.max((int)((double)(s * (float)this.calculateRowCount()) + 0.5), 0); }
```

  这两个方法是 `protected`（在公开内部类 `ItemPickerMenu` 上），外部无法直接调用 ⇒ **自己照抄公式**。
- **最容易写错的一格**：`scrollOffs = 0.75` 时（`items = 72 ⇒ rowCount = 3`）
  `0.75 × 3 + 0.5 = 2.75` → `(int)` **截断成 2**，**不是** 3。所以**不要用 `Math.round`**，要用 `(int)(x + 0.5)`。
- **修法纪律**：客户端**不要另算一套行映射**，就用这个公式 + 原版 `scrollTo` 已经填好的槽位；
  渲染端**只读 `menu.slots`**，不再自己索引 `items`。
- **COE 适用性**：完全适用（`ItemPickerMenu` 是原版内部类，与模组无关）。
- 【读源码】+【参考实现实测】（`0/0.25/0.5/0.75/1.0` 五个值的公式自检日志）

### 6.7 探针四条铁律：只能 `halt` 一次、**绝不留 `halt` 在产物里**、`run\` 独占、只读 JSON/源码不算验证

1. **关服只能调一次 `halt(false)`。**
   - 现象：探针收尾先 `server.stopServer()` 再 `server.halt(false)` ⇒ 日志停在存盘流程里不再推进，看起来像卡死。
   - 根因：`MinecraftServer.halt(boolean)` **只做一件事** —— 把 `running` 置 `false`；
     真正的关闭/存盘在 `runServer()` 的 `finally` 里（`stopServer()`）。你手动调过 `stopServer()` 之后，
     `finally` 里**必然**再走一遍 ⇒ 两遍 "Stopping server" + 两遍存盘。
   - 修法：**只调一次 `halt(false)`**，随后原版自己完成 `Stopping server → 存盘 → 卸载 config`。
   - 附带结论：探针收尾异常会让 `runServer` **以非零码结束**；看到 `BUILD FAILED … non-zero exit value -1`
     且**没有** "Stopping server"，先怀疑探针收尾，**不要先怀疑业务代码**。
2. **能关掉别人游戏/服务器的能力（`halt`、`System.exit`、`stopServer`）绝不允许进生产代码。**
   - 事故：曾有一个临时探针在别人客户端进世界时触发 `halt`，把对方正在跑的集成服务器关掉，整轮验证作废。
   - 纪律：探针收尾要**整块删除**（不是注释掉），并给出 `grep` 证据（`TEMP-|PROBE|halt\(|stopServer\(` 零命中）。
3. **`run\` 目录是独占资源。**
   - 同时跑两个客户端（或客户端 + 服务端）会抢 `run\logs\latest.log`、`options.txt`、世界文件；
     症状是**卡在 100% 加载不动**，或 `Unable to delete file … latest.log`。
   - 重跑前删 `run\world\session.lock` 与 `run\saves\*\session.lock`。
   - **杀进程要精准**：只杀命令行里含 `forgeclientdev` / `forgeserverdev` 的 java 进程；
     **不要** `Get-Process java | Stop-Process -Force`（会连带杀掉 Gradle daemon、写坏配置缓存）。
   - 多人/多代理协作时由协调方**逐个发放** `run\` 许可。**COE 的 `run\` 现在可能被别人占着。**
4. **只读 JSON / 源码不算验证。**
   - 事故：读了掉落表 JSON 里 `chance=0.36` 就宣称修好了，实际那份表**根本没被加载**（解析失败）。
   - 纪律：任何**数据文件**（JSON/标签/配方/模型/语言）都必须让游戏**真的加载它**并留下日志证据；
     任何**渲染**都必须让渲染路径真的执行并留下坐标日志。「我读了源码，逻辑是对的」只能证明逻辑对，
     **不能证明这段逻辑跑起来了**。
5. **探针输出中文会按 GBK 写出**，重定向后按 UTF-8 读会乱码
   ⇒ 探针把中文转成 `\uXXXX` 再打印（本仓探针日志里的 `\u77FF\u7269`（矿物）就是这么来的）。
- 【读源码】+【参考实现实测】+【记录】

### 6.8 构建判读：PowerShell 会把 javac 的「注:」记成 `NativeCommandError`，假报 exit 1

- **现象**：`.\gradlew.bat build 2>&1 | Tee-Object …` 之后 pwsh 打印红色的
  `NativeCommandError` / `注: 某些输入文件使用或覆盖了已过时的 API`，看起来构建失败。
- **根因**：javac 的提示写在 **stderr**；PowerShell 把原生命令写进 stderr 的内容一律记成 `NativeCommandError`。
  这与 Gradle 的退出码无关。
- **修法**：判断成败**只看** Gradle 输出的 `BUILD SUCCESSFUL` / `BUILD FAILED`，或 `$LASTEXITCODE`。
  想让日志干净就把 stderr 单独重定向到文件（`2>build\x.err`）。
  **同理**：`git push` 的进度信息也走 stderr。
- 【参考实现实测】

### 6.9 编码与文件（会浪费半天的那类问题）

1. **一律无 BOM。** Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` **会写 BOM**，
   JSON 与 `.java` 都可能因此出问题。用编辑工具，或
   `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`。
2. **不要用 `Get-Content` / `Set-Content` 做文本替换**：会把中文注释变成乱码（本仓中过两次，只能靠 git 恢复）。
   必须用 PowerShell 时走 `ReadAllText` / `WriteAllText` + 显式 UTF-8。
3. **删代码块按「标记 + 锚点」成对定位**，不要用行数算术（曾多切 4 行，切出多余右括号，构建失败）。
4. 本仓 `.java` 多为 **CRLF**；`docs\` 下的 Markdown 用 **LF**（跨平台好读）——
   本文与 `docs\共享经验-盔甲与材料集\` 其余文件一致，是 **LF 无 BOM**（本轮已核实）。

### 7.1 服务端探针要打印什么

挂在 `ServerStartedEvent`（或 `FMLCommonSetupEvent` 之后任意服务端时机），**直接读 `CreativeModeTab#getDisplayItems()`**。

> ⚠ **【参考实现实测】踩坑提醒**：专用服务器在 `ServerStartedEvent` 时**还没有**构建过任何页的内容，
> 此时读 `getDisplayItems()` 会得到 **0**（不是「丢物品」，是「还没构建」）。探针必须先让原版走一次构建：
> ```java
> CreativeModeTabs.tryRebuildTabContents(server.getWorldData().enabledFeatures(), false, server.registryAccess());
> ```
> 这条路与客户端进创造界面时走的完全相同，所以读到的仍是「游戏真实构建出来的」结果。

**① 本页一行汇总**（字段名建议用 `bucketItems` 而不是 `buckets`，避免看错）：

| 打印项 | 期望 |
|---|---|
| `displayItems` | 显式物品列表长度（含空行） |
| `nonempty` | 其中非空格子数 = **146**（本轮静态清点值，§4.4 / §8） |
| `blankSpacer` | 空格子数 = `displayItems − nonempty` |
| `sections` | 分区数 = **3** |
| `bucketItems` | 所有桶物品数之和 |
| **三方相等** | `nonempty == candidates == bucketItems` ⇒ **一件都没丢、也没有重复放入** |

> ⚠ **146 是【读源码/脚本清点】的数字，不是【实测】。** 探针第一次跑出来如果不是 146，
> **先查是不是本轮清点漏了什么**（最容易漏的是「三个机壳的物品」与「10 个角磨轮」，见 §4.4 三条要点），
> **不要**直接把自己的规则改成去迎合 146。

```java
int nonempty   = (int) tab.getDisplayItems().stream().filter(s -> !s.isEmpty()).count();
int candidates = /* 你的候选/规则算出应有的项数 */;
int bucketSum  = buckets.stream().mapToInt(b -> b.items().size()).sum();
LOGGER.info("[probe] check: nonempty {} vs candidates {} vs buckets {} -> {}",
        nonempty, candidates, bucketSum,
        (nonempty == candidates && candidates == bucketSum) ? "OK none lost" : "MISMATCH");
```

**② 每一个分区一行**：

| 打印项 | 期望 |
|---|---|
| `secN` | 分区序号 = 显示顺序，**必为 `sec1`=矿物 → `sec2`=机械 → `sec3`=装备**（作者明确要求这个顺序） |
| 释词 | 中文**转义成 `\uXXXX`** 打印（避免 GBK 乱码）：`\u77FF\u7269` 矿物 / `\u673A\u68B0` 机械 / `\u88C5\u5907` 装备 |
| `firstItemRow` | 该分区首物品所在行（`SECTION_ROWS` 的值）；**首区恒为 1** |
| `bannerRow` | `firstItemRow − 1`；**首区恒为 0** |
