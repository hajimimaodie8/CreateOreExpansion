# 02 - 可复用的“材料集”抽象

> 这篇讲的是源仓库 `bettergold` 用过的组织方式：**一种金属的整套内容（材料链 + 建材 + 器具 + 盔甲 +
> 升级模板）一次注册**，新增材料只改一处清单。
> 更重要的是**它踩过的那个别名坑**——那个坑在本仓库同样可能踩到，症状是「编译全绿、进游戏就崩」。

---

## 1. 目标：新增一种材料，只改一处

源仓库的 `MetalFamily.Spec` 就是那张“一处”的表
【读源码】`bettergold/.../material/MetalFamily.java:448-524`。字段清单（可以直接照抄结构）：

| 分类 | 字段 | 说明 |
|---|---|---|
| 身份 | `id` / `cnName` | 注册 id 前缀 + 中文名（给生成器与日志用） |
| 材料 | `fireResistant` | 防火防爆（决定 `Item.Properties.fireResistant()`） |
| 工具 | `durability` / `miningSpeed` / `attackDamageBonus` / `enchantmentValue` / `incorrectForDrops` | 直接喂给 `SimpleTier`（一个 `record implements Tier`） |
| 盔甲 | `armorDefense[4]` / `armorDurability[4]` / `armorEnchantmentValue` / `armorToughness` / `armorKnockbackResistance` | 喂给 `new ArmorMaterial(...)` 与逐件 `Properties.durability` |
| 建材 | `blockStrength` / `blockResistance` / `detailStrength` / `detailResistance` | 方块强度 |
| 特性 | `autoSmelt` / `thunderStrike` / `contactEffect` / `contactFire` / `coreItem` | 行为开关，全部由 `Spec` 的链式 setter 写 |

`register(Spec)` 里一次性做完【读源码】`MetalFamily.java:265-423`：

```
材料链      ingot / nugget / raw            （3 个 DeferredItem）
工具材料    new SimpleTier(...)             （由 Spec 现场构造，不写进任何全局 enum）
器具        sword / axe / pickaxe / shovel / hoe
盔甲材质    Holder.direct(new ArmorMaterial(...))
盔甲        helmet / chestplate / leggings / boots（逐件 durability）
建材        block / bricks / stairs / slab / wall / pillar / door / trapdoor / bars / chain / lantern
建材物品    11 个 registerSimpleBlockItem
升级模板    SmithingTemplateItem（5 段文案 + 2 组空位图标）
汇总        allItems / allBlocks 两个列表（供创造页分类、事件反查用）
```

**关键设计点**：

1. **`Tier` 不落地成全局枚举**，而是由 `Spec` 现场构造 ⇒ 新增金属不用去改 `AllTiers`。
2. **`ArmorMaterial` 用 `Holder.direct(...)`**（不注册进 `Registries.ARMOR_MATERIAL`）——代价是它不能被数据包按名字引用，
   收益是少一处注册 + 少一处接线。**要能被数据包引用就用 `DeferredRegister`**（本仓库 `CoeArmorMaterials` 就是这么做的，
   见 `01` §1）。
3. **`allItems` / `allBlocks` 两个 `List<DeferredItem<?>>` 是“这一个家族带了什么”的唯一真相**，
   家族索引、创造页分类、事件判定全部从它派生。

## 2. 家族索引：懒建 + 缓存（**不能在建的时候就 `.get()`**）

源仓库有 3 张反查表【读源码】`MetalFamily.java:93-126`：

```java
private static final Map<String, MetalFamily> BY_ID    = new LinkedHashMap<>();  // 保持注册顺序
private static final Map<Item,  MetalFamily> BY_ITEM   = new HashMap<>();
private static final Map<Block, MetalFamily> BY_BLOCK  = new HashMap<>();
```

`BY_ITEM` / `BY_BLOCK` **不在注册时填**，而是等所有 holder 都绑定之后再填
【读源码】`MetalFamily.java:240-263`：

```java
private static void ensureIndex() {
    if (indexBuilt) return;
    for (MetalFamily family : BY_ID.values())
        for (DeferredItem<?> holder : family.allItems)
            if (!holder.isBound()) return;      // 还没绑完 ⇒ 下次再来
    ...
    family.allItems.forEach(h -> BY_ITEM.put(h.get(), family));   // 到这一步才能 .get()
    indexBuilt = true;
}
```

**为什么必须这样**：`DeferredHolder.get()` 在注册完成前会抛异常
【读源码】`DeferredHolder.java:100-107`：

```java
public T value() {
    bind(true);
    if (this.holder == null)
        throw new NullPointerException("Trying to access unbound value: " + this.key);
    ...
}
```

⇒ **通用纪律：任何「注册名 → 注册项」的反查表都必须懒解析 + 缓存**，
不能在 `static` 初始化器里 `get()`。本仓库同类风险点是
`CoeArmorMaterials.register(...)` 里那些 `() -> Ingredient.of(CoeItems.X_INGOT.get())`
——它**写法正确**（lambda 只在 `repairIngredient().get()` 时求值，即铁砧修理时）。

## 3. ⚠️ 别名禁令：`public static final X ALIAS = Family.holder;` 会造成**类初始化循环**

这是源仓库最有价值的一条教训。

### 3.1 现象（【记录】源仓库原话 + 最小复现留档）

编译**完全通过**，`runServer` 在 mod 构造阶段（首次触碰注册表时）崩：

```
Exception in thread "main" java.lang.ExceptionInInitializerError
    at Family.<init>(CycleDemo.java:43)
    at AllMetals.<clinit>(CycleDemo.java:29)
    at AllBlocks.<clinit>(CycleDemo.java:24)
    at CycleDemo.main(CycleDemo.java:7)
Caused by: java.lang.NullPointerException: Cannot read field "ingot"
    because "AllMetals.STURDYGOLD" is null
    at AllItems.<clinit>(CycleDemo.java:18)
```

留档位置：`bettergold/build/scratch/CycleDemo.java`（约 50 行自包含复现，`java CycleDemo.java` 直接跑）
与 `build/scratch/cycle-demo.log`；结论也记在 `bettergold/docs/1.4-进度与交接.md` §三第 1 条。

### 3.2 根因

**JVM 不会重入一个正在初始化中的类**（JLS 12.4.2：同一线程正在初始化某类时，
再访问该类会直接读到「尚未赋值」的静态字段，而不是等待）。于是：

```
AllBlocks.<clinit>
  → 读别名 AllMetals.STURDYGOLD.ingot
    → 触发 AllMetals.<clinit>
      → 家族构造器注册物品/方块（要往 AllItems.ITEMS / AllBlocks.BLOCKS 里塞）
        → 触发 AllItems.<clinit>
          → AllItems 的字段初始化又要读 AllMetals.STURDYGOLD
            → 它还在初始化中 ⇒ 拿到 null
              → NullPointerException
```

### 3.3 正确做法：**不参与注册的懒绑定别名**

```java
/** 按注册名建一个物品别名（不注册，只懒绑定）—— 骨架/示例 */
public static <T extends Item> DeferredItem<T> item(String path) {
    return DeferredItem.createItem(ResourceLocation.fromNamespaceAndPath(MODID, path));
}
/** 按注册名建一个方块别名（不注册，只懒绑定）—— 骨架/示例 */
public static <T extends Block> DeferredBlock<T> block(String path) {
    return DeferredBlock.createBlock(ResourceLocation.fromNamespaceAndPath(MODID, path));
}
```

**为什么这样就没有循环**（本机对 NeoForge 21.1.228 逐条核对过）：

- `DeferredItem.createItem(ResourceLocation)`【读源码】`DeferredItem.java:46-48` → 只 `new DeferredItem<>(...)`，
  **不查注册表、不触发注册**；`DeferredBlock.createBlock` 同理【读源码】`DeferredBlock.java:47-48`。
- `DeferredHolder` 造出来是**未绑定**的；第一次 `get()/value()` 才 `bind(...)`
  【读源码】`DeferredHolder.java:148`，用 `registry.getHolder(this.key)` **现查**。
  所以它解析到的就是家族注册的**同一个**注册项：**不会二次注册，也永远不会在类初始化阶段去读注册项**。
- 源仓库实测：35/35 个别名解析到与家族 holder **同一个** `Item`/`Block` 实例
  【记录】`bettergold/docs/1.4-进度与交接.md` §二第 1 条②。

### 3.4 比这个坑更值钱的那条通用纪律

> **类初始化期间只能“构造对象”，不能“读取注册项”。**

这条纪律一次能解释两种崩溃：
① 别名直接赋值（`= Family.holder`）→ 读到 `null`；
② 注册名反查表建表时 `.get()` → `Trying to access unbound value`。
两种都是**编译期零症状**，且都只在“某个别人先触碰了某条初始化链”时才出现 —— 这也是为什么它难查。

## 4. 本仓库（COE）现状对照：**不要为了统一而重构**

本仓库没有家族抽象：

- 工具材料是一个 `enum AllTiers implements Tier`【读源码】`coe/.../common/registry/coe/AllTiers.java:19-32`；
- 器具/盔甲逐件在 `CoeItems.java` / `CoeArmorItems.java` 里手写注册
  （`CoeItems.java:135-236` 是翡翠那 5 件，另外 4 套各一段，共 25 件器具）。

**这套写法在本仓库是安全的，不需要改成家族抽象。** 依据：

- `AllTiers` 的枚举常量里，`repairIngredient` 是 **`Supplier<Ingredient>`**
  【读源码】`AllTiers.java:24-32 / 39 / 54-62`，lambda 体里的 `CoeItems.JADE_INGOT.get()`
  **只在 `Tier.getRepairIngredient()` 被调用时求值**（即 `TieredItem.isValidRepairItem` → 铁砧修理时）。
- `AllTiers.<clinit>` 本身**不读 `CoeItems` 的静态字段**，所以
  「`CoeItems.<clinit>` 读 `AllTiers.JADE`」只是一条普通的单向初始化链，**没有环**。
  【推断】这是标准类初始化语义的直接推论，不是本机实测。

⇒ 结论：**本仓库现有写法是“合法别名”的反面教材对照**——
它做对了（延迟求值），只是没有把「一种材料的全套内容」聚到一处。

### 要不要引入家族抽象？判据

| 情况 | 建议 |
|---|---|
| 只再加 1~2 种材料、内容量不变 | **不引入**。重构面大于收益，且要重跑全部验证 |
| 要加 ≥3 种材料，且每种都要“材料链 + 建材 + 器具 + 盔甲 + 模板” | 值得引入。此时“照着手工改名”出错概率已经高于重构风险 |
| 只是想让 `AllTiers` 不再手写 | 不值得。`AllTiers` 不是痛点 |

如果确实要引入，**验收口径必须是「零行为变化」**（源仓库迁移时的口径可以直接照抄）：

- 物品/方块注册条目数前后一致；
- 该材料的 id 列表（排序后）**逐字相同**；
- 器具最终伤害/攻速逐件相同；
- 盔甲耐久/护甲/附魔/韧性/抗击退逐件相同；
- 标签逐项相同（含**负例**：例如「锭不在 `#swords` 里」应为 false）；
- 创造页物品清单逐行相同；
- 别名解析到与家族 holder **同一个实例**（`==` 比较，逐件打表）。

## 5. 一页检查清单

- [ ] 新增材料的“唯一真相”在哪一处？说得出文件名与字段名。
- [ ] 有没有任何 `static` 初始化器里出现 `.get()` / `.value()`？（有 ⇒ 改懒解析）
- [ ] 有没有 `public static final X ALIAS = Family.holder;` 这种**直接赋值别名**？（有 ⇒ 改 `DeferredItem.createItem(...)`）
- [ ] 反查表（注册名→家族/物品）是在“所有 holder 都已绑定”之后才填的吗？
- [ ] `Tier` / `ArmorMaterial` 的修复材料是不是用了 `Supplier` 延迟求值？
- [ ] 新加的材料有没有进**类别标签**（`#minecraft:swords` 等）与**家族标签**（`c:ingots` 等）？
- [ ] 改完有没有跑 `04` 里那张“零行为变化”表？
