# 04 - 验证方法论（重点）

> 这一篇是整份文档里**最该逐条照做**的一篇。来源是源仓库 `bettergold` 的探针实践
> 【记录】`bettergold/docs/创造页分区栏目-参考实现/04-验证清单.md` 与
> `bettergold/docs/构建与跑测注意事项.md`，以及我在本仓库核对出的对应风险点。
>
> 它不是"测试建议"，是"**不这么做就会得出错误结论**"的清单。

---

## 0. 三条总原则（先读）

1. **只读 JSON / 只读源码不算验证。**（§6 有事故原文）
2. **探针必须整块删除**，并给出 grep 零命中的证据。**任何能关掉别人服务器/客户端的能力
   （`server.halt` / `stopServer` / `System.exit`）绝不允许留在生产代码里。**
3. **`run\` 目录是独占资源**：同一时刻只跑一个游戏进程；跑前清 `session.lock`；
   关服**只调一次 `halt(false)`**。

## 1. 探针模板

### 1.1 挂点与形状（骨架/示例）

```java
// 临时探针：整块删除，不要提交。挂在服务端启动之后，此时一切注册与数据加载都已完成。
@EventBusSubscriber(modid = CoeCore.MOD_ID)          // 注意：COE 的 modid 与所在 jar 必须一致
public final class TempProbe {
    private static boolean done;

    @SubscribeEvent
    public static void onServerStarted(ServerStartedEvent event) {
        if (done) return;                            // 只跑一次
        done = true;
        MinecraftServer server = event.getServer();
        // >>> 打印区（见 §2 的"必须量化的量"）
        CoeCore.LOGGER.info("[PROBE] items={}", BuiltInRegistries.ITEM.size());
        // <<<
    }
}
```

**为什么挂 `ServerStartedEvent`**：
- 它在 `RegisterEvent`、数据包加载（标签/配方/语言）之后 ⇒ 你读到的是**游戏真正加载出来的状态**，
  而不是你自己期望的状态；
- 服务端能覆盖「注册表 / 标签 / 配方 / 属性 / 战利品表」；

**为什么必须先 `if (done) return`**：`ServerStartedEvent` 在单人存档里会随开图重复触发。

### 1.2 需要关服时：只调一次 `halt(false)` + 开关文件

【读源码】`MinecraftServer.java`（源仓库核对过同一份语义）：

```java
public void halt(boolean waitForServer) { this.running = false; ... }   // 只把 running 置 false
// 真正的 "Stopping server → 存档 → 卸载 config" 在 runServer() 的 finally 里（会调 stopServer()）
// close() 也会再调一次 stopServer()
```

⇒ **先 `stopServer()` 再 `halt(false)` 会走两遍关闭流程**，日志看起来像卡死。
**只调用一次 `halt(false)`**，其余交给原版。

用开关文件保护（避免误关别人的服务器）：

```java
// 骨架/示例：只有开关文件存在才动作，收尾时开关文件一起删
Path flag = server.getServerDirectory().resolve("probe-halt.enabled");
if (Files.exists(flag)) { CoeCore.LOGGER.info("[PROBE] halt"); server.halt(false); }
```

### 1.3 中文输出会乱码

探针控制台输出中文在 Windows 下按 GBK 写出，重定向后按 UTF-8 读会乱码。
**探针把中文转成 `\uXXXX` 打印**，读日志时再还原：

```powershell
(Get-Content build\probe-server.log -Raw -Encoding UTF8) `
  -replace '\\u([0-9a-fA-F]{4})', { [char][Convert]::ToInt32($_.Groups[1].Value, 16) }
```

### 1.4 跑法与日志判读（照抄本仓库的既有习惯）

本仓库 `AGENTS.md` 已经记过两条，直接沿用：

```powershell
# 清残留（只杀游戏进程，不要一把梭杀所有 java —— 会杀到 Gradle daemon，写坏配置缓存）
Get-Process java -ErrorAction SilentlyContinue |
    Where-Object { $_.CommandLine -match 'forgeclientdev|forgeserverdev' } | Stop-Process -Force
Remove-Item -Force run\world\session.lock, run\saves\*\session.lock -ErrorAction SilentlyContinue

# 跑服务端探针（stderr 单独放，避免 PowerShell 把 javac 的「注:」记成 NativeCommandError 而假报 exit 1）
.\gradlew.bat runServer --console=plain 2>build\probe-server.err >build\probe-server.log
Select-String build\probe-server.log -Pattern 'PROBE|BUILD SUCCESSFUL|BUILD FAILED'
```

**判断成败只看** Gradle 的 `BUILD SUCCESSFUL` / `BUILD FAILED`（或 `$LASTEXITCODE`），
**不要看 pwsh 的红字**。同理 `git push` 的进度信息也走 stderr。

## 2. 必须量化的量（**"打出来"而不是"看一眼"**）

下面每一行都要变成探针里的一行日志。**"我读了源码，逻辑是对的"只能证明逻辑对，
不能证明这段逻辑跑起来了。**

### 2.1 注册规模（改注册后必打）

| 打印项 | 期望 | 为什么 |
|---|---|---|
| `BuiltInRegistries.ITEM.size()` / `BLOCK.size()` | 与改动前**同数**或按预期 +N | 搬注册、改初始化顺序后"少注册了"不报错 |
| 本模组物品 id 全表（排序后） | 与改动前**逐字相同** | 一次 `LIST` 差异就能看出谁丢了/重命名了 |
| 本模组方块 id 全表（排序后） | 同上 | |
| 本模组 `ARMOR_MATERIAL` 全表 | 4 条（COE） | 盔甲材质是**静态注册表**，不注册物品照样能用 `Holder.direct`，容易漏 |
| 创造页每页 `getDisplayItems().size()` 与其中非空项数 | 非空 == 候选数 | 见 §3 |

```java
// 骨架/示例：打全表（排序后可直接 diff）
BuiltInRegistries.ITEM.keySet().stream()
    .filter(rl -> rl.getNamespace().equals(CoeCore.REGISTRY_NAMESPACE))
    .map(ResourceLocation::toString).sorted()
    .forEach(s -> CoeCore.LOGGER.info("[PROBE] item {}", s));
```

### 2.2 工具 Tier：6 个方法逐个打

```java
// 骨架/示例
for (AllTiers t : AllTiers.values()) {
    CoeCore.LOGGER.info("[PROBE] tier {} uses={} speed={} dmgBonus={} ench={} incorrect={} repair={}",
        t.name(), t.getUses(), t.getSpeed(), t.getAttackDamageBonus(), t.getEnchantmentValue(),
        t.getIncorrectBlocksForDrops().location(),
        t.getRepairIngredient().getItems()[0].getItem());
}
```

**注意**：`AllTiers.java:43` 的注释说耐久是"基数 + 修正"，而实际 `TieredItem.java:7` 是
`properties.durability(tier.getUses())` ⇒ **打出来的 `uses` 就是最终耐久**。
这正是"必须打出来"的价值：注释与实现不一致时，日志能定案。

### 2.3 器具最终伤害/攻速：**读实体属性最终值，不要自己套公式**

```java
// 骨架/示例：把物品装到手上，读玩家实体属性（这才是游戏真正用的值）
ItemStack tool = new ItemStack(CoeItems.JADE_SWORD.get());
attributeModifiers(tool).forEach(e ->
    CoeCore.LOGGER.info("[PROBE] {} {} mod={} op={} slot={}",
        idOf(tool), e.attribute().getRegisteredName(), e.modifier().amount(),
        e.modifier().operation(), e.slot()));
// 最终值 = 基础值 + 所有修饰符；玩家基础值：ATTACK_DAMAGE=1.0, ATTACK_SPEED=4.0（见 01 §7.2）
```

**为什么不能自己套公式验自己**：公式是你写的，要么从 `createAttributes` 的参数重算（那就只是验证乘法），
要么**真的生成一个玩家/生物、把物品放到主手、读 `getAttributeValue(...)`**——后者才是实测。
源仓库就是读最终值打出「10/1.8、12/1.2、8/1.4、8.5/1.2、7/4.2」这一组的
【记录】`bettergold/docs/1.4-进度与交接.md` §一。

### 2.4 盔甲：护甲 / 耐久 / 附魔 / 韧性 / 抗击退**逐件**打

```java
// 骨架/示例：逐件读物品自带的 Final 属性 + material holder 的字段
for (ItemEntry<CoeArmorItem> e : List.of(CoeArmorItems.JADE_HELMET, /* ...16 件 */)) {
    CoeArmorItem item = e.get();
    var mat = item.getMaterial().value();
    CoeCore.LOGGER.info("[PROBE] armor {} type={} defense={} durability={} ench={} tough={} kb={}",
        idOf(item), item.getType(), item.getDefense(), item.getMaxDamage(),
        item.getEnchantmentValue(), item.getToughness(), mat.knockbackResistance());
}
```

要点：
- `getDefense()` 走 `material.getDefense(type)`，**漏填的槽位会打 0**（`getOrDefault(type, 0)`）——
  这就是"数组顺序写错"的唯一可观测症状；
- `getMaxDamage()` 读的是物品属性上的耐久，**不要**用"基准 × 倍率"重算（那就又变成验自己了）；
- 源仓库的做法是**再叠一层**：`javap -p -c` 数字节码里的 `sipush` 常量，与探针数字互证
  【记录】`bettergold/build/patch/armor-assets-NOTES.md` §4。

### 2.5 自定义效果：等级与时长

```java
// 骨架/示例：给一个真实生物施加效果，再读实例
zombie.addEffect(new MobEffectInstance(TransmutationEffects.TRANSMUTATION_DISORDER, 200, 2));
MobEffectInstance got = zombie.getEffect(TransmutationEffects.TRANSMUTATION_DISORDER);
CoeCore.LOGGER.info("[PROBE] effect amp={} dur={} ambient={} visible={}",
    got.getAmplifier(), got.getDuration(), got.isAmbient(), got.isVisible());
```

**一定要打的两组**：
① **施加后立刻**读一次（验证等级/时长真的按你写进去了——`amplifier` 是 0 基，你写 3 级应该是 2）；
② **过期后**再读一次 + 在 `MobEffectEvent.Expired` 里打一行（验证"结束结算"真的触发，
见 `03` §4.1：`applyEffectTick` 返回 false 时**不会**触发 Expired）。

### 2.6 掉率：**掷表次数 + 命中率**，不是"读了 chance"

源仓库的事故就是「读了掉落表 JSON 里 `chance=0.36` 就宣称修好，实际那份表**根本没被加载**」
【记录】`bettergold/docs/构建与跑测注意事项.md` §六。

正确做法（骨架/示例）：让游戏**真的掷 N 次**，统计命中率并与期望值比：

```java
// 骨架/示例：用方块自己的掉落逻辑掷 N 次（而不是读 JSON 里的数字）
int hits = 0, N = 1000;
for (int i = 0; i < N; i++) {
    List<ItemStack> drops = Block.getDrops(state, level, pos, be, player, tool);
    if (drops.stream().anyMatch(s -> s.is(targetItem))) hits++;
}
CoeCore.LOGGER.info("[PROBE] drop target={} hits={}/{} rate={}", targetItem, hits, N, hits / (double) N);
```

**判据（粗但可用）**：`N = 1000` 时，真实概率 0.36 的 95% 区间约为 **0.33 ~ 0.39**（±3%）。
打出来落在区间外，或 `hits == 0 / hits == N`（说明表里压根没这条或条件永真），都判失败。
**必须打印 `N`**——只报"掉了"不报次数是没有意义的。

### 2.7 标签：**逐项**打 true/false，并且**必须有负例**

```java
// 骨架/示例：正例 + 负例一起打
record Case(TagKey<Item> tag, Item item, boolean expect) {}
for (Case c : cases) {
    boolean actual = new ItemStack(c.item()).is(c.tag());
    CoeCore.LOGGER.info("[PROBE] tag {} contains {} -> {} (expect {})",
        c.tag().location(), idOf(c.item()), actual, c.expect());
}
```

负例示例：`jade_ingot in #minecraft:swords` 应为 **false**；`jade_sword in #minecraft:swords` 应为 **true**。
只打正例的话，"标签压根没加载 ⇒ 一切 is() 都为 false"和"标签正确"在某些场景下分不开；
而**只打真**的探针会让"标签空文件"看起来像通过。

## 3. 交叉校验：两个数必须自洽

### 3.1 创造页：`slot(0,0) == items[首个可见行 × 9]`

这是源仓库认为"最有价值的一条"【记录】`.../04-验证清单.md` §3.2，它一次性验证
「卷动公式」+「items → 槽位映射」两件事：

```java
int firstVisibleRow = firstVisibleRow(menu, scrollOffs);
ItemStack slot00 = menu.getSlot(0).getItem();
ItemStack expect = menu.items.get(firstVisibleRow * 9);
CoeCore.LOGGER.info("[PROBE] cross-check row={} slot(0,0)={} items[{}]={} match={}",
    firstVisibleRow, idOf(slot00), firstVisibleRow * 9, idOf(expect), ItemStack.matches(slot00, expect));
```

判等要用「物品相同 **或** 两者都空」，不要用 `==`（空行两侧都是 `EMPTY` 也算一致）。

### 3.2 "三方相等"：候选数 == 非空数 == 分桶数之和

源仓库用来证明"一件物品都没丢、也没重复"【记录】同上 §1.3：

```java
int nonempty   = (int) tab.getDisplayItems().stream().filter(s -> !s.isEmpty()).count();
int candidates = candidatesSupplier.get().size();
int bucketSum  = buckets.stream().mapToInt(b -> b.items().size()).sum();
// 断言 nonempty == candidates == bucketSum
```

本仓库的对应风险点是 `CoeCreativeTabs.java` 与各层 `LayerCreativeTab` 的
「先 `remove` 再 `accept`」纪律（`AGENTS.md` 记过：只 `accept` 会抛
`already exists in the tab's list`，dev/发布同崩）。**改创造页必打这三个数。**

### 3.3 数量对，内容不一定对：**存在性 ≠ 正确性**

这是本轮在**本仓库**发现的真实反例（详见 `06` 第 1 条）：翠玉的两张装备层贴图互换了，
但
- `runData` 只校验"贴图文件存在" ⇒ 通过；
- `check-asset-attribution` 只校验"引用的资源解析得到" ⇒ 通过；
- 背包里 16 张图标全部正确 ⇒ 人眼看不出来；
- **症状只在"穿上头盔"的那一瞬间出现**。

⇒ **可自动化的那部分必须自动化**：装备层贴图用「逐区域不透明像素数」断言
（`01` §3.2 给了现成命令）：

| 断言 | 期望 |
|---|---|
| 尺寸 | `_layer_1` 与 `_layer_2` 都是 64×32 |
| `_layer_1` 的 head 区（0,0~32,16）不透明像素数 | **> 0** |
| `_layer_1` 的 arm 区（40,16~56,32）不透明像素数 | **> 0** |
| `_layer_2` 的 head 区不透明像素数 | **== 0** |
| `_layer_2` 的 arm 区不透明像素数 | **== 0** |
| 全套 `_layer_*.png` 的 SHA256 | 两两不同（防"复制一份改名"） |

**剩下靠人眼的**（做不到自动化，必须真的看）：
配色是否和物品图标一致、两层贴图叠加有没有穿模、不同 `guiScale` 下是否发虚、
头盔在幼年/成年模型上的位置、跑动时的观感。

## 4. `runServer` 与 `runClient` 各自确认什么

| 关卡 | **能**确认 | **不能**确认（必须进客户端） |
|---|---|---|
| `compileJava` | 语法、类型、缺失符号 | 一切运行期行为 |
| `runData` | 数据生成物完整、资源引用可解析、Registrate 校验贴图**存在** | 贴图**内容**、渲染、实体 tick、配置项、JEI 装配 |
| `runServer` | 注册表条目 / 标签 / 配方 / 属性最终值 / 效果结算 / 掉落掷表 / 生物转化 / 存档兼容 | **渲染**（盔甲外观、纹饰颜色、紫黑格）、创造页**客户端**渲染、第二页 UI |
| `runClient` | 渲染路径执行、贴图解析、GUI 坐标、创造页卷动、客户端事件 | 服务端权威行为（多数效果结算、掉落） |

本仓库 `AGENTS.md`「5）静态关卡覆盖不到什么」列的那一页（实体/tick、客户端渲染、JEI、配置、
创造页内容同步、包重叠、可选依赖）与这张表一致，**那几类改完必须明确告诉用户"只能进游戏实测"**。

**配置的一条**：`runData` **根本不加载配置**。配置键名/容器名写错要到进游戏才暴露；
**容器名一变（例如 `coe_core-common.toml`）= 老玩家设置静默丢失**（本仓库红线）。

## 5. 交叉校验的两条通用思路

1. **两个独立来源算同一个量。** 例：盔甲耐久 = ① 探针 `getMaxDamage()`；② `javap` 数字节码常量。
   两者不一致 ⇒ 一定有一处没按你想的执行。
2. **三方计数相等。** 例：创造页「候选数 / 显式列表非空数 / 分桶数之和」；
   注册规模「本模组 id 表长度 / 探针计数 / `jar` 内资源数」。
   **任何一个数据流断裂，三方就不等**——这比"看看有没有报错"灵敏得多。

## 6. 铁律：**只读 JSON 或只读源码不算验证**

**源仓库的事故原文**【记录】`bettergold/docs/构建与跑测注意事项.md` §六：

> **只读 JSON 不算验证**：我们有过一次"读了掉落表 JSON 里 chance=0.36 就宣称修好"的事故，
> 实际那份表**根本没有被加载**（解析失败），玩家打半天不掉东西。任何数据文件都必须
> **让游戏真的加载它**，并留下日志证据。

对应到本文档：**§2.6 的"掷表次数与命中率"就是为了让这条不再发生。**
同理：

- 「模型引用了解析得到的贴图」≠「贴图内容对」（§3.3 的翠玉反例）；
- 「`ArmorMaterial` 里有这个属性」≠「玩家身上生效」（要读实体属性最终值）；
- 「`addAttributeModifier` 写在代码里」≠「进游戏真的加了那点伤害」（见 `03` §1，
  源仓库在这里白丢过一轮）。

### 汇报纪律

把「**实机验证过的数字**」与「**仅编译 / 仅读源码 / 推断**」**分开写**。
本目录每一条结论都带依据等级标注，就是这个原因。**不要把推断写成结论。**

## 7. 一页纸收尾清单（可以直接抄进会话末尾）

- [ ] `compileJava` 输出 `BUILD SUCCESSFUL`（**不要**看 pwsh 红字）
- [ ] 改动语言/资源后跑过 `runData`，且 `written: 0` **不作为**健康判据（本仓库 `AGENTS.md` 有记录）
- [ ] 注册规模三处一致：本模组 id 表长度 / 探针计数 / `jar` 内资源数
- [ ] 器具：逐件打出**最终**伤害与攻速（读实体属性，不是重算公式）
- [ ] 盔甲：逐件打出 defense / maxDamage / enchantmentValue / toughness / knockbackResistance
- [ ] 盔甲贴图：逐区域不透明像素数断言通过（`_layer_1` 有头有臂；`_layer_2` 头臂为 0）
- [ ] 标签：正例 + **负例**都打，且逐项为 true/false 符合预期
- [ ] 效果：施加后读 amp/dur；过期后确认 `Expired` 真的触发
- [ ] 掉率/掉落改写：打过**掷表次数 N** 与命中率，且 N ≥ 1000
- [ ] `runClient`：真的进游戏看过渲染（截图或坐标日志）
- [ ] 创造页：`slot(0,0) == items[首可见行 × 9]`，且"三方相等"
- [ ] 探针代码与开关文件**已整块删除**，`grep` 零命中
      （特别确认没有 `halt(` / `stopServer(` / `System.exit(`）
- [ ] `run\` 下没有残留的探针开关文件
- [ ] 结论汇报里区分「实测 / 编译 / 推断」
