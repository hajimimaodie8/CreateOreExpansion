## 1. `ArmorMaterial`：字段、顺序、以及最容易写错的三处

**它是记录类，7 个字段，顺序固定**【读源码】`ArmorMaterial.java:13-21`：

```java
public record ArmorMaterial(
    Map<ArmorItem.Type, Integer> defense,   // 槽位 → 护甲值
    int enchantmentValue,                   // 附魔能力（只影响附魔台等级池与经验消耗）
    Holder<SoundEvent> equipSound,          // 穿戴音效（注意是 Holder，不是 SoundEvent）
    Supplier<Ingredient> repairIngredient,  // ★ Supplier！不是 Ingredient
    List<ArmorMaterial.Layer> layers,       // 贴图层
    float toughness,                        // 韧性
    float knockbackResistance               // 抗击退（0.0~1.0 的比例值，不是百分比）
) {}
```

**三个坑：**

1. **第 4 个参数是 `Supplier<Ingredient>`**。传 `Ingredient.of(...)` 会编译失败；必须传 `() -> Ingredient.of(...)`。
   这正好给了你一个方便：lambda 里晚一点 `.get()`，就不会在类初始化阶段去读注册项
   （见 `02` 的「注册期不能 `.get()`」）。本仓库 `CoeArmorMaterials.java:72` 用的是
   `() -> Ingredient.of(CoeItems.JADE_INGOT.get())`，**写法正确**。
2. **`defense` 是一个 Map，不是数组。** 取值走 `getDefense(type)`，实现是 `getOrDefault(type, 0)`
   【读源码】`ArmorMaterial.java:24-26`。所以**漏填一个槽位不会报错，只会得到 0 护甲**。
   `ArmorItem.Type` 有 **5 个值**，含 `BODY`（狼铠/马铠用）
   【读源码】`ArmorItem.java:149-154`：
   `HELMET(HEAD,11) / CHESTPLATE(CHEST,16) / LEGGINGS(LEGS,15) / BOOTS(FEET,13) / BODY(BODY,16)`。
3. **用 `type.ordinal()` 给数组索引是可以的，但必须加守卫。** 本仓库
   `CoeArmorMaterials.java:140-145` 的做法是：
   `for (type : ArmorItem.Type.values()) if (type.ordinal() < defense.length) defenseMap.put(...)`。
   因为 `values()` 有 5 个而数组只有 4 个，`BODY` 被守卫跳过 → `getDefense(BODY) == 0`（本模组不用 BODY，无害）。
   **风险点**：数组顺序依赖枚举声明序（HELMET/CHESTPLATE/LEGGINGS/BOOTS），写成别的顺序**不会有任何报错**，
   只会静默地把护甲值配错槽位。验证办法见 `04`（逐件读 `getDefense()` 打表）。

### 贴图路径规则（Layer）

`ArmorMaterial.Layer` 只带一个「名字」和一个后缀：
【读源码】`ArmorMaterial.java:35-50`

```java
public Layer(ResourceLocation assetName, String suffix, boolean dyeable) { ... }
public Layer(ResourceLocation assetName) { this(assetName, "", false); }   // 常用构造

private ResourceLocation resolveTexture(boolean innerTexture) {
    return this.assetName.withPath(p ->
        "textures/models/armor/" + this.assetName.getPath() + "_layer_" + (innerTexture ? 2 : 1) + this.suffix + ".png");
}
```

⇒ **`new Layer(rl)` 的 `rl` 命名空间就是贴图的命名空间**，路径规则是
`assets/<rl.namespace>/textures/models/armor/<rl.path>_layer_1.png`（外层模型）
与 `..._layer_2.png`（**内层模型，只给护腿**）。

### 贴图到底从哪来：两条等效路线（别同时以为只有一条）

1.21.1 的渲染链是：

```
HumanoidArmorLayer.renderArmorPiece :90
  → ClientHooks.getArmorTexture(entity, stack, layer, innerModel, slot)   // ClientHooks.java:260-263
      → armor.getItem().getArmorTexture(stack, entity, slot, layer, innerModel)   // IItemExtension.java:332-334，默认返回 null
      → null 时回退 layer.texture(innerModel)                                     // = Layer.resolveTexture
```

所以有**两条等效**的做法：

| 路线 | 做法 | 代价 |
|---|---|---|
| A. 靠 Layer 名字 | `new ArmorMaterial.Layer(ResourceLocation.fromNamespaceAndPath(ns, "<name>_armor"))`，一行代码 | 路径完全由约定决定，不能自定义目录 |
| B. 覆写 `getArmorTexture` | 物品类覆写 `IItemExtension#getArmorTexture`（`Item` 已实现该接口） | 多一个类；但可以拼任意路径 |

**注意**：这里的 `getArmorTexture` 是 **NeoForge 扩展接口 `IItemExtension` 的方法**，
`net.minecraft.world.item.ArmorItem` 在 1.21.1 里**根本没有这个方法**（我通读过 `ArmorItem.java`，
它只有 `getDefaultAttributeModifiers/getDefense/getToughness/getEquipSound/...`）。
之所以 `@Override` 能编译，是因为 `Item implements IItemExtension`
【读源码】`Item.java:59`。**如果哪天换成非 NeoForge 环境，这个覆写会直接编不过。**

本仓库两条都做了：`CoeArmorItem.java:52-59` 覆写了 `getArmorTexture`，而 `CoeArmorMaterials.java:146`
传入的 Layer 名字恰好也是同一个路径（`createoreexpansion:<set>_armor`）。
⇒ **覆写是冗余的（行为与默认完全一致）**，见 `06` 的第 5 条。

## 2. 盔甲耐久：写在 `Item.Properties().durability(n)` 上

1.21.1 的 `ArmorMaterial` **没有耐久字段**。原版的做法就是：
`new ArmorItem(material, type, new Item.Properties().durability(ArmorItem.Type.XXX.getDurability(基准)))`
【读源码】`Items.java:1090-1092`（钻石头盔 = `getDurability(33)`）、`Items.java:1137-1139`
（下界合金靴子 = `getDurability(37)`）。

`getDurability(int factor)` 就是**乘法**，槽位倍率写死在枚举里
【读源码】`ArmorItem.java:149-169`：

| 部位 | 倍率 |
|---|---|
| 头盔 | ×11 |
| 胸甲 | ×16 |
| 护腿 | ×15 |
| 靴子 | ×13 |
| `BODY`（狼/马铠） | ×16 |

常用基准（原版）：钻石 **33**、下界合金 **37**。于是：

| 材质 | 基准 | 头盔 | 胸甲 | 护腿 | 靴子 |
|---|---|---|---|---|---|
| 钻石（原版） | 33 | 363 | 528 | 495 | 429 |
| 下界合金（原版） | 37 | 407 | 592 | 555 | 481 |

**本仓库现状（已核对，正确）**：`CoeArmorItems.java:138-169` 的 `Durability` 内部类逐件写死
= `基准 × 倍率`，四个基准 36 / 47 / 74 / 74 与注释表一致；`armor()` 里用
`.properties(p -> p.durability(durability))`（`CoeArmorItems.java:190`）落到物品属性上。
⇒ 翠玉 396/576/540/468、宝石 517/752/705/611、星界与雷鸣 814/1184/1110/962。
**验证方式**：编译后用 `javap -p -c` 数 `sipush` 常量（源仓库就是这么验的，见
`bettergold/build/patch/armor-assets-NOTES.md` §4），比读代码硬。

> ⚠️ 另一个易错点：`TieredItem`（工具）**不一样**——工具耐久直接取 `tier.getUses()`，
> 没有「基数 × 倍率」这一步【读源码】`TieredItem.java:7`。见本文 §6。

## 3. 盔甲贴图：64×32 画布 + **逐区域**核对（不是"文件存在就算对"）

### 3.1 画布与 UV 分区

两张装备层贴图都是 **64×32**（本仓库 8 张全部实测为 64×32，正确）。模型读取的区域写死在
`HumanoidModel` 的 `texOffs` 里【读源码】`HumanoidModel.java:82 / 92 / 97 / 102 / 107 / 112`：

| 身体部位 | `texOffs` | UV 区域（x0,y0 ~ x1,y1） | 出现在哪一张 |
|---|---|---|---|
| 头 `head` | `(0, 0)` | 0,0 ~ 32,16 | **layer_1** |
| 躯干 `body` | `(16, 16)` | 16,16 ~ 40,32 | layer_1 **和** layer_2 |
| 手臂 `right/left_arm` | `(40, 16)`（左臂 `mirror()`） | 40,16 ~ 56,32 | **layer_1** |
| 腿 `right/left_leg` | `(0, 16)`（左腿 `mirror()`） | 0,16 ~ 16,32 | layer_1 **和** layer_2 |

配合 `HumanoidArmorLayer.usesInnerModel(slot) == (slot == LEGS)`
【读源码】`HumanoidArmorLayer.java:80 / 163-165`，得到结论：

- **`_layer_1.png` 供头盔 / 胸甲 / 靴子用** ⇒ 它必须有**头**区和**手臂**区；
- **`_layer_2.png` 只供护腿用** ⇒ **它不应该有头部像素、也不应该有手臂像素**。

## 4. 附魔能不能生效，取决于**标签**，不是「附魔值不够」

这是最容易被误诊的一条。1.21 把附魔的适用范围改成了数据驱动的 `supported_items`，
它引用的是 **`#minecraft:enchantable/*` 系列标签**，而这些标签**由物品类别标签拼出来**
【资源实测】原版 `data/minecraft/tags/item/enchantable/armor.json` 全文：

```json
{ "values": [
  "#minecraft:enchantable/foot_armor",
  "#minecraft:enchantable/leg_armor",
  "#minecraft:enchantable/chest_armor",
  "#minecraft:enchantable/head_armor" ] }
```

而 `enchantable/head_armor.json` 里只有一条：`"#minecraft:head_armor"`（其余三个槽位同理）。
所以链条是：

```
#minecraft:head_armor / chest_armor / leg_armor / foot_armor      ← 你的盔甲必须在这里
   ↑
#minecraft:enchantable/<slot>_armor  →  #minecraft:enchantable/armor
   ↑
附魔的 supported_items（例：protection.json → "#minecraft:enchantable/armor"）
```

**【资源实测】原版附魔的 `supported_items`**：

| 附魔 | supported_items |
|---|---|
| `minecraft:protection` | `#minecraft:enchantable/armor` |
| `minecraft:respiration` | `#minecraft:enchantable/head_armor` |
| `minecraft:sharpness` | `#minecraft:enchantable/sharp_weapon` |
| `minecraft:efficiency` | `#minecraft:enchantable/mining` |

工具同理，必须进**类别标签**：

| 标签 | 内容【资源实测】 |
|---|---|
| `#minecraft:enchantable/mining` | `#minecraft:axes` + `#minecraft:pickaxes` + `#minecraft:shovels` + `#minecraft:hoes` + `minecraft:shears` |
| `#minecraft:enchantable/sword` | `#minecraft:swords` |
| `#minecraft:enchantable/sharp_weapon` | `#minecraft:swords` + `#minecraft:axes` |

⇒ **结论**：`Tier.getEnchantmentValue()` / `ArmorMaterial.enchantmentValue()` 只决定
「附魔台给的候选等级池与经验消耗」；**决定"能不能附"的是上面这些标签**。
一件附魔值 24 的镐如果不在 `#minecraft:pickaxes` 里，附魔台照样一个效率都不给，
而且**不报错、不警告**。

**本仓库现状（已核对，正确）**：工具在注册时挂了类别标签
（`CoeItems.java:143 / 164 / 184 / 205 / 225` 分别 `.tag(ItemTags.SWORDS/PICKAXES/AXES/SHOVELS/HOES)`），
盔甲在 `CoeArmorItems.java:191` 挂 `armorTag(type)`（`CoeArmorItems.java:198-206` →
`HEAD/CHEST/LEG/FOOT_ARMOR`），四个生成标签里各 4 件【资源实测】。
⇒ 24 件装备的附魔路径全部通畅。

> 顺带：`CoeArmorItems.java:192` 还额外挂了 `ItemTags.TRIMMABLE_ARMOR`。**这是多余的**——
> 原版 `#trimmable_armor` 的内容就是那四个槽位标签【资源实测】。多挂无害，但别以为它是必需的。

## 5. 盔甲纹饰：**四样齐全**才显示（缺哪一样，症状不一样）

### 5.1 机制全链（每一步都要成立）

```
① 锻造台合成
   SmithingTrimRecipe.matches           :34-36   template ✓ && base ✓ && addition ✓
   例子 data/minecraft/recipe/coast_armor_trim_smithing_template_smithing_trim.json
        { "type":"minecraft:smithing_trim",
          "template": {"item":"minecraft:coast_armor_trim_smithing_template"},
          "base":     {"tag":"minecraft:trimmable_armor"},
          "addition": {"tag":"minecraft:trim_materials"} }      ← 18 条原版纹饰配方逐条如此
② 组装时把「材料物品」翻译成「纹饰材质」
   SmithingTrimRecipe.assemble          :38-46
     TrimMaterials.getFromIngredient(registries, input.addition())   ← TrimMaterials.java:45-47
       扫 TRIM_MATERIAL 注册表，找 ingredient 匹配的那一条
     找不到 ⇒ 返回 Optional.empty ⇒ assemble 返回 ItemStack.EMPTY（没产物）
③ 写入 DataComponents.TRIM（ArmorTrim = TrimMaterial + TrimPattern）
④ 渲染时算 sprite 名
   ArmorTrim:66-86  getColorPaletteSuffix(material, armorMaterial)
       = overrideArmorMaterials.get(armorMaterial) ?? trimMaterial.assetName()
     innerTexture(armorMaterial) = <pattern.assetId 的命名空间>:trims/models/armor/<pattern path>_leggings_<suffix>
     outerTexture(armorMaterial) = ...:/trims/models/armor/<pattern path>_<suffix>
⑤ 从 armor_trims 图集取 sprite
   HumanoidArmorLayer.renderTrim        :146-148  armorTrimAtlas.getSprite(...)
   ⇒ 图集里必须有这个 sprite
⑥ 图集里的 sprite 从哪来
   assets/minecraft/atlases/armor_trims.json 的 paletted_permutations
     textures = ["trims/models/armor/coast", ..., "<pattern>_leggings", ...]   （36 条）
     palette_key = "trims/color_palettes/trim_palette"
     permutations = { "quartz": "trims/color_palettes/quartz", ... }          （14 条）
   PalettedPermutations.run :57-68  为每条 texture × 每个 permutation 生成一个 sprite，
     名字 = <texture>_<permutationKey>            ← 正好等于第 ④ 步算出来的 suffix
```

### 5.2 四样 + 一样隐含项

| # | 要写的东西 | 位置 |
|---|---|---|
| **1** | 纹饰材质定义（`asset_name` + `ingredient`） | `data/<ns>/trim_material/<id>.json` |
| **2** | 8×1 色卡 PNG | `assets/<ns>/textures/trims/color_palettes/<asset_name>.png` |
| **3** | 图集置换条目 | `assets/minecraft/atlases/armor_trims.json` 的 **`permutations`** 里加 `"<asset_name>": "<ns>:trims/color_palettes/<asset_name>"`（注意：source 的 `type` 是 `paletted_permutations`，**里面那个字段叫 `permutations`**） |
| **4** | 材料物品进标签 | `#minecraft:trim_materials`（它就是原版 18 条纹饰配方的 `addition`） |
| **5**（隐含，通常自动满足） | 盔甲进 `#minecraft:trimmable_armor` | 内容 = 四个槽位标签，所以挂了 `head/chest/leg/foot_armor` 就自动成立 |

> **覆盖原版文件会合并，不会替换**：`SpriteSourceList.load` 用 `getResourceStack(...)` 读图集定义，
> 所以你只要在自己的 jar 里放
> `assets/minecraft/atlases/armor_trims.json`（只需要写 `permutations` 里你新增的那几条），
> 原版的 36×14 个 sprite 照旧存在。**不要**把原版那 36 条 textures 抄一份过来改。
> 【读源码】`PalettedPermutations.run` + 源仓库 `docs/创造页分区栏目-参考实现/02` §2 对
> `SpriteSourceList` 的同类结论（那一条是针对 `gui.json` 的，机制相同）。

### 5.3 缺哪一样 → 表现成什么（照症状查）

| 缺什么 | 玩家看到的现象 | 客户端日志 | 依据 |
|---|---|---|---|
| **材料不在 `#minecraft:trim_materials`** | 锻造台里放好模板+盔甲+材料，**根本不匹配配方**：结果槽空着、点不动 | 无 | `SmithingTrimRecipe.java:34-36` |
| **没有 `data/<ns>/trim_material/<id>.json`** | 配方**能**匹配（标签里有它），但结果槽**就是不出产物**，点了没反应 | 无 | `SmithingTrimRecipe.java:38-46`、`TrimMaterials.java:45-47` |
| **色卡 PNG 缺失** | 锻造**成功**（tooltip 里纹饰名字都在），但身上的纹饰显示 **紫黑格（missing sprite）** | `Failed to load palette image <ns>:trims/color_palettes/xxx` + `unable to apply palette to ...` | `PalettedPermutations.java:104-120`（缺图 → error + throw）、`apply` 捕异常后返回 null ⇒ sprite 被丢弃 |
| **色卡不是 8×1（像素数与 `palette_key` 不等）** | 同上紫黑格 | `Palette mapping has different sizes: N and M` | `PalettedPermutations.java:78-84` |
| **图集里没加 `permutations` 条目** | 同上紫黑格 | **一条日志都没有**（`getSprite` 是 `getOrDefault(list, missingSprite)`，静默回退） | `PalettedPermutations.run:57-68` 只对 `permutations` 里的 key 生成 sprite |

**「8×1」的硬约束来自哪**：`createPaletteMapping` 要求**两个 `int[]` 长度相等**
【读源码】`PalettedPermutations.java:78-84`——比较的是 `palette_key` 与你的色卡的**总像素数**
（`NativeImage.getPixelsRGBA()`）。原版 `trims/color_palettes/trim_palette.png` 是 8×1，
所以你的色卡也必须是 8×1（8 像素）。写成 16×1 会直接触发长度不等。

### 5.4 本仓库现状

## 6. 猪灵中立：覆写 `makesPiglinsNeutral` 与进 `#piglin_loved` 的区别

**判定链**【读源码】：

```java
PiglinAi.isWearingGold(LivingEntity)          :641-650
  for (ItemStack stack : livingEntity.getArmorAndBodyArmorSlots())
      if (stack.makesPiglinsNeutral(livingEntity)) return true;

IItemExtension.makesPiglinsNeutral            :132-134   ← 默认实现
  return stack.getItem() instanceof ArmorItem
      && ((ArmorItem) stack.getItem()).getMaterial() == ArmorMaterials.GOLD;
```

注意默认实现里的 **`==`**：它比的是 Holder 身份，**只认原版金质材质**。所以：

| 做法 | 效果 | 副作用 |
|---|---|---|
| **A. 覆写 `makesPiglinsNeutral`** 返回 `true` | 只要穿在身上就中立（单件即中立） | 无。但**只影响"穿着"这一条判定** |
| **B. 把物品加进 `#minecraft:piglin_loved`** | 穿着中立，**而且**：掉在地上的这件物品会被猪灵**主动捡起并端详**；玩家**手持**它时猪灵不主动攻击 | 是"金质物品"的完整语义，不只是防具语义 |

**依据**：`PiglinAi.isLovedItem(ItemStack)` 就是 `item.is(ItemTags.PIGLIN_LOVED)`
【读源码】`PiglinAi.java:478-480`；捡起/端详走的是同一个判定
【读源码】`PiglinAi.java:342-345`；「玩家手持喜爱物 → 猪灵不生气」也是
【读源码】`PiglinAi.java:826-827`。

⇒ **建议**：只想「穿甲不被猪灵打」就用 A（覆写）；想让它同时是「猪灵的宝物」才用 B。
把一整套盔甲塞进 `piglin_loved` 会让猪灵把你掉在脚边的头盔捡走，这一点必须先想清楚。

> 另一条容易混淆的：`IItemExtension.isPiglinCurrency`（默认只认金锭）只管**以物易物**，与中立无关。

**本仓库现状（已核对，正确）**：`coe/src/main/resources/data/minecraft/tags/item/piglin_loved.json`
把 `createoreexpansion:sapphire_ingot` 与 `sapphire_block` 放进去了。因为本仓库**没有蓝宝石盔甲**，
所以不会出现「盔甲被猪灵捡走」。**只有锭和块会**被捡——按 `#piglin_loved` 的语义这是符合预期的。
（4 套盔甲都是翡翠/宝石/星界/雷鸣，不该有猪灵中立，本仓库也没给，正确。）

## 7. 工具 `Tier` 与最终伤害/攻速

### 7.1 六个方法各自影响什么

| 方法 | 影响 | 备注 |
|---|---|---|
| `getUses()` | **工具的总耐久** | `TieredItem` 直接 `properties.durability(tier.getUses())`【读源码】`TieredItem.java:7` —— **没有"基数+修正"这回事** |
| `getSpeed()` | 挖掘速度倍率（进 `Tool.Rule.minesAndDrops(block, speed)`） | 见 `Tier.createToolProperties`【读源码】`Tier.java:14-16` |
| `getAttackDamageBonus()` | **加进攻击伤害修饰符**的加成 | 见下 7.2 |
| `getEnchantmentValue()` | 附魔台等级池/经验消耗 | **不决定能否附**（见 §4） |
| `getIncorrectBlocksForDrops()` | 挖了也不掉落的方块标签 | 例：`BlockTags.INCORRECT_FOR_NETHERITE_TOOL` |
| `getRepairIngredient()` | 铁砧修复材料 | 每次调用都 `.get()`，所以可以晚绑定 |

**【记录 + 读源码】本仓库 `AllTiers.java:43` 的注释说「耐久基数，耐久基数加上工具的耐久修正值才是耐久度」——
这在 1.21.1 是错的**：`TieredItem.java:7` 说明 `getUses()` 就是最终耐久。
所以 `AllTiers.JADE(1600, ...)` 的翡翠镐耐久就是 **1600**，不是「1600 + 某个修正」。

### 7.2 最终伤害/攻速的公式（含算例）

`createAttributes` 只有一个式子（`DiggerItem` / `SwordItem` 完全相同）
【读源码】`DiggerItem.java:18-31`、`SwordItem.java:35-53`：

```java
ItemAttributeModifiers.builder()
  .add(Attributes.ATTACK_DAMAGE, new AttributeModifier(BASE_ATTACK_DAMAGE_ID,
        attackDamage + tier.getAttackDamageBonus(), ADD_VALUE), MAINHAND)
  .add(Attributes.ATTACK_SPEED,  new AttributeModifier(BASE_ATTACK_SPEED_ID,
        attackSpeed, ADD_VALUE), MAINHAND)
```

玩家基础值【读源码】`Player.createAttributes():228-232` + `Attributes.java:27-40`：

- `ATTACK_DAMAGE` 玩家为 **1.0**（`Player.createAttributes` 里显式 `.add(Attributes.ATTACK_DAMAGE, 1.0)`）
- `ATTACK_SPEED` 默认 **4.0**

⇒

```
最终伤害 = 1 + (createAttributes 的第 2 参数 + tier.getAttackDamageBonus())
最终攻速 = 4 + createAttributes 的第 3 参数          （单位：次/秒）
```

**源仓库给的算例（题面那份）**：tier 加成 **4.5**，剑取 `createAttributes(t, 4.5F, -2.2F)`

```
伤害 = 1 + (4.5 + 4.5) = 10.0     ✅ 与规格「剑 10 伤害」一致
攻速 = 4 + (-2.2)      = 1.8      ✅ 与规格「剑 1.8 攻速」一致
```

源仓库把这一组数字跑了运行时探针（读实体的 `Attributes.ATTACK_DAMAGE` 最终值），
四件套结果与规格逐项相同【记录】`bettergold/docs/1.4-进度与交接.md` §一。

**对照：本仓库五件器具的实际数值**（按上面的公式推算，`CoeItems.java` 各器具的
`createAttributes` 参数 + `AllTiers.java:22-32` 的 tier 加成）：

| 器具 | 翡翠 (3.5) | 黄玉 (4.0) | 蓝宝石 (4.5) | 星辉石 (5.0) | 雷鸣 (5.0) |
|---|---|---|---|---|---|
| 剑 | 8.5 / 1.6 | 9.0 / 1.6 | 10.5 / 1.6 | 10.0 / 1.6 | 10.0 / 1.6 |
| 镐 | 5.5 / 1.2 | 6.5 / 1.7 | 7.5 / 1.5 | 7.5 / 1.7 | 7.5 / 1.7 |
| 斧 | 10.5 / 1.0 | 11.5 / 0.8 | 12.0 / 0.6 | 12.5 / 0.8 | 12.5 / 0.8 |
| 锹 | 6.0 / 1.0 | 6.5 / 1.2 | 7.0 / 1.2 | 7.5 / 1.2 | 7.5 / 1.2 |
| 锄 | 2.5 / 3.0 | 3.5 / 4.0 | 4.5 / 4.0 | 4.5 / 4.0 | 4.5 / 4.0 |

（格式：**最终伤害 / 最终攻速**。这是**算出来的**，标【推断】——要变成【实测】必须按 `04` 跑探针打表。）

⚠️ 表里有一处**符合预期但值得用探针确认**的地方：**蓝宝石斧（12.0）低于星辉石斧（12.5）且攻速更低（0.6 vs 0.8）**，

## 8. 数据驱动的材料链 / 升级模板

### 8.1 材料链（原料 → 熔炼 → 锭、锭↔粒↔块）

源仓库的做法是**两层标签**：

```
data/<ns>/tags/item/{ingots,nuggets,raw_materials,storage_blocks}.json     ← 家族标签（只往这里加一次）
data/<ns>/tags/item/... 之外：桥接标签的内容是 "#<ns>:ingots"                ← 自动流进 c: 与 minecraft:
```

于是新加一种金属**只改家族标签**，`#c:ingots`、`#minecraft:beacon_payment_items` 自动跟上。
【记录】`bettergold/docs/新增材料家族.md` §一/§二。

**本仓库现状**：用的是**按材料分文件**的写法，例如
`coe/src/generated/resources/data/c/tags/item/ingots/jade.json`、`.../rods/jade.json`…
（生成物，来源是 Registrate 的 `.tag(AllGemTags.JADE.ingots)` 之类）。
【资源实测】`c:ingots`、`c:nuggets`、`c:raw_materials`、`c:ores/*`、`c:storage_blocks/*` 都在，
覆盖面比源仓库更细。⇒ **已正确**，不需要改造。

⚠️ **一条要留意的现状**：全仓（`coe` + `cews` + `core` + 根 `src`）grep **没有任何
`minecraft:smelting` / `minecraft:blasting` 配方**。矿石掉落 `raw_*`，而 `raw_* → *_ingot`
只能走 Create 的加工链（`crushing` → `splashing` → 粒 ×9 → 锭，或 `pressing`/`rolling`）。
这**可能是有意设计**（本模组是 Create 附属，矿物加工本就该走机械），也可能只是漏了。
`06` 把它列为「观察，不确定是否有意」并给了确认方法。

### 8.2 `smithing_transform`（升级锻造）与 `SmithingTemplateItem` 的五段文案

`smithing_transform` 配方三槽：`template` / `base` / `addition`，产物写在 `result`。
（`smithing_trim` 是另一种类型，见 §5。两者不要混。）

`SmithingTemplateItem` 的构造器在 1.21.1 是 **7 个参数**
【读源码】`SmithingTemplateItem.java:71-86`：

```java
public SmithingTemplateItem(
    Component appliesTo,                  // 1 段文案
    Component ingredients,                // 2 段文案
    Component upgradeDescription,         // 3 段文案（工具提示里的标题行）
    Component baseSlotDescription,        // 4 段文案（基础槽空位说明）
    Component additionsSlotDescription,   // 5 段文案（添加槽空位说明）
    List<ResourceLocation> baseSlotEmptyIcons,        // 基础槽的空位图标
```

**五段文案是你自己传进去的 `Component`，语言键由你决定**——原版只是用
`Util.makeDescriptionId("item", <ns>:smithing_template.<name>.<suffix>)` 这个写法，
得到 `item.<ns>.smithing_template.<name>.<suffix>`。源仓库的写法可以直接照抄
【读源码】`bettergold/src/main/java/com/hjmmd_8/bettergold/material/MetalFamily.java:396-413`
（它用 `item.bettergold.smithing_template.<id>_upgrade.applies_to` 等 5 个键）。

**⚠️ 空位图标的文件名很容易写错**——`SmithingTemplateItem` 里原版用的常量是

```java
EMPTY_SLOT_CHESTPLATE = "item/empty_armor_slot_chestplate"
```

【资源实测】原版 `assets/minecraft/textures/item/` 下**只有** `empty_armor_slot_*.png`

> missing texture（紫黑格）。因为源仓库没有为"空位图标"做过像素级验证，这条一直没被发现。
> **COE 做升级模板时请直接用 `empty_armor_slot_*`。**

### 8.3 材料链与纹饰的"生成器"思路（值得抄的组织方式）

源仓库把「一种材料的全套资源」交给 `tools/asset-generator/` 下的 Python 生成器批量产出
（贴图/方块状态/模型/语言/战利品表/标签/配方/纹饰），并配两个校验器
（`validate_metal_assets.py` / `validate_metal_data.py`）在收尾时确认没漏文件。
【记录】`bettergold/docs/新增材料家族.md` §三。
**关键收益**：新增材料**只改一处清单**（生成器里的 `METALS` 表），而不是"照着现有材料手工改名"。

本仓库的资源已经是 datagen（Registrate + `src/generated`），思路等价但**更硬**：
生成物进版本库、`runData` 就是校验关卡。要加材料时优先沿用现有 datagen 路径，
**不要**手工往 `src/main/resources` 里放与 datagen 同名的文件——本仓库的
`AGENTS.md` 已经记过「同名会让 `processResources` 报 duplicate 而构建失败」。
