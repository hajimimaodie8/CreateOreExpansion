# 技能内核对比与迁移分析（createoreexpansion ↔ Skiller）

- 分析对象 A：本工程 `E:\mc\mcmod\createoreexpansion`（分支 `leaf-dev`，包根 `com.hjmmd_8.createoreexpansion`）
- 分析对象 B：朋友 Leaf 的参考实现 `https://github.com/lizhanyu-leaf/Skiller`（本地克隆 `E:\mc\mcmod\_ref\Skiller`，包根 `com.leaf.skiller`）
- 结论基于实读代码 + grep 实证；无法本地编译 B（见 §7 说明），因此 B 的编译期问题未做实证，仅做静态判定。

## 0. 结论速览

1. **两者同源**：B 是在 A 的技能系统上做的「抽核」重构。14 个同名文件，其中工具层（`IParams` / `ParamsPool` / `FrameParams` / `MinecraftMixin`）**几乎逐字搬走**（相似度 89%~99%），语义层则全部重写。
2. **换核方向上，B 解决了我这边审计出的最痛的 5 处倒置**：静态注册表、能量耦合、客户端渲染器倒置、`MOD_ID` 硬编码翻译键、`SkillType` 枚举不可扩展。
3. **但 B 目前是「接口齐、接线缺」，且有三处硬阻塞**（均已逐条实证，见 §6）：
   - **序列化往返是坏的**：`SkillData.toString()` 丢掉 `factoryId`，而 `fromString()` 去读一个**从来没被写入过**的 `"Factory"` 键 → 新数据也存不下、读不回，技能会被静默丢弃。
   - **主链路断在服务端**：按键能发能存，但 `PlayerPressedKeys.isPressed` / `ServerSkillCache.getBundle` / `SkillBundle.releaseSkills` **零调用点** → 没有触发入口。
   - **渲染器从未注册**：`StrategyRenderers.register(...)` 零调用 → `RENDERERS` 永远空表，一旦真有策略技能实例，`schedule()` 必然 NPE。
   它是一个**从未被编译验证过**的骨架（`build/classes` 下 0 个 class），没有一个可直接用的具体技能。
4. **B 缺少我这边的四类能力**：属性修饰器（砍树减速）、技能冷却、附魔驱动的等级/消耗修正、**物品级**资源（工具上的 FE；B 的 `SkillResource` 只吃 `Player`，拿不到 `ItemStack`）。这四类必须在换核时自己补。
5. **建议路径**：不要把 A 的 `foundation/item/skill` 直接删掉等 B。先做「依赖倒置」（把 A 里框架对 content/common/client 的 11 处反向依赖抽成接口），再按 §8 的分阶段顺序换核；同时对 B 补 3 处接线。

### 2.2 五张自定义注册表（B 的核心机制）

`SkillerRegistries:42,54,66,78,80` 定义键，`SkillerBuiltInRegistries:52,65,79,92,94` 创建实例：

| 注册表 | 装什么 | 谁写入 |
|---|---|---|
| `SKILL_RESOURCES` | `SkillResource` | `AllSkillResources` 静态块 |
| `SKILL_FACTORIES` | `SkillInstanceFactory` | `AllSkillInstanceFactories` 静态块 |

| `STRATEGIES` | `SkillStrategy` | **无人写入** |
| `CONTEXT_FACTORIES` | `SkillContextFactory` | **无人写入** |

创建方式（`SkillerBuiltInRegistries.register:170-181`）：`new RegistryBuilder<>(key).sync(true)` → `create()` → `((WritableRegistry) BuiltInRegistries.REGISTRY).register(key, registry, RegistrationInfo.BUILT_IN)`；时机靠 `BuiltInRegistriesMixin:16-18` 的静态块在 `BuiltInRegistries.<clinit>` 期间触发。第二个注入点 `:20-28` 把 `BuiltInRegistries.validate` 里的 `Registry.forEach` 包装一层，**跳过所有 `skiller:` 命名空间的注册表**（让自己的空表免于校验报错）。

### 2.3 三条数据流（简）

- **注册**：`BuiltInRegistries.<clinit>` → mixin 静态块 → 5 张表就位 → `Skiller.onRegister:127` → 三个 `register()`（空方法，仅触发静态块）→ 写入资源/工厂。
- **收集**：`ClientEvents.onKeyInput:53` → `ClientSkillCache.enable:165` → `SkillProviders.collectAllSkills:134`（对每个 provider 调 `collectSkills`）→ `HeldItemSkillProvider:66` 取主手/副手 → `SkillProvider.addStack:96` 读 `SKILL_COMPONENT` → `SkillSet.add:132` 按 skillId 去重、保留最高 level → `toBundle()` → 客户端缓存 + 渲染调度 + `SkillTogglePacket` 通知服务端（`ServerSkillCache.onToggle:69`）。
- **释放**：`SkillBundle.releaseSkills:204` → 非创造才收费 → 按资源键 `computeIfAbsent(getDelayConsumable)` → `instance.consumeResource(ctx, consumable)`（技能内部只调 `consumable.consume(cost)` 累加）→ **统一 `canConsume()` 校验** → **统一 `apply()` 结算** → 逐个 `instance.release(ctx)`。**但全仓库没有任何地方调用 `releaseSkills`。**

## 5. 我这边必须自己补（B 没有的四类能力）

1. **物品级资源**：`SkillResource.getAmount/canConsume/consume` 全部只吃 `Player`（`SkillResource.java:67,94,120`），`SkillContext` 只有 `getPlayer()`（`SkillContext.java:6`）。
   - 处理：给资源接口加 `ItemStack` 参数（改 core），或让 `SkillContext` 提供 `getStack()`（更通用），或把工具能量搬到玩家身上（下策，会改变现有玩法）。
2. **技能冷却**：需要新的数据组件（B 的 `AllDataComponents` 只有 `SKILL_COMPONENT`），并统一 A 里散落的 3 处冷却来源。
3. **附魔驱动的等级/消耗修正**：B 无接入点 → 建议做成 `SkillInstanceFactory` 的可选扩展（读档时按附魔修正 level / 按附魔折算消耗）。
4. **分级数值表**：A 的 9 个技能全部 `.config().configsByLevel()`，B 只有 `level()` → 数值表下沉到 content 层，用 `instance.level()` 查表（这一步其实是好的解耦）。

## 7. 迁移风险（我这边的 Top 5）

1. **存档静默丢技能**：技能 id 存在物品组件的字符串里（`createoreexpansion:skills` → `skillId{Level,Config,OutlineColor}`）。换核后组件键与 NBT schema 全变（新版要求 NBT 内有 `Factory` 字段，否则 `SkillData.fromString` 解析出空 factory → `NbtSkillInstanceFactory` 返回 null → 技能静默消失）。**必须决定：写 DataFixer / 做一次性升级 / 声明 1.0.0 不兼容旧存档。**
2. **触发链要整体重写**：A 的 4 个入口（`ServerPlayerGameModeMixin`、`HurtLivingEntityHandler`、`UseItemHandler`、`JadeTopazBowItem`）都要改成「收集 → 释放」模型。
3. **纯客户端按键的多人缺陷（现存 bug，换核正好修掉）**：`AllKeys` 是 `@EventBusSubscriber(Dist.CLIENT)`（:18），`isPressed()` 在服务端因 `keybind == null` 恒返回 false（:82-84），而 `ServerPlayerGameModeMixin:26` 注入的是 **`ServerPlayerGameMode`**（服务端类）。全工程**没有任何按键同步包**（只有能量场的 `EnergyFieldSyncPayload`）→ 单人/局域网靠同 JVM 静态状态"看似正常"，**专用服务器上技能键永远不会触发**。B 的 `KeyPressedPacket` + `PlayerPressedKeys` + `ServerSkillCache` 就是这个问题的正解。
4. **`SkillsComponent.applySkillBoost` 改内存态**：`SkillsComponent:198-208` 会替换 `data.config` 实例，破坏其"不可变"注释与 `equals/hashCode` 稳定性；换核时这段逻辑要按 B 的 `instance.level()` 模型重写。
5. **条目命名空间必须自己守住**：B 的 5 张注册表**键**硬编码在 `skiller:` 命名空间（`SkillerRegistries:96-98`），但**条目 id 的命名空间由注册方决定**。注册时务必用 `createoreexpansion:fell` 这类 id（而不是 `skiller:fell`），否则翻译键（`skill.{ns}.{path}`）与存档里的技能 id 全部对不上。这是本次分析中最容易被忽略、但代价最高的一处。

## 8. 建议的处理路线

### 阶段 0（现在，不等 core，可独立完成）
在 A 里做**依赖倒置**，把 §3 表的 11 处反向依赖抽成接口：能量 SPI、等级修正 SPI、注册表 SPI（`getId/get/getData` 三个方法即可）、渲染器改 `ResourceLocation`、翻译键去 `MOD_ID`、`resolvePlayer` 统一。这一步做完，A 编译通过、玩法不变，但换核时改动面从"重写半个框架"降到"改 import 与注册方式"。

### 阶段 1（等 core 稳定：先让人把硬阻塞修掉）
按优先级要求作者修 §6 的 #0（序列化 `Factory` 键）、#5（`AllKeys` 标 `Dist.CLIENT`）、#4（注册渲染器）、#1~#3（注册内容 / 释放入口 / 写回路径），并跑通一次 `gradlew compileJava` + 客户端与服务端双端启动。**在 #0 修好之前不要开始换核**——否则存进物品的技能读回来全是 null。

### 阶段 2（换核）
按 §4 的映射表逐类替换：先 `IParams/ParamsPool/FrameParams`（零改动复用）→ 再 context/config/attribute（改 import）→ 再 `ItemSkill/ISkillInstance` 语义层（重写 9 个技能类）→ 最后 `AllSkills` 注册表与 `AllItems` 绑定（改动最大）。

属性修饰器、冷却、附魔修正、物品级 FE 资源 —— 建议以「core 的扩展件」形式实现（放我这边，或做成 core 的可选模块反哺朋友），不要把强模组语义塞回 core。

### 每阶段验证
`.\gradlew.bat compileJava` → `.\gradlew.bat runData`（mixin/Bootstrap 冒烟）→ `.\gradlew.bat processResources jar --rerun-tasks` → 进游戏实测（重点：按键触发、能量扣减、冷却、旧存档读档）。换核后额外加一项：**专用服务端启动一次**（验证 `Dist` 边界与 mixin 时序）。
