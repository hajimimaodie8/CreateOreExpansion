## 0. 结论速览

| 项 | 结论 |
|---|---|
| 引入方式 | **JarJar 嵌套**：`jarJar(implementation("com.leaf:skiller:1.0.0"))`，jar 放 `libs-maven/`（本地 maven 布局，随仓库提交）。dev 运行时它作为独立 mod（mod id `skiller`）加载，mixin 生效。 |

| 迁移方式 | **增量并行**：技能注册进 Skiller 注册表 = 新内核接管；没注册 = 旧框架照旧。同一时刻只有一个内核处理某个技能 → 不会双重生效。 |
| 技能开销 | 走新的 `SkillResource`（`createoreexpansion:tool_energy`），仍读主手工具 FE + 凝能佩兜底。 |
| 总开关 | **不要** Skiller 的「按 R 启用技能」总开关（保持本模组随时可用的既有玩法）：客户端进入世界自动 `ClientSkillCache.enable(...)`，服务端释放路由**不读** `ServerSkillCache`。 |

## 2. 架构：新旧并存的接线

```
旧：ItemStack(createoreexpansion:skills = List<字符串 "id{Level,Config,OutlineColor}">)
      │
      ├─(未迁移的技能)→ 旧框架 foundation/item/skill/** + content/skill/**（一行不改，继续跑）
      │
      └─(已迁移的技能)→ CoeSkillProvider ── 转成 ──→ Skiller SkillComponent(Map<槽位, SkillBundle>)
                              │                        槽位 = 该技能在自己 SkillType 里的下标（= 键一/二/三）
                              │                        nbt = 旧 nbt 拷贝 + resource:"createoreexpansion:tool_energy" + level
                              ↓
        ClientSkillCache.enable/refresh（客户端）  ──按键状态──→  PlayerPressedKeys（服务端权威）
                              ↓
        CoeSkillRelease.release(player, type, env)  →  bundle.releaseSkills(type, env)  →  新技能实现
```

要点：
- **槽位语义**沿用旧系统：某类型内第 i 个技能 → 按键槽位 i（键一/二/三）。三个类型同槽位的技能放进同一个 `SkillBundle`。
- **未注册进 Skiller 的技能 id 会被 Provider 跳过** → 旧框架继续处理它。这条是增量迁移的基础。
- 释放**不读** `ServerSkillCache`/`SkillReleaser`（那条路要求玩家先按开关启用），改用 `PlayerPressedKeys` 直接判按键。
- 客户端 `enable()` 由我方自动调用（登录后一次），换主手物品时调 `ClientSkillCache.refresh(player)` 重算槽位。

## 3.5 W5 渲染器移植清单（下一块要做的活，已勘明改动面）

**目标**：让新内核负责挖掘预览（现在预览仍由旧 `SkillsStrategyRenderer` 提供），从而具备删旧框架的条件；同时完成目标里那句「接通 `StrategyRenderers.register` 调用点」。

**前置已完成**：上游 `StrategyRenderers.schedule()` 的判定对象修好了（`instance.skill()` → `instance.skill().getSkill()`，fork 提交 `4c0246c`，jar 已同步为 SHA256 `D39281CC…09E3`）。不修这条，注册渲染器也永远不会被调度。

**要写的东西**（新文件，放 `integration/skiller/client/`）：

1. `CoeSkillRenderers.java`（客户端初始化）：`StrategyRenderers.register(CoeAreaAoeStrategy.RENDERER_ID, new CoeBlockOutlineRenderer())`。注册时机要早于 `ClientSkillCache.enable(...)`（`enable` 内部会 `StrategyRenderers.schedule()`）—— 最省事的落点是 `CoeSkillClient.injectKeySourceOnce()` 里，与键位注入同一处。
2. `CoeBlockOutlineRenderer implements StrategyRenderer<ExcavationSkillContext>`：
   - `getContext(mc, level, player, instance)`：
     * 准星拾取中心：`player.pick(20.0D, 0, false)` → `BlockHitResult`（与释放路径同一个 20 格）；
     * 构造 `new ExcavationSkillContext(level, hit.getBlockPos(), player.getMainHandItem(), player)`；
     * 用该技能自己的策略判 `canCollect` + `collect`（策略从 `instance` 走 `StrategySkill.strategy()`），空集合则返回 `Optional.empty()`；
     * 颜色从 `instance.data().getCompound("OutlineColor")` 读（旧实现读的是 `DataSkill.nbt` 的同名子标签，键格式一样）。
   - `render(context, instance, mc, stack, camera, buffer)`：
     * **注意缓冲类型变了，而且必须自己冲刷**：旧实现收的是 Create 的 `SuperRenderTypeBuffer` 并自己 `buffer.draw(type)`；新接口给的是原版 `MultiBufferSource`，**没有人替我们 `endBatch`** —— 上游 `com.leaf.skiller.client.ClientEvents#onRenderLevel` 只把 `mc.renderBuffers().bufferSource()` 传进来、**自己不冲刷**，所以算完必须自己按 RenderType 结算（本仓 `CoeBlockOutlineRenderer#flush` 就是这么做的：`((MultiBufferSource.BufferSource) buffer).endBatch(RenderType.LINES)` + `endBatch(AllRenderTypes.LINES_TRANSPARENT)`）。分别 `buffer.getBuffer(RenderType.LINES)`（不透明层）与 `buffer.getBuffer(AllRenderTypes.LINES_TRANSPARENT)`（穿透层，仍然绘两遍、第二遍 alpha×0.3）；⚠️ **本节早期写的"不要调 draw（由框架统一冲刷）"是错的、与代码相反，已更正**（W1 实测）。
     * 画线逻辑直接复用现成的 `OutlineRenderer.renderOutline(...)`（它只吃 `Set<BlockPos>` + `VertexConsumer`，与新旧框架无关，是这次唯一不用改的资产）。⚠️ **落点订正**：它现在住在 `integration/skiller/client/OutlineRenderer.java`（W2 渲染统一时从 `client/tool/` 搬走，`client/tool/` 目录已不存在）——**不能放进 `client/render/**`**，`check-layering.ps1` 按路径判层、那里刻意判 SHARED，会当场产生 `SHARED -> COE` 违规；
   - `getStage()` 返回 `RenderLevelStageEvent.Stage.AFTER_TRANSLUCENT_BLOCKS`（与旧 `BlockToolOutlineRenderer` 一致）。
3. `CoeFellingStrategy` 与 `CoeAreaAoeStrategy` 共用 `createoreexpansion:block_outline`（已经是这样），所以只需要注册一个渲染器。
4. 命中/挖掘类以外的技能（`skin`/`plunder` 的实体描边）：**`skin`/`plunder` 现在都实现 `StrategySkill` 并引用 `CoeEntityStrategy`**（本条早期写的"新实现是普通 `ItemSkill`（不实现 `StrategySkill`）"**已过期**——那正是"对着生物没有预选框"的病根，已在迁移中补上；`CoeEntityStrategy.collect` 恒返回空集合，只为给出 `getRendererId()`）。内核 `schedule()` 因此能把它们扫到，描边由 `CoeEntityOutlineRenderer` 画。

    - **AOE 矩形朝向要本地化**：结构场景把玩家视线与所击方块面先用 `bridge.toLocalDir` 转进局部系再交给 `DualDirection`（新增 `fromLocal`，旧签名一字未改），矩形才会随结构倾斜；玩家自身已在局部系时**不要**再转一次（会反向旋转两遍）。
    - **已知未做项**：服务端释放路径的 `ExcavationSkillContext` 仍由 4 参构造器建立（`subLevelHit` 恒 null）→ **结构上真正挖哪些方块仍按世界坐标算**，预览与实效在结构上不一致。
15. **调试"看不到效果"的问题，先确证路径有没有被激活**：这轮我在结构兼容代码从未激活的前提下，连改相机位移、发光钩子、矩形朝向、局部坐标识别四轮而毫无效果。正确顺序是：**先让现场数据可见 → 确认入口成立 → 再改内部逻辑**。用户在生产整合包里测试时日志路径与 dev 的 `run/logs` 不同，**优先用动作栏显示诊断**（`displayClientMessage(..., true)` + 节流），成本最低。
