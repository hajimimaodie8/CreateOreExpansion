## 0. 总览：波命中一个方块容器之后发生了什么

入口：`handleItemInventoryBlock(IItemHandler handler, BlockPos pos)`

```
命中方块带物品容器
 ├─ 客户端 / 无加工能力(attributes+recipeTypes 皆空) → 交回基类默认行为
 ├─ chainLeft <= 0 → 释放载荷并消散
 ├─ 取命中方块的流体能力（工作盆盆内流体；置物台无 → null）
 └─ while (chainLeft > 0):
      ① findCraftableSlot()  找"第一个存在可执行候选"的槽
      ② craftFromSlot()      从该槽执行一次加工
      ③ 成功 → batchLock = 本次候选；chainLeft--；回到 ①
      ④ 失败（该槽所有候选都推不出产物）或 找不到槽 → break
 └─ 本批是否加工过？
      ├─ 有 → 链尽则释放载荷+消散；否则波继续飞行（不在此消散）
      └─ 无 → 按"撞墙"消散（调用方处理）
```

**链式（连锁加工）的来源**：每轮循环都重新 `findCraftableSlot()`，所以"上一步的产物"会在下一轮被当作新输入重新评估。
**前提**：产物必须**留在容器里**（放不下会被丢到地上，连锁就断了——这是"一盆原木只去皮"的原因，已修）。

## 0.1 变器"扫描到哪些加工机"：含**非动能机**（2026-09 修正）

`StellarWaveTransmuterBlockEntity#collectMachines` 收录条件是 `isMachinery(pos)`
（目录登记机器 ∪ 启发式动能处理机），<b>不再要求 `instanceof KineticBlockEntity`</b>。

**修的是什么**：Create 的**注液器 Spout**（`filling`）与**物品排放器 Item Drain**（`emptying`）
都是 `SmartBlockEntity`、不是动能机 → 旧实现把它们整个跳过 → 波永远拿不到 `filling`/`emptying`
类型 → §1.1 的类型门把这些配方挡掉。用户实测表现："水正常抽到了，但击中之后只被存进附近储罐，
不给铁桶注液"——本质是**没候选 → 波按撞墙消散 → 余料按 `wave.payloadRelease` 就近入储罐**。

**配套口径**：
- 机器数（面板"读取到 N 台加工机"）＝全部收录机器；
- 应力乘子只按**动能机**数算（`scannedKineticCount`，新增同步字段；旧存档无该键时退回旧口径），
  非动能机不耗应力、不进乘子；
- 载荷抽取的排除口径（`isMachinery`）不变：机器内部库存照旧不抽。

## 0.2 「给桶注液」不是配方：载荷注液旁路（2026-09-14 新增）

**用户反馈**："注液配方仍然没有被成功执行"。日志实测（`[变体波轨迹]`）：

```
命中 MutableBlockPos{x=19, y=72, z=-149} 无任何可加工候选 → 按撞墙消散；
容器内容 [0]minecraft:bucket×1（属性 13 个 / 配方类型 14 个）
```

空桶在容器里、波带着 13 个属性 / 14 个配方类型，候选却是 **0 条**。逐条核到底（反编译 Create 源码）：

- Create 的 19 条内置 `create:filling` 配方里**没有任何一条以空桶为原料**（都是"瓶/食物 + 流体"这类）；
- 真机里"给空桶灌水"根本不走配方——流体喷口（spout）走的是 `GenericItemFilling` 的**特判**：
  拿物品自身的 `Capabilities.FluidHandler.ITEM` 灌满，再用 `getContainer()` 换出成品桶；
- 也就是说：`filling` 类型门、辅料门槛、流体门槛**都不是问题所在**——这条路径从头到尾就不存在配方。

**结论（口径缺失，不是门槛缺陷）**：注液是**货载动作**，与"余料流体注进附近储罐"（`WaveOutputPlacer.fillNearby`）
同一层级，<b>不需要</b>波携带任何加工机属性 / 配方类型。

**改法**：新增 `content/charger/craft/WaveItemFluidFilling`（唯一实现），在 `WaveCraftExecutor.handleBlockHit`
的批量循环里作为"找不到任何配方候选时"的**兜底分支**（`plan.slot() < 0` → `fillOne(...)`）：

| 环节 | 口径 |
|---|---|
| 用量与成品 | **委托** Create `GenericItemFilling`（`getRequiredAmountForItem` / `fillItem`）——空桶 1000 mB、玻璃瓶 250 mB、需要"该流体有对应桶物品"、已装物品不再灌，全部与真机一字不差，不自己复刻桶/瓶/药水语义 |
| 流体来源 | **只认载荷**（命中容器自己的流体槽不参与——波没有理由把容器里的液体倒进容器自己的物品里） |
| 够不够 | 载荷流体不足一份用量则**整条跳过**（不做半份注液；真机喷口同样"够一份才灌"） |
| 物品进出 | 取 1 件 → 成品**回原槽**（`WaveOutputPlacer.insertBack`），放不下则掉在命中方块上方，绝不凭空消失 |
| 链数 | **不消耗** `chainLeft`（注液不占加工额度，否则"路过一箱空桶"会把整条波的加工额度吃光）；循环必然收敛——每次成功注液至少扣 1 mB 载荷流体 |
| 状态归属 | 载荷流体的读写只走 `WaveCraftConsumption`（新增 `payloadFluid()` 只读视图 + `drainPayloadFluid(int)`），本类不直接摸实体字段 |

**取证方式**：`WaveItemFluidFilling` 每次成功注液写一行轨迹日志
（`注液：槽 N 的 minecraft:bucket ×1 + 1000 mB water → water_bucket（实扣 1000 mB，载荷流体余 …）`）。

## 1. 候选择取：两级过滤

### 1.1 库级过滤（`collectCandidates` 第一段）

| 顺序 | 条件 | 说明 |
|---|---|---|
| 1 | `allWaveRecipes()` | Create `RecipeFinder` 全库取配方（带缓存，数据包重载自动失效重查） |
| 2 | **配方类型门**：`isTypeAllowed(recipe, allowedTypeIds)` | 只收"波携带到的类型"（= 变器扫描半径内读到的机器能力快照）。**2026-09 修复**：旧实现只按材料做全库匹配，导致"把卷簧机拆掉，波照样能卷簧"。配置 `wave.requireCarriedType = false` 可回到旧的全库行为 |
| 3 | 在**波可执行范围**内：`WaveRecipeFamilies.isExecutable(recipe)` | = Create `ProcessingRecipe` 族（**族 0**，主路径）**∪** `content/charger/family/WaveRecipeFamilies` 登记的非 `ProcessingRecipe` 族（**族 1..N**，当前：拆解 `dismantling`） |
| 4 | 非本 mod 闪电类 | `LIGHTNING` / `LIGHTNING_BLOCK` 排除——闪电加工只能走"避雷针释放机会"专用路径，不能被全库命中白嫖 |
| 5 | `AllRecipeTypes.shouldIgnoreInAutomation(holder)` 为 false | Create 的 `automation_ignore` 标签；原版 Create 只标了 `occultism` 两条，故实际几乎不排除任何东西 |

**类型门的白名单从哪来**：`StellarWaveEntity#activeRecipeTypes()` —— 变器扫描半径内机器的类型快照
（含状态选择器裁剪：真空室 mode、杠杆锤锤下方块、角磨床磨轮等级+转速）＋ 载荷电量带来的额外类型
（CC&A 充电）。所以**拆掉机器 → 波不再携带该类型 → 那类配方立刻不再参与**（已在飞的旧波仍按发射时的
快照执行，这是快照语义的必然结果，寿命很短）。

配套把 Create 侧"现在能执行、但原先没有提供者"的类型补进登记表，避免开门后误伤老玩法：
压机 +`compacting`、鼓风机 +`transmuting`（嬗变液介质）、新增 注液器→`filling`、物品排放器→`emptying`、
本模组三个应力充能器→`charging`。

### 1.2 逐条门槛（`evalCandidate`）——**严格按此顺序**，任一不过即淘汰

| # | 门槛 | 不过时的含义 |
|---|---|---|
| ① | 流体输入数 ≤ 2（`MAX_FLUID_INPUTS`，对齐 Create 盆口径） | 超出口径，做不了 |
| ② | 物品输入数 ∈ [1, 9]（`MAX_ITEM_INPUTS`） | 0 输入或 >9 输入，做不了 |
| ③ | **辅料解析**：`ingredients[1..n-1]` 逐个 `findAux` | 缺料 |
| ④ | **流体解析**：`resolveFluidRefs` | 流体不足 |
| ⑤ | **电量解析**：`resolveEnergyDraws` | 电量不足 |
| ⑥ | **材料匹配**：`matches()`（三段式，见 §2） | 材料不匹配 |
| ⑦ | **机器环境**：`environmentSatisfied`（见 §4） | 热档/媒介/机头不满足 |
| → | 全过 → 产出 `Candidate(id, recipe, auxes, fluids, energies)` | |

**族 1..N 的门槛更短（`evalFamilyCandidate`）**：`族认领 → family.matches(材料) → 环境`，产出的
`Candidate` 辅料/流体/电量三张空表——<b>仅限"单输入族"（拆解）</b>；**步骤族**（序列装配）会覆写
`Family#currentStepRecipe` 给出"当前这一步"的 `ProcessingRecipe`，引擎改用族 0 的完整门槛链
（辅料解析/流体/电量/材料三段式），详见 §10。

**辅料搜索顺序（③ 的内部）**：先**命中容器自身的其它槽**（排除主料槽、排除已占用槽）→ 再**波载荷**（从扫描圈容器抽来的 ≤5 件）。
去重按"槽号/载荷条目"而非物品种类：同一槽不能被两个 ingredient 复用，但两个装着同种物品的不同槽可以。

### 1.3 工作盆过滤器闸门（候选集生成**之后**、排序**之前**）

命中方块是**带过滤器的工作盆**时（`basin.getFilter()`），对每个候选问 `recipeOutputAllowed`：

1. 配方**声明产物**（`getResultItem`）→ 过滤器放行？
2. **推导产物**（`results` 为空的变形升级/锻造融合，以及"声明产物与真产物不一致"的情况）→ 用**与执行时同一套** `computeCraftResults` 现算真实产物再测；
3. **流体产物** → 测第一个流体产物；
4. 过滤器测试带**"裸物品"兜底**：先按原样测，再清空数据组件测一次——避免"产物继承了钻石剑的附魔/耐久，就匹配不上过滤器里那把干净的下界合金剑"。
5. 判定异常 → 保守**放行**（过滤器不该把波卡死）。

过滤器为空时 `FilteringBehaviour` 本身放行一切。**被过滤器挡掉时会有轨迹日志**。

## 2. `matches()`：三段式材料匹配

Create 6 里 `BasinRecipe.matches()` 与 `HammeringRecipe.matches()` 这类"机器上下文配方"的 `matches` 恒为 `false`（真实匹配走机器静态 `match`，需要机器实体上下文），波是**远程执行器**、没有机器实体，所以：

| 顺序 | 分支 | 处理 |
|---|---|---|
| 1 | `recipe instanceof BasinRecipe` | 直接走**手判** `genericIngredientsMatch`（忽略机器过滤器与热需求——热需求由 ⑧ 单独判） |
| 2 | `SingleRecipeInput` 型（单输入主流配方：压制/喷洗/闹鬼…） | `matchesQuietly(recipe, new SingleRecipeInput(input))` |
| 3 | `RecipeWrapper` 型（需要 1 主料 + 辅料槽） | 用**临时** `ItemStackHandler(1+辅料数)` 装配（槽 0 = 主料，槽 1..n = 辅料真实物品副本），再 `matchesQuietly`；绝不对命中容器做 `setStackInSlot` |
| 4 | 都失败 → 通用兜底（仅 `ProcessingRecipe` 族） | `genericIngredientsMatch`：`ingredients[0].test(主料)` 且 `ingredients[i]` 能从对应辅料解析出真实物品并再测一次 |

`matchesQuietly` 把 `ClassCastException`（输入类型不符）与任何桥接异常都当作"不匹配"，不向调用方抛。

## 3. 搅拌配方**不需要**搅拌器（2026-09-10 修正）

**结论：搅拌器不是任何加工的前置条件。** 曾经按"盆上必须有机械搅拌器才能搅拌"实现过一版，用户确认那是输入法打错（原句应为"**不**必须"），已撤销。

**搅拌配方的实际条件**：

- 不需要搅拌器、也不需要任何机器实体（波是远程执行器）；
- 只要盆里有料、材料匹配，就能执行；
- 是否需要加热由配方自己的 `heat_requirement` 决定：`NONE` → 直接做；`HEATED` / `SUPERHEATED` → 按 §4 找烈焰人取热档。

**搅拌器的作用**：仅作为**环境判定的第三个中心**（§4），让"热源贴着搅拌器放"也认——因为搅拌器就压在盆正上方一格。它不构成门槛。

**加热能力的来源（2026-09-10 修复）**：加热**不再要求热源紧贴命中点**。变器在扫描半径内单独扫**烈焰燃烧室**
（`StellarWaveTransmuterBlockEntity#scanHeatSources`：读方块状态属性 `HEAT_LEVEL`，取最高档），
把热档随波携带（`StellarWaveEntity#carriedHeat`）——"波把周围机器的加工能力整合进自己"的机制对**热**同样成立。
**修复前的问题**：烈焰燃烧室不是动能机器（`BlazeBurnerBlockEntity` 不是 `KineticBlockEntity`），机器表永远收不到它；
而加热只在命中点/波源/搅拌器三处的 3×3×3（半径 1）里现找——变器读取半径可达 3 格，玩家把燃烧室摆在
"变器读得到、波够不着"的位置时，读表显示"没读到加热"、执行日志则报"邻域内无达标烈焰人"。

**能力矩阵（当前实现）**

| 盆的配置 | 不要求加热的搅拌配方 | HEATED 搅拌 | SUPERHEATED 搅拌 |
|---|---|---|---|
| 空盆 | ✓ | ✗（除非变器侧有热源） | ✗ |
| 只有搅拌器 | ✓ | ✗（除非变器侧有热源） | ✗ |
| 盆下普通点燃烈焰人（无搅拌器） | ✓ | ✓ | ✗ |
| 盆下超级加热烈焰人（无搅拌器） | ✓ | ✓ | ✓ |
| 搅拌器 + 超级加热烈焰人 | ✓ | ✓ | ✓ |
| 盆边什么热源都没有、但**变器扫描半径内有点燃的烈焰燃烧室** | ✓ | ✓（普通点燃及以上） | ✓（超级加热） |

即："**只要在盆下面放了烈焰人，就能根据它的状态执行这个盆的搅拌配方**"——无需搅拌器；
**而把烈焰燃烧室摆在变器旁边（半径内）同样成立**：变器读到的热档随波携带，波自带加热能力执行加热配方。

## 4. 机器环境判定（`environmentSatisfied`）

**判定中心（三处，任一满足即通过）**：

1. **命中点**（被加工方块，通常是工作盆本身）
2. **波源**（变器出射面）——玩家会把烈焰人摆在变器旁边，不该因此判"没点着火"
3. **搅拌器所在格**（盆上有搅拌器时）——"搅拌配方只需在搅拌器附近加热"

> 加热一项还多一条**优先于三中心**的来源：波携带的变器热档（`carriedHeat`，见 §3）。
> 变器扫描半径（1~3 格）比三中心的 3×3×3（半径 1）大，故"变器侧有火"在波飞出去几格后依然成立。

**判定内容**：

| 配方类别 | 要求 | 复用谁的口径 |
|---|---|---|
| `ProcessingRecipe.getRequiredHeat() != NONE` | **变器携带的热档**（扫描半径内点燃的烈焰燃烧室）**或**命中点/波源邻域 3×3×3 内有达标烈焰人 | Create `BlazeBurnerBlock.getHeatLevelOf` + `HeatCondition.testBlazeBurner` |
| Vintage `curving`（压弯） | 邻域需有**装了对应头**的压弯机 | 反射读 `itemAsHead` / `mode`，读不到时保守降级为"有压弯机即通过" |
| fan 系（`create:splashing` / `create:haunting` / 本模组 `createoreexpansion:transmuting`） | 邻域需有对应媒介 | Create `FanProcessingType.isValidAt` |

**热档判定（Create 原生语义，字节码实证）**：

```
SUPERHEATED 分支 → 只有 SEETHING 通过
HEATED 分支      → 只要不是 NONE、也不是 SMOULDERING 就通过（FADING / KINDLED / SEETHING）
```

即：**一个超级加热（SEETHING）的烈焰人同时给出"普通加热 + 超级加热"两档**；不需要两个烈焰人，也不需要任何累加规则。

判定异常一律按"环境满足"放行（环境判定不该让波莫名停摆）。

## 5. 优先级：同一输入匹配多条配方时选谁（`orderCandidates`）

| 优先级 | 依据 | 作用域 |
|---|---|---|
| 1 | **批锁** `preferred` | 本次方块命中（一次碰撞处理一"批"）内已选定的配方 |
| 2 | **输入种类 LRU** `lastRecipeByInputKey` | 波实体生命期内（上限 8 条）；该输入种类最近一次成功的配方 |
| 3 | **转速档匹配** `compareCandidates` | Vintage 抛光配方 `speed_limits`（低/中/高）↔ **波加工转速档**；匹配者优先（见下） |
| 4 | **专用度** `compareSpecificity` | 物品输入数**多者**优先 → 流体输入数**多者**优先 → 配方 id **字典序** |

- 第 3 条与 Vintage 自身口径一致：砂带打磨机 `GrinderBlockEntity` 把配方按
  `speed_limits == 当前转速档` 分成**优选桶 / 兜底桶**，优先执行匹配的，一条都不匹配才退化执行不匹配的
  （去混淆字节码核对；档位算法 `getCurrentSpeedMode()`：`停转 → 0；|RPM| ≤ lowSpeedValue（默认 16）→ 1；
  ≤ mediumSpeedValue（默认 64）→ 2；更高 → 3`，阈值取自 Vintage 自己的配置）。
  **所以这是优先级、不是硬门槛**——本模组照此实现：波用携带的**变器转速**算档，匹配者排前面，其余照常可执行。
- 第 4 条**绝不再随机**（旧实现是 `random.nextInt`，导致"铜+锌→黄铜"被"铜→铜板"抢走、"下界合金锭+钻石剑→升级"被"锭→板"抢走）。
- 想强制走"不那么专用"的那条：把目标产物写进工作盆的配方过滤器（闸门在排序之前生效）。

**波加工转速（RPM）的取值（用户 2026-09 拍板）**：**取自变器自身转速**（穿波瞬间写入 `carriedRpm`，
绝对值为准）。变器本就是动能机器、护目镜里已有它的转速，故选它最直观也最好预测
（对比另两种可选口径：按波速换算会引入与 Create 不同源的换算系数；取命中点附近机器转速会让
"这锅料能不能做"取决于旁边恰好摆了哪台机器）。护目镜显示 `波加工转速：N RPM（取自本机转速）`，
Jade 指向波显示 `携带转速: N RPM`。

## 6. 执行顺序（`craftFromSlot`）

```
1. 取槽内物品的 1 个副本作为 probe
2. collectCandidates(probe, pos, handler, slot, containerFluid)   ← §1 全部门槛 + 过滤器闸门
3. orderCandidates(candidates, probe, preferred)                  ← §5 优先级排序
4. 逐条候选（按顺序）：
   a. computeCraftResults(probe, candidate, handler) —— 推不出产物 → 跳过该条，试下一条（不再中断整批）
        · 变形升级 vintageimprovements:auto_upgrade → upgradeResultOf（diamond_* → netherite_*，保留数据组件）
        · 锻造融合 vintageimprovements:auto_smithing → smithingBridgeResult（借原版锻造配方，6 种角色排列暴力匹配 + assemble）
        · 其它 → RecipeApplier.applyRecipeOn（滚结果）；物品结果为空但有流体产物 → 放行
   b. 真取 1 个主料 extractItem(slot, 1)
   c. consumeForCraft：辅料 → 流体 → 电量
        · 辅料 CONTAINER → extractItem 对应槽；PAYLOAD → 从载荷尾部往前扣
        · 流体：容器罐优先，缺口用载荷流体补
        · 电量：邻域储能真取（含特斯拉线圈按需扣），缺口退回载荷电量补齐
   d. rememberCraftLock（写入输入种类 LRU）
   e. 产物回位：productSlotHint（升级/融合类 → **首个辅料所在槽**，普通配方 → 主料槽）
        → 首选槽放不下 → 扫描整个容器找空位/可叠加槽
        → 实在放不下才掉落在方块上方
   f. 流体产物 → 先注入命中方块自身储罐，否则就近容器/储罐
   g. chainLeft--；写轨迹日志；返回本次候选
5. 全部候选都被跳过 → 返回 null（调用方结束本批处理）
```

## 7. 明确"不检查"的东西

| 不检查 | 原因 / 现状 |
|---|---|
| 源机器本体是否存在 | **能力侧要"存在过"**：类型必须在变器扫描半径内读到（§1.1 类型门），拆掉机器后下一发波就不再带该能力；但**执行侧不要求它还在**（波飞到别处加工时不会回头核对那台机器） |
| 命中点附近是否真有那台**状态机** | 状态（切模式 / 装头 / 换磨轮 / 锤下方块）在**变器扫描时**读取并随波携带（§9）；波飞到别处执行时不再回头核对源机器 |
| 机器转速 / 应力 | **转速档已进入候选排序**（§5 第 3 档：Vintage 抛光 `speed_limits` ↔ 波携带的变器转速档）；但**不是硬门槛**——与 Vintage 自身"优选桶→兜底桶"行为一致。机器应力仍不检查。 |
| 搅拌器是否通电 | 当前只认"盆正上方有搅拌器"这个存在性 |
| **热源的位置** | 变器扫描半径内的**任意位置**都算（热档随波携带）；命中点邻域内另有热源同样认——两条来源任一满足即可 |
| 压弯机的朝向/动力 | 只认"装了对应头"（头的种类要匹配，见 §9） |
| **扫描到的设备坐标** | 读数一律只报"读到了什么设备、几台"，**不在护目镜/Jade 里显示方块坐标**（避免提示框被坐标撑爆，也避免把玩家基地布局写进面板） |
| 加创造模式豁免 | 不适用（这不是技能系统） |

## 8. 轨迹日志（排查用）

搜索关键字 `[变体波轨迹]`，每次实际加工最多一行：

```
加工 copper_ingot → 选中 create:mixing/brass_ingot [create:mixing]（候选 2 条，辅料 CONTAINER#1）
 产出 create:brass_ingot×2，需加热 HEATED（命中点 无烈焰人 / 波源 普通加热 / 变器携带 普通加热）
命中 (x,y,z) 无任何可加工候选 → 按撞墙消散；容器内容 [0]oak_log×64, [1]...
加热环境不满足：命中点 (x,y,z) 与波源 (x,y,z) 邻域 3×3×3 内均无达标烈焰人（变器携带热档 = NONE，此处最高热档 = NONE）
工作盆过滤器挡掉候选 ...：其产物不在过滤器内
跳过候选 ... [..]：材料匹配但推不出产物（输入 ...）
```

**变器护目镜 / 波 Jade 读数**（"读到了什么"口径，全部不带坐标）：

| 面板行 | 含义 |
|---|---|
| `读取到加热：普通加热（烈焰燃烧室）` | 扫描半径内点燃的烈焰燃烧室的**最高**热档；无火时 `读取到加热：无（扫描半径内没有点燃的烈焰燃烧室）` |
| `读取到物品容器：N 台（箱子/工作盆/抽屉等）` | 按 `Capabilities.ItemHandler.BLOCK` 统计的**非加工机**容器台数（读到才显示） |
| `读取到流体容器：N 台（储罐/流体抽屉等）` | 按 `Capabilities.FluidHandler.BLOCK` 统计（含其它模组的流体抽屉/储罐，读到才显示） |
| `读取到储能设备：N 台（发电机/蓄电池等，合计 X FE）` | 按 `Capabilities.EnergyStorage.BLOCK` 统计台数与**可读总量**（只读 `getEnergyStored`，不在此处抽电） |
| `波加工转速：N RPM（取自本机转速）` | 波执行配方用的"加工转速"= 变器自身转速（§5 转速档优先级的依据） |
| `已接入加工机：N` / `加工机应力合计：X` | 动能加工机台数与应力（含未注册的启发式识别机） |
| `携带配方类型：N`（按住 Shift 展开） | 波会携带的配方类型清单（热档达普通加热时自动并入 **搅拌**） |
| `辅料载荷 / 流体载荷 / 电量载荷` | 波**真正会带走**的量（穿波瞬间真抽；与上面的"设备台数/可读总量"不是一回事） |
| Jade 指向变体波：`携带加热: 普通加热` | 波自带的热档（服务端运行态，经 Jade 服务端通道下发） |
| Jade 指向变体波：`携带转速: N RPM` | 波自带的加工转速（= 变器转速；转速档优先级依据） |

逐条淘汰原因（全库量级、会刷屏）另由 `CRAFT_DEBUG` 常量控制，默认关闭。

## 9. 状态驱动的加工机（"换头 / 切模式 / 换工作方块 / 换磨轮"这一类）

**结论：有，而且不止一台。** 共同点是——同一台方块，随"装上去的东西"或"切到哪个模式"不同，
**能做的配方整套都变**（机器本身往往只是普通动能方块，状态藏在方块实体字段 / 配方字段 / 下方方块里）。
逐台核到的实现细节如下（括号内是核对依据：方块实体字段、配方字段或 mod 自带 ponder 文案）：

| 机器 | 状态来源（核对依据） | 状态如何改变可用配方 | 变器当前口径 |
|---|---|---|---|
| Vintage **压缩机 / 真空室** `vacuum_chamber` | 方块实体 `boolean mode`（扳手右键切换，ponder：「压缩机有两种工作模式，可以通过扳手右键来切换」） | `mode` = 加压 `pressurizing` / 抽真空 `vacuumizing` 两套；加压配方还可能带 `heat_requirement: heated`（如 硫磺 → 二氧化硫） | **已按状态裁剪**：档案挂 `MachineStateSelector`，扫描时反射读 `mode` 只带当前那一套；加热由 §3 的携带热档满足 |
| Vintage **冲压机** `curving_press` | 方块实体 `public int mode` + `public SmartInventory itemAsHead`；配方字段 `mode`（整数）或 `item_as_head`（物品，如 `minecraft:nether_star`）；ponder：「不同弯折头提供不同配方」 | 装不同的弯折头（凸/凹/V 形/W 形/自定义物）→ 可做的 curving 配方不同 | 类型不细分（都是 `curving`），但**环境判定按头精确比对**：反射读 `itemAsHead`/`mode` 要求装对应头（mode=5 = 自定义物头）；读不到时保守降级为"装了任何头即通过" |
| Vintage **杠杆锤** `helve_hammer` / `helve_hammer_kinetic` | 方块实体 `private int operatingMode` + 字段 `anvilBlock`，由 `updateAnvilState()` 按<b>锤正下方方块</b>推导；护目镜文案 `no_operating_block` = "Place an Anvil or a Smithing Table under the Hammer"；ponder：「模式取决于锤下的方块，有两种选择：铁砧和锻造台」 | 锤下 **铁砧** → `changeMode(1)` 锤击 `hammering`；锤下 **锻造台** → `changeMode(2)` 锻造 `auto_smithing` / `auto_upgrade`；锤下无工作方块 → `changeMode(0)`，`canProcess()` 为 false = **整机不能加工** | **已按状态裁剪**：选择器读锤正下方方块（`AnvilBlock` / `vintageimprovements:anvils` / `custom_hammering_blocks` → 锤击；`minecraft:smithing_table` → 锻造；其它 → **空表 = 该机此刻无加工能力**），判据与该 mod 自身 `updateAnvilState()` 逐条对齐（去混淆字节码核对） |
| Vintage **砂带打磨机** `belt_grinder` | 配方字段 `speed_limits`（1/2/3）；方块实体 `GrinderBlockEntity#getCurrentSpeedMode()`（0 停转 / 1 ≤`lowSpeedValue` / 2 ≤`mediumSpeedValue` / 3 更高，阈值走 Vintage 自己的配置）；护目镜 `not_enough_rpm`；ponder：「有些配方需要特定 RPM：低 ≤16、中 16–64、高 >64」 | 同一台机器，**转速档位**决定优先做哪些 polishing 配方（匹配的进优选桶，一条都不匹配才用兜底桶——**是优先级不是硬门槛**） | **已按优先级实现**（§5 第 3 档）：波用携带的**变器转速**算档，匹配档位的候选排前面；档位算法与阈值与该 mod 完全同源（含其配置项，读不到时退回 16/64 默认值） |
| Vintage **离心机** `centrifuge` | 方块实体 `private int basins`；护目镜 `not_enough_basins` = "Not enough Basins for the Centrifuge to work" | 结构（盆数量）不足则整机不工作；配方类型不变 | 不检查结构；波作为远程执行器直接做 |
| Vintage **激光切割机** `laser` | 配方字段 `energy` / `max_charge_rate`；护目镜 `Energy:` | 需要**电量**（不同配方耗电不同） | 已由 `VintageRecipeEnergy` 读 `energy` 当电量门槛，缺口用波载荷电量补 |
| 本模组 **动力角磨床** `power_angle_grinder` | 方块实体持有的**角磨轮**（`getWheel()` / `getWheelTier()`，等级由物品 tag `grinding_wheels/tier_N` 判定）；`GrinderRecipeTypes` 按等级挂接类型；本机判据 `Math.abs(getSpeed()) < tier.getMinRpm()` 时不加工 | 1 级轮 = 打磨 `grinding`；2 级轮 **+=** 粉碎/研磨（Create `crushing`/`milling`）；3 级轮 **+=** 拆解 `dismantling`；等级还决定**最低转速门槛** | **已登记 + 按状态裁剪**：选择器按实时等级给出全部对应类型（含 3 级轮的拆解），**并在本机转速不足该等级门槛时返回空表**（与角磨床自身判据一致：停转/转速不够的机器此刻不可能加工，波就不该带上它的能力）；未装轮同样空表 |
| Create **鼓风机** `encased_fan` | `FanProcessingType.isValidAt` 检查**风机身后的介质**（水 / 灵魂火 / 火或烈焰燃烧室，按流体与方块 tag） | 介质决定 喷洗 `splashing` / 闹鬼 `haunting` /（原版）烟熏与高炉熔炼 | **已按介质判定**（`nearbyMediaSatisfies`，复用 Create 现成入口） |

**反例（不需要状态选择器）**：CC&A 轧机、Vintage 卷簧机/车床/振动台——只有输入输出仓与计时器，配方完全由输入物品决定；

## 10. 波可执行配方族（`content/charger/family/WaveRecipeFamilies`）

**两段式**：波引擎能执行的配方族全部在这<b>一个文件</b>里可见——

| 族 | 归属 | 执行方式 |
|---|---|---|
| **族 0**：Create `ProcessingRecipe` 族 | 引擎主路径（不在该文件里登记） | `collectCandidates` 全库管线：多输入辅料 / 流体 / 电量 / 加热·介质·机头环境 / 产物推导（锻造融合、变形升级）/ `RecipeApplier` 滚结果 |
| **族 1**：拆解 `dismantling` | `WaveRecipeFamilies` 登记 | 单输入族：族自己做"认领 + 材料判定 + 产物推导"，引擎负责事务（先算产物→再扣主料→回位/掉落） |
| **族 2**：序列装配 `create:sequenced_assembly` | `WaveRecipeFamilies` 登记 | **步骤族**：族给出"当前这一步"的 `ProcessingRecipe`，引擎照走族 0 全套门槛（辅料/流体/电量/环境），族负责推进进度或收尾抽产物 |

**当前登记的族（2 条）**

- **拆解 `dismantling`**（`DismantlingRecipe implements Recipe<SingleRecipeInput>`，单输入；
  产物 = `floor(materialCount × 剩余耐久比)`，耐久耗尽/不足 1 份 → 无产物 → 该候选被跳过且**不消耗**）。
  与角磨床自身共用同一套语义（`DismantlingRecipe#matches / #getResult`），族只做"认领 + 转发"。
- **序列装配 `create:sequenced_assembly`**（`SequencedAssemblyRecipe`）：金板 → 精密构件这类
  **N 步 × 循环 M 次**的装配。算法<b>逐条对齐 Create</b>（它的 `getStep/advance/rollResult` 是 private，
  这里按同一算法重写）：
  - 起步 = 物品命中装配配方的 `ingredient`（金板）；进行中 = 物品带 `create:sequenced_assembly`
    数据组件（中间产物 + `id` + `step` + `progress`），且组件 `id` 必须等于本装配的数据包 id；
  - 当前步骤 = `sequence.get(step % sequence.size()).getRecipe()`——它本身就是一条 `ProcessingRecipe`
    （如 `create:deploying`），且 Create 已把它的 `ingredients[0]` 换成中间产物
    （`SequencedRecipe#initFromSequencedAssembly`），所以<b>辅料（小齿轮/大齿轮/铁粒…）直接由引擎
    从命中容器或波载荷里解析并扣减</b>，族不需要自己扣物品；
  - 推进：`(step+1) / sequence.size() >= loops` → **收尾**，按 `resultPool` 权重抽最终产物；
    否则产出带新进度的中间产物（进度 = `(step+1)/(size*loops)`）；
  - 链式上限 = 波等级：一发波能连推进几步，整条装配（精密构件 = 5×3 = 15 步）需多发波接力。
  - 能力来源：`create:sequenced_assembly` 类型挂在**机械手**（装配核心）+ 压机/锯/注液器上
    （装配线常见的步骤机），变器半径内有其一即可携带该能力。

**接入新族**：在该文件 `static { register(new XxxFamily()); }` 加一行 + 实现 `Family`
（单输入族实现 `typeInfo / accepts / matches / results`；多输入/流体/电量的族<b>覆写
`currentStepRecipe` 返回那一步的 `ProcessingRecipe`</b> 即可，辅料与流体/电量由引擎解析与扣减）。
能力声明侧同步：在 `StellarWaveMachineCatalog` 里把该类型挂到对应机器上
（如 3 级角磨轮 → `dismantling`、机械手 → `sequenced_assembly`）。

**契约边界**：<b>单输入族</b>由引擎给一个"辅料/流体/电量皆空"的 `Candidate`；
<b>步骤族</b>走族 0 的全套门槛。**任何族都不要自己扣物品**，否则"先算产物再消耗"的事务性会被破坏
（波是远程执行器，一次加工必须要么全成要么全不动）。

## 11. 载荷的来源（变器穿波；命中点补料默认**关**）

波携带的载荷（辅料物品 / 流体 / 电量）取自同一实现 `content/charger/entity/WavePayloadGather`，
上限走配置（`wave.maxPayloadItems` / `maxPayloadKinds` / `maxPayloadFluidMb` / `maxPayloadEnergyFe`，
默认 **5 件 / 5 种 / 2000 mB（2 B） / 电量 = CC&A 充电配方里最贵那条的耗电量**）：

| 时机 | 范围 | 谁在用 | 状态 |
|---|---|---|---|
| **穿波瞬间**（变器把原波转成变体波） | 变器的**扫描半径**（1~3 格，随能量场档位） | 变器 `collectPayloadForWave()` | **默认启用**（唯一取料点） |
| **命中目标后**（方块容器或掉落物） | = 变器当时的读取半径（随波携带 `carriedScanRadius`） | 波 `refillPayloadAround()` | **默认关闭**（`wave.refillPayloadOnHit`，见下） |

**命中点补料默认关闭（2026-09-11 用户拍板）**：玩家反馈"包不要这么自作聪明"——前一发包里没有序列加工要用的
东西时，这一发包会自己在命中点周围再抓一次。现在载荷**只在变器穿波那一刻取一次**，取自变器读取半径内的
容器（= 玩家自己摆在变器旁的箱子）；波不在命中点搬东西，包里用完就没了，等下一发波重新带。
要恢复旧行为把 `wave.refillPayloadOnHit` 设为 true 即可（打开时行为仍与变器同口径、节流 5 tick、
**不抽**命中点自身/工作盆/动能机器内部库存）。

**取料顺序（用户 2026-09 明确）**：
1. **先铺种类**：按扫描顺序每种物品各取 1 件（最多 `maxPayloadKinds` 种）——"小齿轮 / 大齿轮 / 铁粒 各 1"；
2. **再补数量**：还没到 `maxPayloadItems` 件时，从"当前剩余存量最多的那种"继续各抽 1 件。
（旧实现是"从第一个槽抽到上限为止"，第一槽放着一组小齿轮时会把 5 个全抽走，
导致多辅料组合永远凑不齐——实测反馈后修正。）

### 取料铁律（"**傻抽**"，禁止需求匹配；用户 2026-09 明确，勿"优化"）

变器处理之后的波，吸收辅料/流体/电量的行为**本身就是非常傻的**：**周围有多少就抽多少，直到抽饱（上限）为止**；
它**不会**根据"这次要做什么加工"来决定抽什么、抽几个。以下方向用户明确否决，不要实现：

- ❌ 按当前配方需要挑辅料 / 只抽"用得上的那几种"；
- ❌ 抽之前先判断"有没有活干""值不值得抽"；
- ❌ 按配方需要的数量精确抽。

唯一存在的"规则" = **容量上限（`[wave] maxPayloadItems=5 件 / maxPayloadKinds=5 种 / maxPayloadFluidMb=2000 mB（2 B）`，
电量 `maxPayloadEnergyFe=-1` 自动 = **CC&A 充电配方里最贵那条的耗电量**（`CreateAdditionTransmuterSupport#maxChargingEnergy`；
未装 CC&A / 无此类配方时回退为不设上限 = 抽干，旧行为））**
＋ **取料顺序（先每种各 1，再从剩余最多的那种补到上限）**
＋ **排除口径（不抽工作盆、正在加工的那个方块、动能机器内部库存）**。
这条原则在代码里也有硬注释：`WavePayloadGather` 的类注释（"设计铁律"一节）。

### 11.0 读数口径：清单 + "n/上限 件 · m/上限 种"（2026-09-11 修正）

Jade 的波提示行曾把物品清单**写死只列前 3 种**（超出补 "…"），于是"箱子里 3 种、每样都很充足"时
玩家读到的是"波一次只能带 3 个物品"（实测反馈），而真实载荷是 5 件 3 种。现在：
清单按配置上限列全（安全上限 8 种），行首给出 `携带物品（n/上限 件 · m/上限 种）`，
与护目镜的"辅料载荷：n 个 / m 种"同一口径。

### 11.1 载荷消散时的去向（2026-09-11 修正，默认：留现场最近的容器）

真抽时 `WavePayloadGather` 会把**实际被抽过的容器/储罐/储能位置**记进 `sources`
（变器 → `Payload.sources()` → 波 `attachPayload(...)`；命中后补料 → `rememberPayloadSources()`，
去重、保留最近 16 个），载荷消散时按"**最新来源优先**"归还：

| 载荷 | 归还顺序 | 都还不上时 |
|---|---|---|
| 物品 | 逐个 `insertItem` 回来源容器（逐槽全扫） | 落在来源方块**上方**（没有来源记录才落回消散点） |
| 流体 | `fill` 回来源储罐 | 就近注入（仍无处可存则浪费） |
| 电量 | `receiveEnergy` 回来源储能 | 就近注入（仍无处可存则浪费） |

**为什么必须改（用户实测反馈）**：旧实现把剩余载荷**爆在消散点**，而波的消散点常常就在它刚加工过的
**工作盆口**上——掉落物被工作盆直接吸进去，表现成"加工金板时，携带的物品也被同时转移进了工作盆里；
消耗了一份产物加工后，原材料却没少"。改成"还回取料容器"后：箱子抽出来没用完的辅料原样回到箱子，
工作盆里只剩玩家自己摆的料与产物（净消耗 = 真正用掉的辅料）。

**2026-09-11 再修正：默认改为"留在加工现场"（`wave.payloadRelease = NEAREST_CONTAINER`）** ——
用户口径："用不完的余料在击中目标方块之后，不返回原来的箱子，而是保存在击中方块周围、
变器所对应范围之内的最近的可保存容器中"。三种口径都在配置里可选：

| `wave.payloadRelease` | 余料去向 |
|---|---|
| `NEAREST_CONTAINER`（默认） | 以**最近加工过的方块**为圆心、**变器读取半径**为范围，按距离由近到远逐个容器试：装满一个接着下一个；**工作盆 / 正在加工的那个方块 / 动能机器内部库存不算可存容器** |
| `SOURCE_CONTAINER` | 还回实际取料的那几个容器（上一版行为，原箱） |
| `DROP_AT_DISSIPATION` | 全部爆落在消散点（最旧的行为） |

三种口径都**不会**把余料放进正在加工的工作盆。现场放不下时（`NEAREST_CONTAINER`）退回原箱，
仍放不下才落在原箱上方——绝不落在击中的那个方块上（避免被工作盆吸走）。
流体/电量同口径：就近注入/充入同一范围内的储罐/储能，放不下再退回原处，最后才"就近尽力而为"。

### 11.2 手持物类配方**照样扣辅料**（2026-09-11 修正）

`create:deploying`（机械手部署）与 `create:item_application`（物品应用）的"第二输入"在实物机械手上是
**手持物**——一台机械手夹着一个齿轮能盖很久，Create 因此不消耗它。旧实现照搬了这条规则
（`isHeldItemRecipe` → 整条辅料扣减直接跳过），后果是：

- 波抓着一份载荷辅料**无限盖章**，箱子里的原料永远不少（"直接也不从箱子里边抽物品，就逮着一个…往机器里加工"）；
- 序列组装（精密构件等 3 步 deploying / 5 循环）变成**无消耗**，
  "消耗了一份产物进行加工后，原材料却没有被消耗"也是同一根因。

**波的语义应当是"物化"而不是"手持"**：波没有手，每一击都得把辅料从容器/载荷里真取出来，
所以 2026-09-11 起默认**照样扣**（`consumeAux` 不再对 `isHeldItemRecipe` 提前 return）。
配置 `wave.consumeHeldItemAux = false` 可回到"手持物免费"的旧口径（会让序列组装变成无消耗，仅供排查）。

**因此序列组装的正确玩法**：箱子/载荷里备好每一步要用的那件辅料（小齿轮 → 大齿轮 → …），
波每推进一步扣 1 件；一件都不备时该步没有候选，本批直接结束（不会空转）。

## 12. 引雷：波携带的强化避雷针"引雷次数"（2026-09-11 修正为真落雷）

用户口径："强化避雷针满了之后波会把它抽取（**只有满的时候才抽**），这时候波就有了一种**引雷**的能力：
它**打中哪个地方，哪个地方就会引雷**。"

| 环节 | 实现 |
|---|---|
| 蓄满 | `ReinforcedLightningRodBlockEntity`：伽马能量波命中 10 次（`MAX_CHARGE = 10`）→ `readyCharges++`；`hasReadyCharge()` 要求**进度满格且有待释放次数** |
| 抽取（**只有满的才抽**） | 变器扫描半径内只收集 `hasReadyCharge()` 的避雷针（`StellarWaveTransmuterBlockEntity#getChargedRodPositions`）；穿过波的瞬间经反射清零该针的进度与次数（`StellarWaveTransmuterPass#drainRodCredit`），带出 1 次引雷机会 |
| 引雷 | 波命中<b>方块或掉落物</b>时调 `StellarWaveEntity#summonLightningAt(命中点)`：消费 1 次、在该处生成一道闪电 |

**为什么"引雷"就够了**：本模组已有**闪电落地统一加工**（`content.lightning.LightningEventHandler`）——
任何闪电落地的首个 tick 会收集**落点周围 1 格**内的输入（掉落物 / 置物台 / 弹射置物台 / 工作盆），
按 `createoreexpansion:lightning`（**多输入配方优先**，含 CC&A 充电配方）与闪电方块配方加工。
所以波只要在命中点落一道雷，闪电加工就**物理地**发生在那里。

**旧实现（已删除）**：在命中的掉落物上"模拟执行一次**单输入**闪电配方"，
代码注释当年写的是"波不引雷、不能远程让避雷针真引雷"——与这条口径正好相反，
且只支持单输入、玩家也看不到雷。

**安全性**：用 `ReinforcedLightningRodEffects#spawnLightning`（**纯视觉**闪电：不点火、不伤害生物、
不生成骷髅陷阱马），但闪电加工照常生效。要"真落雷（会点火）"需另行确认。

**读数**：Jade 的 `引雷次数: n`、护目镜的 `避雷针引雷次数：n` 都补了"满充能才抽取 / 打中哪里就在哪里落雷"的说明。

### 12.1 绝不重复执行：雷负责的配方，波不再自己跑一遍（用户 2026-09 指出）

用户原话："他既然都引来一道闪电了，那么这个时候你觉得他还有必要再给物品执行一次雷击加工配方吗？
这相当于不是重复两遍执行了吗？"

- **旧实现就是这么错的**：`tryLightningCraft` 在命中掉落物上"直接套一遍单输入 lightning 配方"，
  与落雷**重复执行**——已整段删除；
- 现在波的全库管线里**显式排除** `lightning` / `lightning_block`（`allWaveRecipes` + `isLightningRecipe`），
  即波自己**永远不执行**雷击类配方；
- **同类第二处（顺带查出并修掉）**：`LightningEventHandler` 在落点**兼容性地**也会执行 CC&A 的
  `createaddition:charging` 放电配方；而携带电量（FE）的波自己也带这个类型 → 同一件物品会被
  "雷"和"波"各加工一遍。护栏：波**引雷的那次命中**把"雷顺带执行的类型"从自己的类型门里摘掉
  （`StellarWaveEntity#strikeOwnsTypes` → `allowedTypeIds()` 减去
  `StellarWaveMachineIntegrations#strikeHandledTypeIds()`）。

#### 12.1.1 口气澄清（用户 2026-09 明确，勿再混淆）

- **CC&A 的充电 ≠ 本模组的雷电加工**：`createaddition:charging`（特斯拉线圈放电）与
  `createoreexpansion:lightning` / `lightning_block` 是**两套独立机制、两个不同配方类型**。
  上面那条护栏只是"落点顺带执行"引起的碰撞，不代表它们是一回事。
- **本模组的充电加工可以执行 CC&A 的全部充电配方**：类型 `createoreexpansion:charging`
  （应力充能器 / 星辉波变器）＋ `CreateAdditionTransmuterSupport#extraEnergyRecipeTypes`
  （带电波补入 CC&A charging 类型）＋ `ChargingRecipeAssemblyMixin`（CC&A 充电可作序列加工步骤）
  ⇒ 玩家**不需要特斯拉线圈**也能完成这些加工。
- 本模组自己的 `createoreexpansion:charging`（约 160 条 tool_charge 配方）**不在此护栏范围内**，
  照常由波执行。

**分工一句话**：雷 = `lightning` + `lightning_block`（本模组雷击加工）＋ 顺带兼容的 CC&A charging；
波 = 其它所有它携带到的类型（含本模组 charging）；两者在**同一次命中**里不重叠（引雷那次波让位），
每件物品只被加工一遍。

**补一台状态机的做法**（一行注册 + 一个选择器，范式与真空室、杠杆锤、角磨床一致）：

```java
StellarWaveMachineRegistry.register(SomeBlocks.SOME_MACHINE.get())
    .addTypes(TYPE_A, TYPE_B)                       // 静态全集（展示兜底）
    .withSelector((machine, base) -> ...)            // 按实时状态裁剪（见 MachineStateSelector）
    .register();
```
