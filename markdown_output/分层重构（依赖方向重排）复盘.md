# 分层重构（依赖方向重排）复盘

> 本文记录 2026-09-28 那次「把分层判据从『按功能板块』改成『按谁需要谁』」的全过程结论。
> **用途**：AGENTS.md 的预算腾挪目的地（AGENTS.md 只能放索引与红线，长内容搬到这里）。
> 与 `RELEASE.md` 分工：那份写「发什么」，这份写「为什么这样分层、踩过什么」。

## 1. 判据的更换（本次重构的全部意义）

| | 旧判据 | 新判据 |
|---|---|---|
| 一句话 | 这东西**属于哪个功能板块**（矿物 / 波动 / 嬗化） | **谁需要它** |
| 后果 | 嬗化被切出去，而矿物线的东西（工具充能、嬗化剑、星辉石漂浮）**反过来需要它**，但方向被禁 ⇒ 只能造窄契约补丁 ⇒ 需求做不出来 | 凡第一层需要的东西就住第一层，因为第一层是最底层 |

**同一件事在两组内容上各发生了一遍**：

1. **嬗化**：`TransmutationLink`（core 里的 140 行窄契约）就是为了「TRANS 可能不在场」而造的。它让 `JadeTopazBowEventHandler` 只能在运行期**间接**取嬗乱效果、取不到就静默跳过。撤掉它、把嬗化 16 个文件整块并入第一层之后，那 4 处恢复成直连。
2. **应力充能器**：充能器住在第二层，而第一层 `CoeItems` 里 6 处 `ChargingRecipeTools.register(...)` 要让工具/凝能佩可被充能，那 160 条工具充能配方却由第二层产出 ⇒ 第一层的 5 条手写 `sequenced_assembly` 配方被迫引用第二层的 `createoreexpansion:charging` 类型 ⇒ **只装 `coe.jar` 时那 5 条配方整条解析失败**（实测）。

> **可复用的判据**：一个模块的边界**不能按功能命名来切**，要按**依赖方向**切。切错的地方会立刻长出「窄契约补丁」——**补丁出现的密度就是判据错误的度量**。

共同特征：**语法合法、编译通过、关卡全绿，但运行期是坏的**。每一次都只能靠「扰动」或「真跑」发现。

| # | 事件 | 为什么全绿 | 怎么发现的 |
|---|---|---|---|
| 1 | `check-skill-render-coverage` 被**注释掉的** `register(...)` 骗过 | 正则匹配到了注释里的调用 | 控制扰动：注释掉一行 ⇒ 必须变红 |

| 4 | `check-module-selfsufficiency` 剥注释顺序错：**行注释里的 `/*`** 与后面的 `*/` 配对，吞掉中间真实代码 | 删掉的是"看不见的"代码 | 修好剥离顺序后审计「被漏读的量」：**`CreateOreExpansionDatagen.gather()` 主体 3081 B 此前不可见** |

**结论**：可靠的验证方式不是「跑通了」，而是「**我把它弄坏，它必须报错**」。上面 6 例中有 4 例是被"扰动必须变红"这条纪律抓出来的。

## 7. 勘误与过程教训

### 7.1 `6e82fdb1` 的提交信息与内容不符（父代理误操作，已披露）
该提交本意**只修一行注释日期**，实际装了 **78 个文件** = 1 行日期修复 + **77 个 `cews`→`coe` 重命名**（由另一个正在工作的代理用 `git mv` 暂存）。77 条全部是 `R100`（**内容逐字节相同，无损坏**），构成 = 71 个应力充能器资源（贴图 47 + 模型 24）+ 6 个机壳贴图。

- **根因**：`git add <单个文件>` 之后执行 `git commit` —— **`git commit` 提交的是整个暂存区**，而并发的另一个代理已经用 `git mv` 把它的改动暂存好了。
- **正确做法（并发工作时）**：`git commit -- <pathspec>`（只提交点名的路径），或者提交前先 `git diff --cached --name-only` 确认暂存区里只有自己要的东西。
- **未修历史**：改写 `HEAD~1` 需要 rebase，而当时工作树有 7 个在飞的文件，rebase 要求干净树 ⇒ 选择**记录**而不是**重写**；更正写进了后续提交的信息里。

### 7.2 注释日期错（11 处 / 6 文件，已修）
多轮代理在**永久注释**里写下了未来日期：`2026-09-30`（9 处）与 `2026-09-29`（2 处），而当时是 `2026-09-28`。真实日期由**承载该改动的提交日期**定：W6-b2 = 09-27 22:35、W6-d = 09-27 23:35、W9 = 09-28。
**教训**：本工程靠「带日期的裁定」编码决策史（`用户 2026-09-14 裁定` 之类），**日期一旦系统性偏移，这份历史就不可信**。而"两个不同代理写出两个不同的未来日期"这个现象本身就说明**"今天"在两边的上下文里都不准**。

### 7.3 一条更一般的观察
本工程最贵的一类缺陷是「**全绿但坏掉**」（见 §2 的六例），而本次又出现两个**同类但不同形**的：
- **卡关卡的**：`check-module-selfsufficiency` 的剥注释顺序吞掉 3081 B 真实代码；
- **卡记录的**：提交信息说"修日期"而实际装了 77 个文件。

两者都是**"叙述与事实分家"**：一个让工具少看，一个让历史说错话。**唯一的防线是独立复核**——用另一条路径去量同一件事（例如：用 `git show --stat` 量提交，而不是相信它的信息；用 `git ls-files` 量资源，而不是相信报告）。

### 7.4 勘误：一次「被过度解读的中途态」（父代理核实后纠正）
新关卡交付报告里断言：「中途真实存在过一个**只有本关卡能看见**的缺陷——`cews` 的机器模型引用 `coe` 的 3 张机壳贴图、而机壳方块还在 cews ⇒ 单装 `cews.jar` 丢 3 张贴图（`illegal=110` 站点 / 72 去重）」。

**父代理逐条核实后判定：这句话不成立。**

- **`9987f132` 那一刻 `cews` 的 `mods.toml` 已经声明 `createoreexpansion` = `required`**（实测：`modId = "createoreexpansion"` / `type = "required"`）⇒ `cews → coe` 的资产引用**本来就是合法方向**，不该判红。
- 「单装 `cews.jar` 丢贴图」**在机制上不可能**：只装 cews 会被 FML 在加载期拒载（COE 是 required 依赖）。
- 那 110 / 72 条**正是本条关卡旧版判据的假阳性**（不识别依赖方向），也就是父代理当时请它去修的那一类。
- 那一刻的真实资源分布（实测）：机壳的 blockstate / 模型 / 战利品表 / `create:casing` 标签**都还在 cews**，只有 6 张机壳**贴图**已进 coe —— 也就是说中途态**不完整但不损坏**：`cews → coe` 的引用有 required 依赖许可，玩任何组合都不会缺文件。

**⇒ 可复用的教训**：**新关卡的第一次输出不能直接当结论**——要先问「这个数字是**旧判据**还是**新判据**算出来的」。同一份报告里既有旧判据的历史读数（110/72）又有新判据的当前读数（`illegal=0 legal-cross=110`），**两者混在一起就会造出一个从未存在过的缺陷**。这也是本工程第七次「叙述与事实分家」，只不过这次出错的是**对人说的话**，而不是代码或工具。

## 8. 跨层数据引用扫描（观测型，2026-09-28）

**为什么要「先观测、后断言」**：本工程已两次吃过「**永久红的关卡会被学会忽略**」的亏（`check-package-heritage` 最终降级成报告型；资产归属关卡 A1 第一版因不认识依赖方向而永久红）。所以这一半的落地顺序是：**先只报告**（载体覆盖率、`UNINDEXED`、跨模块引用分布），跑够几轮再把归属断言加上。

**工具**：`tools/check-data-attribution.ps1`。**它的 exit 语义刻意收窄到一件事**：只有 **23 条反空转守护**能判红——它的作用是发现「**扫描器快瞎了**」，而不是判断归属。`UNINDEXED`、悬空引用、跨模块方向一律只报告。

**实测（576 个 data JSON / 1529 条本命名空间引用）**：
- 载体 **11 类**，各有覆盖率与反空转下限；两路索引并集 **645** 个 id（产物反推 159 + 数据定义产物 457 + Java 注册调用字面量 167）。
- ★ **跨模块（引用方 ≠ 拥有方）的引用对 = 0** ⇒ 所有本命名空间数据引用都在**引用方模块内部**被满足；P7c/P7d 的按层改道**没有留下跨层数据边**。**这一条就是将来升级成归属断言时的 U1 起点**（它今天已经是绿的）。
- `UNINDEXED` 只有 **2 条**：`flowing_transmutation_fluid`（Registrate 从 `.fluid(...)` 派生的后缀，**永久 UNINDEXED**）；`energy_sensing_lamp`（**判定为真悬空**——方块已下架、Java 里 0 个字面量、唯一引用是 `core/.../tags/block/machines_light.json` 里 `"required": false` 的 tag 条目，游戏静默忽略）。
- 唯一「同 id 两提供者」：`#createoreexpansion:machines_heavy`（coe 的角磨床 + cews 两个调节器）⇒ **合法跨层拆半**，但会让 `owner(X)` 变成集合，**升级判据必须显式处理**。

**三条可复用的经验**：
1. **不按 key 白名单提取引用**：只认 `values` 里裸字符串的写法会漏掉**对象形式**的 tag 条目（`{"id": "...", "required": false}`）——而 `energy_sensing_lamp` 那条正是这样被漏掉的。
2. **调用形状规则要覆盖「字面量不在第一个实参」**：`AllStructureProcessors.register(event, "bastion_treasure_sapphire", CODEC)` 被第一版漏掉，而它真被 worldgen 引用；补上后 `UNINDEXED` 从 3 降到 2。
3. **别把「id 形字面量」一律索引**：`modLoc("L")` / `fromNamespaceAndPath(ns, "L")` 多是模型/贴图/tag/JEI UID 路径而**不是注册表条目**，索引它们等于用假覆盖把 `UNINDEXED` 冲小。把「不扫」也打印成计数，它对读者才是可度量的。

**两条 PowerShell 陷阱（都会「看起来在工作其实没工作」）**：
- `@($list | Group-Object a,b).Count` 会**静默变成 1**（`Group-Object` 退化成单个无名组）；`@($list).Count` 对泛型 List 直接抛 `Argument types do not match`。**先赋变量再读 `.Count`。**
- `$script:OutFile = ''` 会**清空绑定的 `-OutFile` 参数本身** ⇒ 静默不写任何文件（实测 `bound=[OutFile] param=[]`）。内部接收变量必须改名。
