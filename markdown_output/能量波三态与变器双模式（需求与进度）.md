# 能量波三态化 + 变器双处理模式（需求与实现进度）

> 2026-09-13 用户提出并逐条定稿。**这是需求与进度的唯一权威记录**，接手时先读这一份。
> 实现进度用 ✅/🔄/⏳ 标注；每步都必须 `compileJava` 退出码 0 收尾并跑 `runData` + `jar`。

## 0. 一句话

把"能量波既打人又加工"的单一行为，拆成**三种状态**（普通态 / 变体态·全能态 / 攻击态），
并给星辉波变器加**两档处理模式**（加工波变态 / 攻击波变态）。

---

## 1. 三种状态的职责（用户 2026-09-13 定稿，逐条不可自行"优化"）

| 状态 | 充能加工（`createoreexpansion:charging`） | 读机器 → 远程加工 | 对生物伤害 | 颜色/特效 |
|---|---|---|---|---|
| `NORMAL` 普通态 | ✅ **唯一会做的**（"废物"，此外什么都没有） | ❌ | ❌ | 保持原样 |
| `OMNI` 变体态／全能态 | ❌ | ✅ 全保留：扫描携带 / 候选门槛 / 链式 / 引雷 / 载荷 | ❌ | **保留原色调**，拖尾改"机械感" |
| `ATTACK` 攻击态 | ❌ | ❌（**纯攻击**） | ✅ 伤害值沿用原普通波公式 `WaveLevels.damage(waveLevel)` | 拖尾改红色伤害感 |

**铁律：一个波一生只能改变一次状态。** 非 `NORMAL` 即"已定型"（`WaveState#isLocked()`），
此后任何场 / 变器都不再改动它。由此自动得到两条：

- 攻击波飞过"加工波变态"变器 → **不会**变成全能态；
- 全能态飞过"攻击波变态"的场 → **不会**获得伤害。

**不动的东西**：波与波湮灭（`triggerWobBoom`/`triggerBoom`）及其对生物/实体的伤害，
与状态无关，保持原样（用户明确）。

## 2. 变器两种处理模式与交互分工（用户 2026-09-13 定稿）

### 2.1 交互分工

| 操作 | 行为 |
|---|---|
| **空手右键** | 切换**该面波口开关**——侧面与**顶面（灯盘面）**都能切；灯盘面的 4 分区点击逻辑复用现有实现（与差波器 `sideForShellClick` 同一套口径），**不要复制粘贴** |
| **扳手右键** | **只有一件事：切换处理模式**（加工波变态 ↔ 攻击波变态）。**不再负责旋转朝向**（原先 `onWrenched` 的面开关/转向语义整体让位给空手） |

模式需**存档持久化**，并在**护目镜与 Jade** 显示为「加工波变态 / 攻击波变态」。

### 2.2 加工波变态（`PROCESSING`）

现有行为：波**穿过**变器时被转换成变体波（= `StellarWaveEntity` = 全能态），
几何判定（开口/对面/竖直撞击 → HIT_WALL/BOUNCED/CONVERTED）保持不变。

### 2.3 攻击波变态（`ATTACK`）

- **波直接穿过去**（不发转换；面的开关也不拦波，视为透明）。
- 以变器为中心、半径 = **该变器自己的读取半径**（`scanRadius`，即"加工波变态读取机器"的那个范围），
  把范围内**仍为普通态**的波**点燃成 `ATTACK`**（一次性，保持到消散；离开半径不恢复）。

### 2.4 攻击态的碰撞口径（用户 2026-09-13 定稿）

| 命中对象 | 行为 |
|---|---|
| 生物 | **造成伤害** + 绽放消散（沿用原普通波攻击表现） |
| 带物品槽方块（置物台/工作盆…） | **按撞墙消散**（不加工） |
| 掉落物 | **无视**，继续飞 |
| 普通方块 | 按撞墙消散（原逻辑） |

## 9. 全能波 × 星辉石应力充能器（新增机制）

- 全能波（变体态）**本身没有充能加工**。
- 但若**变器的读取半径之内**存在一台**星辉石应力充能器**，且其侧面已设定"发射能量波的等级"（手动 1~5 档，
  见 `StellarstoneChargerLevelSlot` / `StellarstoneStressChargerBlockEntity`），则该全能波**也能进行充能加工**。
- 此时充能加工的**波级 = 那台星辉石充能器设定的发射等级**，**与该波变体化之前的等级无关**。
- 待定（Q3）：半径内有多台时取哪一台。

## 15. 本轮我做的工程判断（代码层，无需用户拍板）

**字段初始化器之前**就可能被调用（对象还没构造完、对象字段全是 null）。上一版把"瞬移断点"写成
`wavePath.markLiveBreak()`，于是任何充能器发射第一只波就 NPE（本次是蓝宝石充能器 tick 发射）。

**改法**：把状态挪回波实体自己的**原始类型字段**，`WavePath` 只被"构造完成之后"的代码触碰。
- `WavePath`：删 `markLiveBreak()` 与内部 `liveBroken`；改为 `push(point, breakBefore)` +
  `crosses(box, live, liveBroken)`（断点由调用方传参）。
- `AbstractChargerWaveEntity`：新增 `private boolean pathBroken`（构造期有默认值 false，安全），
  `setPos` 里**只许碰原始类型**——这条约束已写进字段与方法的 javadoc（含崩溃报告文件名）。

**重跑验证**（脚本时序同时改成与真实代码一致：观测发生在两次采样之间，真正压到"实时段"这条路径）：
3 万条随机弹道 / 38 万次观测 → 旧为真而新为假 = **0**（不回归）、补漏 2611、节拍 1~5 漏报/误报全 0、
节拍 6 起漏报 → **PASS**。并修正上限口径：最坏观测时机（观测恰落在采样之后）上限 = **4**，
常规时机上限 = 5，clamped 取最坏的 4。

**教训（重要）**：`compileJava` / `runData` 都**不构造波实体**，所以"构造期"这一类缺陷静态验证
一律抓不到——能抓到它的只有真跑一遍。这正是首次实测的价值；后续凡是"覆写父类生命周期回调"的改动，
都要先问一句"这方法会不会在构造期被调用"。

### 23.2 【我方缺陷】储存模式"改了档位后第一发还是旧档"（用户实测）

**现象（用户原话）**："在储存模式下，第一次发射还是原来的波形，第二次发射才是改进后的波形。"

**根因**（唯一能对得上"第一次旧、第二次新"的机制，代码层面已确认）：
两种充能器的储存模式都只在 `onChargeComplete()`（攒层那一刻）**抄一份档位**到 `storedLevel`，
而 `releaseOneLayer()` 用的是这份副本：

| 机器 | 档位来源 | 抄写时机 |
|---|---|---|
| 蓝宝石应力充能器 | 转速档（blockstate `MODE`，`getModeForSpeed()` 每 tick 刷新） | 每次充能完成时 |
| 星辉石应力充能器 | **手动等级槽**（`getManualLevel()`） | 同上 |

于是"调好档位 → 立刻释放"用的还是调之前那一发；等下一次充能攒满、`storedLevel` 被刷新，
**第二发**才跟上——与用户描述逐字吻合。同一台机器的**普通模式**没有这个问题：`launchWave()` 每发都读当前 `MODE`。
**两种模式对"波级从哪来"给出两个答案 = 缺陷**，不是设计。

**改法**（口径只有一处：`AbstractCreateChargerBlockEntity#resolveReleaseLevel(int rememberedLevel)`）：

1. **有应力**（`MODE` 有效）→ 释放一律取**当前档位**（与普通模式一致）；
2. **停转**（`MODE = 0`）→ 才回落到"最后一次有效档位"，否则囤的层数在停转/大退重开后会一发都放不出来；
   两者都无效（新机器/坏数据）→ `WaveLevels.GAMMA` 兜底。

**两机各自的"回落值"来源不同，各有理由**：
- 蓝宝石：转速=0 时没有别的档位信息可读 → 保留 `storedLevel`（攒层时记录，NBT 键 `StoredLevel` 不变）；
- 星辉石：等级是**持久的手动设置**（等级槽），任何时刻都读得到 → 直接用 `getManualLevel()` 做回落值，
  于是该机的 `storedLevel` 字段与 `StoredLevel` 键**整体删除**（老档里的旧键留着不影响读档）。

> ⚠ **可由用户推翻的取舍**：原注释写的是"每层记它充能当时的等级"（其实没真正实现——层数只是个计数、
> 界面上只显示 `充能层数：x/y`，玩家无从预期哪层是哪级）。本次改为**跟随当前档位**、与普通模式对齐。
> 若用户要的其实是"每层各记各的等级"（需要把层数改成等级队列 + 护目镜逐层显示），一句话即可改回。

## 24. 第八批：波口规则的机器本地化 + 波波碰撞口径核实（2026-09-14 深夜）

### 24.1 【我方缺陷·已修】"4 个开口默认是开的、4 个灯也都是亮的、用手点是关不掉的"

**用户报告**（变器切到攻击态后观察到的）。**读代码的结论**：攻击态本身**不碰** blockstate、
也不碰交互——`TransmuterMode.ATTACK` 只做两件事（对波透明 `onWaveHit` + 攻击场 `applyField`），
`cycleMode()` 也只写 BE 字段。全仓对那 4 个开口属性的**写入点只有 1 处**
（`toggleWavePort` 里的 `level.setBlock`），所以"切了模式就点不掉"这个因果不成立。

**真因（与模式无关，是**取向**相关）**：`StellarWaveTransmuterBlock#isOpenable` 的口径是
**"世界水平方向"**：

```java
public static boolean isOpenable(Direction worldSide) {
    return worldSide != null && worldSide.getAxis().isHorizontal();   // ← 旧实现
}
```

而本机是**六向放置**的（`FACING` 可取 6 个方向），**它自己的 4 个侧面朝哪四个世界方向会随 FACING 一起转**。
躺倒放置（FACING 水平）时，4 个侧面里有 2 个朝**上/下** → 这 2 个口按旧口径"不可开"：

- 它们的 blockstate 默认值仍是 `true`（模型显示"开"、灯亮）——**显示与规则不一致**；
- 空手点它们 → `isOpenable` 为假 → `toggleWavePort` 直接 `return SUCCESS`（静默无反应）→ **"点不掉"**；
- 灯盘面的 4 分区里也有 2 个分区落在这些方向（`MachineFaceQuadrants` 按 FACING 选平面，
  躺倒时分区落在含竖直分量的平面上）→ 那两块灯位点了同样没反应。

**改法（口径落在机器自己的侧面上，与差波器一致）**：

```java
public static boolean isOpenable(BlockState state, Direction worldSide) {
    return state != null && state.getBlock() instanceof StellarWaveTransmuterBlock
        && modelFaceOf(state.getValue(FACING), worldSide) != null;   // 能在模型上找到侧面 → 可开
}
```

- 差波器 {@code EnergyWaveDisperserBlock} 的开关**从来就没有**这道"世界水平"限制
  （它直接按模型侧面切），变器复用的正是它那张世界方向↔模型侧面的表 → 两机口径现在一致；
- **正立/倒置机器逐项零变化**（FACING=UP/DOWN 时模型 4 侧面正对世界 4 个水平方向，
  灯盘面/轴口面在模型上本来就没有侧面对应）；
- **波判定零变化**：波只水平入射（`tryConvert` 先按 `|movement.y| > 0.2` 判墙），
  对这些方向新旧口径结论相同；唯一差别是"躺倒机器的灯盘面/轴口面"这两类方向——
  旧口径先按水平放行、再在 `propertyForWorld` 返回 null 而判关闭，新口径直接判关闭，**结论一致**；
- 顺带把 `isOpen` / `propertyForWorld` / `toggleWavePort` 三处的重复判定收敛成
  **`propertyForWorld` 一处**（返回 null = 该方向在模型上没有波口）。

### 24.2 【核实：已是用户口径，未改玩法】波波碰撞

用户口径："任意两列波（不管波级），只要发生碰撞，就会产生爆炸效果或其他类型的影响。"

**核实结果：现行实现就是这条**（`AbstractChargerWaveEntity#handleWaveCollision`，
调用点在同一 tick 的**实体碰撞优先**分支，早于掉落物/方块判定）：

| 项 | 现行口径 |
|---|---|
| 触发条件 | 两波碰撞盒相交（波体积 0.2³，查询框再外扩 0.4）→ **与波级、波型、电荷完全无关**（设计文档 §1 早已写明"与状态无关，保持原样（用户明确）"） |
| 爆炸等级 | `min(两波等级)` |
| 范围 | 以碰撞点为中心、**水平正方形**（半径 = 爆炸等级：1→3×3 … 5→11×11），**不破坏地形** |
| 生物 | 受 `WaveLevels.damage(爆炸等级)` 伤害（α4 / β6 / γ8 / ε10 / ω12） |
| 掉落物 / 置物台物品 | **按该等级直接执行充能加工**（`ChargerWaveProcessor`） |
| 声光 | `30 + 25×等级` 颗主粒子（55/80/105/130/155）+ 第二色半数 + 风格点缀 + 原版爆炸音效 |
| 结局 | 两波**相互湮灭**（`collided` 标记防同 tick 重复触发） |

**几何安全性核实**（防止"高速对穿而不触发"）：最高波速 12 格/秒 = 0.6 格/tick，两波对撞的
相对位移 ≤ 1.2 格/tick，而判定窗口（每轴 0.6 格）要求步长 < 2×窗口 = 1.2 格/tick →
**数学上不可能一步跨过**，正面/斜向/垂直相交都必然被某一 tick 采到。

**本轮唯一改动是"让它可被证实"**：碰撞时补一行轨迹日志（`[变体波轨迹] 波波碰撞：…`），
粒子数走新增的 `ChargerWaveFx.boomParticleCount(int)`（**唯一算式**，日志里的数与真实发出的数
不可能分叉）。**玩法一行未改**——是否要改（等级和/更高者/额外效果）见 §24.3。

### 28.3 「动态」这一条：查询仪原来其实是定格快照

### B. 转速分档的唯一实现：`util/SpeedBands`（2026-09-25 定稿）

- **攻击场三档 = 转速线性分档**（用户 2026-09-25 规格，分界已当面确认为**区间三等分**）：`TransmuterMode#attackTier(float speed)` 是唯一实现（`t = clamp((|speed| − 128) / (256 − 128), 0, 1)`，档 = `clamp(floor(t × 3), 0, 2)` → **128–170.67 档一 / 170.67–213.33 档二 / ≥213.33（含 256 以上）档三**）；`attackFieldRadius(speed)` 是它的别名（档位序号就是半径：0/1/2）。三个常量 `ATTACK_MINIMUM_RPM=128` / `ATTACK_MAXIMUM_RPM=256` / `ATTACK_TIER_COUNT=3` 在 `TransmuterMode` 里各只有一份，**显示层一个新数字都不写**（区间两端由 `minimumRpm()` + `attackTierCeilingRpm()` 自报）。档一 = **场盒就是机器本体**（波必须真的穿过这台机器），档二 = 半径 1 的立方体，档三 = 半径 2。**攻击场半径因此不再取能量场 `scanRadius`**；`applyField` 签名已改为 `(Level, BlockPos, float speed)`，BE 只递 `getSpeed()`。
- **转速分档一律走 `util/SpeedBands`（唯一实现，别再写内联三元 + 魔法数字）**（用户 2026-09-25 原则："转速的相关调整区间代码…不要使用硬编码…不能直接套用之前别人写过的其他机器的代码"）：一张表同时回答"第几档 / 该档下限·上限 RPM / 该档对应的值"，**判定与显示共用同一个对象**。工厂 `linear(min,max,count,baseValue)`（等分）与 `of(lowers,values[,topRpm])`（散阈值）；查询 `indexAt`（内部取 `Math.abs`，两端夹紧）、`valueAt`、`valueOfIndex`、`lowerRpm/upperRpm`、`topRpm`、`count`；`SpeedBands.formatRpm` 是全模组转速文案的唯一格式化（`%.1f` 去掉多余 `.0`，`Locale.ROOT`）。非法表构造即抛 `IllegalArgumentException`（刻意不静默纠正）。两处消费者：`TransmuterMode.ATTACK_TIERS = linear(128,256,3,0)`（档值 = 场盒半径；`attackTierCeilingRpm()` = `topRpm()`、`MIN_FIELD_RADIUS` = `valueOfIndex(0)`，都是派生而非再抄一份）与 `StellarWaveTransmuterBlockEntity.FIELD_RADIUS_BANDS = of({0,128},{2,3})`（取代原先那句抄自蓝宝石场控的 `speed >= 0 ? (speed >= 128 ? 3 : 2) : 2`；`fieldControllerSpeed` 成功时**本就返回 `Math.abs(...)`**，所以 `speed < 0` 只是"解析失败哨兵 −1"，改成读表后**行为零变化**，方法里保留了显式分支+注释，别再误读成转向语义——本会话我已误读过一次）。
- **RPM 一律整数，且量化只能"向上取整"**（用户 2026-09-25："把那个转速调成整数RPM，不要用小数了"）：`SpeedBands` 的档位下限全部量化成整数——`linear(...)` 用 `Math.ceil`、充能器专用的 `equalSteps(min,max,count,base)`（= 把 `[min,max)` 等分 `count−1` 段再追加一档 `≥max`，末档无上界）也是 ceil；闭区间上界由 `upperInclusiveRpm(i)`（= 下一档下限 − 1）给出，显示因此是 `128~170 / 171~213 / ≥214` 这种整数闭区间。**必须 ceil 而不是 round/floor**：对整数转速 `s` 与实数边界 `b` 有 `s ≥ ceil(b) ⟺ s ≥ b`，ceil 是唯一能保证"**每个整数转速的归档与量化前逐点相同**"的取整；`round` 会把 `213.33 → 213`，让 213 RPM 从第二档挪进第三档（攻击场半径 1→2，直接改玩法）——本会话代理先用 round，靠 `build/patch/ChargerBandCheck.java`（对 `max∈{64,128,256,512,1024}` 逐整数转速比对，含边界 ±2 与正负号）查出这一处，改 ceil 后输出 `identical everywhere (integer rpm)`。**改动分档公式后请重跑该取证程序**（用 `javac -sourcepath src/main/java` 编译，直接验生产源文件）。非整数转速（齿轮比带小数才有）在边界附近 <1 RPM 的一小段仍会换档，这是整数口径的必然结果。
- **充能器的转速档位也走 `SpeedBands`（第二个消费者）**：`AbstractCreateChargerBlockEntity#createSpeedTierBands(int max)` 是每台机器档位表的唯一来源（基线 = 翡翠三档 `equalSteps(1,max,3,1)`；蓝宝石覆写为 `equalSteps(1,max,5,1)`；**星辉石返回 `null`** = 档位与转速无关，护目镜退回"单行 `getStateName` + `getGoggleColor`"老路，行为文案一字未动）。表按 `max` 缓存、配置改了重建。判定 `getModeForSpeed()` 与显示区间读的是**同一张表**——蓝宝石原先"`getModeForSpeed` 一个 floor 公式 + 私有 `tierLo/tierHi` 又一个"的重复已删除（那是同一套边界写两遍，`max=65/255/257` 时旧**显示**与旧**判定**差一格，新实现顺手对齐了显示、判定未变）。`max` 取自 Create 配置 `AllConfigs.server().kinetics.maxRotationSpeed`（默认 256）。
