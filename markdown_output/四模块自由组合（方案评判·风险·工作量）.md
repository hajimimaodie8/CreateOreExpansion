## 0. 结论先行

| # | 问题 | 结论 |
|---|---|---|
| 1 | 三个分层是否独立成"新小模组"让玩家自由搭配？ | **要独立成 3 个独立 jar，但不要拆成 3 个仓库/工作区** —— 用**同一仓库 + Gradle 多模块**出 4 个 jar。玩家侧的自由搭配只取决于"发布的是 4 个 jar"，与仓库怎么组织无关。**并且：先照航空学的模型做（§8 实证）——一个仓库 + 每个分层一个子模块 + 一个独立的 `-bundled` 便利包**；"真·自由搭配"（软依赖 + 降级路径）留作第二阶段。 |

| 4 | 变化学强依赖矿物扩展 | **同意**，且它是最该**第一个**拆出去的一层（现在只有 4 文件 / 277 行，是验证整条流水线的最佳试验田）；但它的**内容本身还不完善**，建议先补内容、后拆分。 |

## 2. 两个直接问题的正式回答

### 2.1 "3 个独立工作区"？—— 不推荐拆仓库，推荐"一个仓库 + 4 个 Gradle 子模块"

**为什么不拆成 3 个 git 仓库**：

1. **共享代码量很大且会继续长**：注册器基类、材料/标签口径（`SeriesTraits`）、
   `util/*`（`GoggleUtil`/`SpeedBands`/`RadiusScan`）、`compat/*` 隔离范式、datagen 规范、
   语言键规范——这些是"四层都要用"的东西。拆仓库后它们要么各自复制一份（口径必然漂移，
   本仓已经有"同一套边界写两遍"的教训），要么再开第 5 个库仓库（等于现在的多模块方案，但多了 5 个仓库的同步成本）。
2. **一次接口调整要开 4 个 PR / 4 次版本发布**：本仓的迭代节奏是"一次会话改十几处"，
   拆仓库会把每次跨层改动变成发布流程。
3. **玩家侧完全无差别**：玩家下载的是 jar，不是仓库。4 个 jar 由同一个多模块构建产出即可。
4. **版本一致性**：4 个 jar 的兼容矩阵（谁配谁）在单仓库里靠 Gradle 版本一致性天然守住，
   拆仓库就得靠人工维护"1.2.3 只能配 1.2.x"。

**什么时候才该拆仓库**：四层由不同人/不同发布节奏维护，或你要把某一层**开源出去独立运营**。
那时至少需要一个 `coe-api` 公共库，否则每一层都要复刻材料与注册基类。

**结论**：`settings.gradle` 加 4 个 `include`，每层一个子项目 → 各自 `jar` 产物；
主 jar 不再 `jarJar` 这些内容层（JarJar 只留给 skiller 这种"必须随行"的库）。

### 2.2 Skiller 内置 vs 独立成新模组

| 方案 | 评价 |
|---|---|
| **JarJar 内置进矿物扩展**（推荐） | 它是**运行时库**（无方块/物品/配方内容）、是**实现细节**，玩家不该看到"要不要装技能内核"这个选项；技能玩法属于矿物扩展。JarJar 天然满足"随父 jar 走、不可单独卸载"。 |
| 独立成第 4 个可下载模组 | 只有一种情况成立：**你希望玩家能"关掉技能"**。但技能是矿物线的核心玩法（9 个技能全挂在工具上），关掉技能会让工具线残缺 → 体验上是"半个模组"，不推荐。 |
| 独立成**不发布的库子模块** | 若将来 CEWS/变化学也要用技能，就把它降级为共享库模块（`api`/`implementation` 依赖），但**只在矿物扩展里 JarJar 一次**（多处 JarJar 同一库会有重复类与类加载冲突风险），别层通过**可选依赖 + 桥接接口**使用。 |

**注意**：JarJar 的语义是"打进父 jar"，所以"Skiller 是否由玩家自由选择"这个命题**本身不成立**——
它不是一个可选项，而是矿物扩展的实现细节。这与你的规划一致。

## 3. 逐条评判你的三条规划

### 3.1 Skiller → 矿物扩展（同意）

- 保持 `mod id = skiller`、注册命名空间不变（它注册的三类 `skill`/`skill_context_factory`/`skill_resource`
  都在自己的命名空间下，与本模组不冲突）；
- 本模组的技能**数据组件 id 与 NBT 格式不变**（`createoreexpansion:skills`），所以老存档无感——
  这一点 `AGENTS.md` 已记（"老存档天然兼容"）；
- 唯一要守的是那条既有纪律：**Skiller 的 fork 补丁不能丢**（`build/patch/skiller-coe-embed.patch`，
  升级上游要重放）。

### 3.2 能量波阵学 = 新数据包 + 继承类 + 换材质（**这一条要改写**）

**(a) "检测到矿物扩展就自动继承它的类" —— 做不到。**
独立 jar 之间是**类加载器隔离 + 编译期互不可见**。正确形态是三件套：
`compileOnly` 依赖（编译期看得见）+ 运行期 `ModList.isLoaded("createoreexpansion")` 分支 +
**桥接接口**（本仓 `SableBridges`／`SableBridges.get()` 返回 null 的范式，直接照搬即可）。
本仓对可选模组已经有两年的成熟做法（"绝不直接 import 可选模组类"），把这套用在自家模块上就行。

**(b) "创建一个新数据包解决配方" —— 可以，但要选形态。**
两条路，都可行：
1. **两套配方**：`..._standalone.json` / `..._stellar.json`，各自带
   `neoforge:mod_loaded` 条件 → 装谁用谁，永不共存（**推荐**：一目了然，好排查）；
2. **一套配方 + 材料用标签**：配方写标签（如 `#createoreexpansion:charger_casing`），
   标签内容按是否装矿物扩展变化 → 数据更省，但"同一个配方在不同环境表现不同"，排查时更容易懵。

**(c) "把机器材质也换成安山岩+黄铜" —— 数据包做不到。**
贴图/模型是**资源**（resource pack 层），资源包没有"按模组存在与否切换"的机制；
而**同一个 block id 只能有一个 blockstate 文件**。可行的三种做法（成本递增）：

| 做法 | 机制 | 成本 | 副作用 |
|---|---|---|---|
| **(A) 双模型变体 + 布尔 blockstate 属性** | JSON 里同时写两套模型（属性 `true/false`），运行期按 `ModList.isLoaded` 把属性固定到对应值 | 小（每机器 +1 模型变体 +1 属性） | 需要改每个机器的 blockstate/放置逻辑；**推荐** |
| (B) 注册期分支 | `ModList.isLoaded` 决定注册哪套 Block | 中 | **同一 id 只有一个 blockstate**，所以单靠它做不到 → 必须配 (A) 或换 id（换 id = 破坏存档，禁止） |
| (C) 自定义 baked model | bake 期按安装情况选贴图 | 大 | 多一层渲染代码，且与现有 505 个模型 json 的生成链耦合 |

**我的建议：先只做"配方随装换"，外观不随装换。**
理由：外观两套意味着**每个机器的模型/方块态/语言/文档都要维护两份**，而玩家几乎不会因为
"这台机器是星辉石还是安山岩外观"来决定装不装 CEWS；而"配方能被造出来"才是 standalone 的**硬需求**。
（"纯应力充能"的安山岩+黄铜外观可以做成 CEWS **自带的一套贴图**，装了矿物扩展时也照样用它——
视觉上是"CEWS 自己的机器"，反而更清楚。）

**(d) 真正的耦合不止材料，还有"机器目录 API"。**
波系统要扫描半径内的加工机（含 CC&A/Vintage 机型）、要与"引雷统一加工"对接——
这是**运行时能力探测**，不是材料依赖。这部分必须留在矿物扩展，或抽成 `coe-api` 的窄接口，
CEWS 只依赖接口。**这是"CEWS 能单独运行"的唯一技术前提**（`CEWS 拆分方案` §4.2 第 7 条已写明）。

### 3.3 宇宙魔法学 → 机械动力变化学（同意，且建议先补内容）

- 强依赖矿物扩展**合理**：嬗化本质上是对矿物线物品/流体的特殊加工（嬗变液、嬗乱销毁、保护标签…）。
- 现在只有 4 文件 / 277 行代码 + 配方数据 → **它是拆分流水线的完美试验田**：
  最小、强依赖、独立数据包。**建议第一个拆它**，用最小代价验证"注册器分家 → 多模块 → 发布"整条链。
- **先定名与 id**：中文名"机械动力变化学"、英文名与 mod id 建议现在定稿
  （**注册 id 与翻译键一律不动**——这是本仓既有的红线；mod id 与注册命名空间解耦的做法见 `CEWS 拆分方案` §4.1）。

## 4. 风险清单（按严重度排序，附对策）

## 7. 需要你拍板的 5 件事

1. **一个仓库多模块（推荐）** vs 三个独立仓库？
2. **CEWS 的外观要不要"随装换"**？→ 我建议**不要**（只换配方，外观统一用 CEWS 自带的安山岩/黄铜风）。
3. **变化学的定名与 mod id**？→ 建议现在定（英文名 + mod id），**注册 id 与翻译键保持不动**。
4. 能否接受"只装 CEWS 时，世界里原本的矿物扩展方块变成未知方块"这一必然结果？
5. **Skiller 将来会不会被 CEWS/变化学使用**？→ 会的话，现在就要把共用面抽成 `coe-api`，否则以后要从四层里反向拆。

## 8. 参考实现实证：航空学 = Simulated Project（2026-09-25 实测）

参考仓库：<https://github.com/Creators-of-Aeronautics/Simulated-Project>（本地克隆在 `E:\mc\mcmod\_ref\Simulated-Project`，
与本仓的 `_ref/Skiller` 同处；jar 实证还用了 `libs/aeronautics-neoforge-1.21.1-1.3.0.jar` 与
gradle 缓存里的 `sable-2.0.3+mc1.21.1.jar`）。

### 8.1 它到底是什么（**纠正一个常见误读**）

用户以为"航空学这个模组里内置了 3 个小模组、可以自由搭配"。实测结论是：
**它确实内置了 3 个小模组，但它们不是"可选搭配"，而是"硬绑在一起、只能整包下载"。**

`aeronautics-bundled/gradle.properties` 自述：

> `mod_id=aeronautics_bundled` · `mod_name=Create Aeronautics`
> "…**This is a bundled JAR that contains Simulated, Aeronautics, and Offroad.**"

三个小模组（各自的 `gradle.properties` / `neoforge.mods.toml`）：

| 小模组 | mod id | 定位 | 依赖（**全部 required**） | 单独发布？ |
|---|---|---|---|---|
| **Create Simulated** | `simulated` | 物理交互式 contraption 内核（团队核心） | create, flywheel, **sable**, jei | ❌ 仓库里**没有**发布块 |
| **Create Aeronautics** | `aeronautics` | 航空学（热气球/螺旋桨/浮空石） | create, sable, **simulated**, jei | ❌ 同上 |
| **Create Offroad** | `offroad` | 越野学（车与陆地载具） | create, sable, **simulated** | ❌ 同上 |
| **Create Aeronautics（捆绑包）** | `aeronautics_bundled` | 只做"把上面三个打进一个 jar" | minecraft（内层各自带依赖） | ✅ **只有它**有 `publishMods`（Modrinth `create-aeronautics` / CurseForge 676721） |

**所以玩家侧的真实体验**：一个下载、mod 列表里看到 3 个 mod、**不能只装其中一个**
（`aeronautics`/`offroad` 对 `simulated` 是 required 依赖，少一个就加载失败）。

### 8.2 它的工程写法（**这些照抄**）

`settings.gradle.kts`：

```kotlin
rootProject.name = "simulated-project"
include("all-neoforge")                    // 开发运行用的聚合工程
include("simulated:common");   include("simulated:neoforge")
include("aeronautics:common"); include("aeronautics:neoforge")
include("offroad:common");     include("offroad:neoforge")
include("aeronautics-bundled")             // 发布用的便利包
```

捆绑包模块的依赖声明（**这就是"内置 3 个小模组"的全部机制**）：

```groovy
dependencies {
    jarJar(project(path: ":simulated:neoforge",   configuration: "runtimeElements"))
    jarJar(project(path: ":aeronautics:neoforge", configuration: "runtimeElements"))
    jarJar(project(path: ":offroad:neoforge",     configuration: "runtimeElements"))
}
```

值得照抄的 8 条：

1. **一个仓库、每个分层一个子模块、外加一个独立的 `-bundled` 发布模块**——正是本评审 §6 的路线（P1/P2 + 独立捆绑包）。
2. **每个小模组有自己的 mod id / mod_name / group / description**（各自的 `gradle.properties`），`archivesName = "${mod_id}-${project.name}-${minecraft_version}"`。
3. **每个小模组有自己的 asset 命名空间与语言文件**（`assets/simulated/lang/*`、`assets/aeronautics/lang/*`、`assets/offroad/lang/*`，各 20+ 语言）——**这正好是本文 R2 的解法**：绝不共用同一份 lang 路径。
4. **每个小模组自己的 mixin 配置**，并在 `mods.toml` 里用 `[[mixins]] config = "xxx.mixins.json"` 声明（aeronautics 有 2 份：通用 + neoforge 专用）。
5. **`buildSrc` 里放约定插件**（`multiloader-common.gradle` / `multiloader-loader.gradle`），每个模块的 `build.gradle` 只有十几行——共享配置只有一份。
6. **版本集中在根 `gradle.properties`**（`mod_version` 一套版本管所有模块；依赖版本范围集中，并注释"只在要同步进 mods.toml 时才改"）。
7. **库用 JarJar 塞进需要它的那个模组**（Sable 的 jar 里嵌了 `sable-rapier` 原生库 + `veil` 渲染库 + `sable-companion`，带 `META-INF/jarjar/metadata.json`）——**这正是本文给 skiller 的建议**（库随父 jar，不做成玩家可选项）。
8. **datagen 可以 `--existing-mod` 引用兄弟模组**（`offroad` 的 datagen 参数里有 `--existing-mod simulated`）——跨模块数据生成有官方姿势。

### 8.3 它**不能**照抄的部分（与本项目目标冲突）

| 它的做法 | 为什么不合我们的"自由搭配"目标 |
|---|---|
| 兄弟模块之间 **required 依赖** | 目标若是"偏执玩家只装能量波阵学"，required 会让游戏**加载失败**；必须换成 `optional` + 运行期 `ModList.isLoaded` 分支 + 桥接接口 |
| **只发布捆绑包**（内层无发布块） | 我们要让玩家能单独下载某一层 → 内层模块也要各自发布（多一个 `publishMods` 块 + 各自的依赖元数据） |
| **common/neoforge 双份**（多加载器） | 我们是 NeoForge-only，**不要**学这一层拆分，否则每个文件都要多一层目录 |
| 硬依赖带来的"零降级" | 自由搭配必须做降级路径（standalone 配方、外观、未知方块说明），这是纯新增工作量 |

### 8.4 由此得到的**两条路线**（需要用户选一条）

| | **(A) 航空学式：一个下载、4 个 mod**（推荐起步） | **(B) 真·自由搭配**（用户原目标） |
|---|---|---|
| 结构 | 一个仓库 + 4 个子模块 + `coe-bundled` 发布包 | 同 (A) |
| 依赖 | 四层之间 **required**（或"波/变化学 → 矿物扩展"required） | **optional** + 桥接接口 + 运行期分支 |
| 单独发布 | 只发 bundle（玩家一个下载，mod 列表 4 项） | bundle **和** 每层单独发布 |
| standalone 配方/外观 | **不需要** | **必须做**（64 条配方 + 外观方案 + 未知方块说明） |
| 工作量 | P1+P2+P3+P5+P6 ≈ **10–20 轮** | 在左栏基础上 **+3–8 轮**（P4），且长期每台机器多维护一套数据 |
| 玩家体验 | "一个几 MB 的包，装了就有四个模组" | "想要哪层就下哪层" |
| 风险 | 低（与成熟实现一致） | 中（降级路径是全新的、需要长期测） |

**我的建议：先做 (A)，把 (B) 留成第二阶段**——因为 (A) 做完之后，"独立发布 + 降级"只是
**改依赖声明 + 加降级路径**，不会返工搬运成果；而 (A) 本身就能满足"这是一套四个模组"的观感，
也是航空学已经跑通的形态。

## 9. 综合评估之后的最终建议（2026-09-25 定稿）

用户提出的第三种分法（**前两个分层合一组 / 第三个依赖第二个 / 第四个依赖第二个 + 一个与第三个
相关的拓展模组去改它的配方与材质**）**比"一拖四"和"软依赖运行期分支"都好**。下面是我按这个思路
给出的**推荐终态**。

### 9.1 推荐终态：5 个 jar、3 组、1 个便利包

| # | 产物（jar / mod id 待定） | 内容 | 依赖声明 | 单独可玩？ |
|---|---|---|---|---|
| **A** | **矿物扩展 `createoreexpansion`**（内含 JarJar 的 `skiller`） | 矿石/宝石/工具/技能/嬗变液/雷鸣合金 + 避雷针 | create 等基础依赖 | ✅ 地基 |
| **B** | **能量波阵学 `cews`** | 充能器/调级器/波速器/差波器/场控/变器/机壳/查询仪 + **自带一套 standalone 配方（安山岩/黄铜风）** | **对 A 是`optional`**（桥接接口，缺失即降级） | ✅ **偏执玩家只装它也能玩** |
| **C** | **能量波阵学·材料拓展**（与第三个相关的那一个） | **纯数据**（无 Java）：用星辉石/蓝宝石/翡翠材料的那套配方 + 标签；凭它的存在**关掉 B 的 standalone 配方** | A + B **required** | ❌（没 B 没意义） |
| **D** | **变化学 `changology`**（暂名） | 嬗化内容与配方（当前 4 文件 / 277 行，需先补内容） | A **required** | ❌ |
| **E** | **便利包 `coe-bundled`** | 只是把 A+B+C+D 用 `jarJar(project(...))` 打进一个 jar | 内层各自带依赖 | ✅ 一站式 |

**关键点：这才是"自由搭配"的正解。** 玩家侧真正需要的不是"软依赖 + 运行期分支"，
而是"**每个可选层是一个独立 mod，依赖关系写在 `mods.toml` 里、由加载器替玩家检查**"：

| 玩家装了什么 | 结果 |
|---|---|
| 只有 A | 完整矿物线（含技能，skiller 在里面） |
| A + B | 波系统用 **B 自带的 standalone 配方**（安山岩/黄铜风） |
| A + B + C | 波系统换成**星辉石/蓝宝石/翡翠**那套配方（C 的存在关掉了 standalone 那套） |
| **只有 B** | 波系统照常工作；**部分与矿物线相关的联动（强化避雷针引雷加工等）静默降级** |
| A + D | 嬗化玩法 |
| E（便利包） | 等于 A+B+C+D 一次装好，mod 列表里看到 4 个 |

### 9.2 三条必须写死的修正（否则会踩坑）

1. **C 必须是"纯数据"的（只有 `data/**`，没有 Java）**：配方/标签用 JSON 引用材料 id 即可，
   于是**B 对 A 完全没有编译期依赖**——"材料依赖"这件事被 C 整个接走了。
   这比"编译期 compileOnly + 运行期分支"简单一个数量级。
2. **"C 的存在关掉 B 的 standalone 配方"用原版条件实现**，不要用代码：
   B 的 standalone 配方带条件 `not(mod_loaded: C 的 id)`；C 的配方带 `mod_loaded: A`。
   （NeoForge 支持 `neoforge:not` / `and` / `or` 组合条件，配方层面就能表达。）
3. **外观不随装换**：**不要**让 C 去替换 B 的模型/贴图——两个 jar 提供同一个
   `assets/createoreexpansion/blockstates/xxx.json` 路径时，**谁生效取决于加载顺序**（不确定），
   这正是 §4 R2/R3 那类坑，而且是**不可测**的那种。B 的机器统一用自己那套安山岩/黄铜风贴图；
   想要"星辉石外观"只能新增方块 id（**破坏存档，禁止**）。

### 9.3 与另外两个方案的代价对比

| | 一拖四（只发 bundle，航空学式） | **§9.1 方案（推荐）** | 全软依赖 + 运行期分支（本文原 (B)） |
|---|---|---|---|
| 玩家能选吗 | ❌ 只能全装 | ✅ 5 种组合（见 9.1） | ✅ 但组合更多、语义更模糊 |
| standalone 配方 | 不需要 | **需要**（B 自带一套，纯数据） | 需要 |
| 外观方案 | 不需要 | **一套，不随装换** | 需要双模型变体/自定义模型 |
| 代码分支 | 无 | **几乎无**（只有 B→A 的桥接接口降级） | 每个功能点都要 `isLoaded` 分支 |
| 额外工作量 | 基准（10–20 轮） | 基准 **+3–6 轮**（B 的 standalone 配方集 + C 的数据 + 两个发布配置） | 基准 **+8–15 轮** 且长期维护双份 |
| 风险 | 低 | **低**（依赖由加载器检查，不靠运行期猜测） | 中高（组合爆炸、难测全） |

**结论：选 §9.1。** 它把"自由搭配"从"代码问题"降级成"数据 + 打包问题"，
而"一拖四"只在**你彻底放弃玩家选择**时才更省。

### 9.4 落地顺序（在原 §6 路线上修订）

| 步 | 内容 | 备注 |
|---|---|---|
| P0 | 定稿：4 层归属清单、依赖矩阵（9.1 表）、命名与 id 前缀、**C 是否现在就做**、变化学定名 | 本轮已完成大半（本文档） |
| P1 | 注册器分家（`AllItems`/`AllBlocks`/`AllBlockEntityTypes` 按 4 层拆类，**同 jar、id 不变、行为零变化**） | 4–8 轮，行为零变化，可分片并行 |
| P2 | 包级隔离 + 架构断言（禁止反向 import） | 3–6 轮 |
| P3 | Gradle 多模块：A / B / C / D / E 五个子项目 + `buildSrc` 约定 + 每层自己的命名空间与语言文件 | 2–4 轮（照航空学写法） |
| P4 | **B 的 standalone 配方集**（纯数据，安山岩/黄铜）+ **C 的数据包**（星辉材料版 + 关掉 standalone） | 3–6 轮 |
| P5 | skiller JarJar 进 A；E 用 `jarJar(project(...))` 打便利包 | 1–2 轮 |
| P6 | D（变化学）独立 + 内容补全 | 2–3 轮（**建议先补内容**） |
| | **合计** | **15–29 轮** |

> 与 §5 的旧估算相比：总轮次几乎不变，但**风险显著下降**——因为"运行期分支"被换成了
> "数据包 + 加载器依赖检查"，而后者是可静态验证的。

## 10. 发布策略：CF / Modrinth 上到底发几个项目（2026-09-25 追加）

用户的问题一针见血：「总不能直接塞一个模组'整合包'，里面 1 拖 4，然后又单独发布各个模组——
这样就重复了，肯定不好，不合适」。**结论：三个模型里选一个，不要混用；推荐模型 1。**

### 10.1 三个模型

| | **模型 1（推荐）** 只发独立 mod | **模型 2（航空学式）** 只发 bundle | **模型 3** 两者都发 |
|---|---|---|---|
| 平台项目数 | A / B / C / D 四个项目（**skiller 不建项目**——它是库，只内嵌） | 1 个项目（bundle），内层不建项目 | 5 个（1 bundle + 4 内层） |
| 玩家怎么装 | 装 A~D 里他想要的；required 依赖由平台提示/一键补装 | 装 1 个，mod 列表里看到 4 个 | 两种来源都能拿到同样的内容 |
| 依赖元数据 | 写在 `mods.toml` **和**平台版本元数据两处 | 只写在内层 mods.toml（内层不上架） | 两处都要写，容易不一致 |
| "一键全装"体验 | 由平台依赖机制承担（MR 的 Install with dependencies / CF 客户端缺依赖提示） | 天然就有 | 天然就有 |
| 内容重复 | 无 | 无 | **有**（同一内容两个来源） |
| 下载量 / 评论 / issue 归属 | 清晰（每层一个项目） | 清晰（都在 bundle 项目下） | **分裂**：同一个 bug 会在两个地方报 |
| modpack 作者 | 直接依赖需要的层（粒度正确） | 只能整包依赖（想要波就得带全部） | 容易被同时引用两个来源 |
| 与"自由搭配"目标 | ✅ 完全满足 | ❌ 不满足（玩家不能选） | ⚠️ 名义上满足，实际玩家会直接装 bundle |

### 10.2 为什么"两者都发"最差（你的直觉是对的）

1. **平台层面重复**：同一份内容有两个可下载来源，统计、评论、issue、更新通知全部分裂；
2. **CF 的自动校验会咬人**：CurseForge 有自动化检查，会以 *"File is a duplicate"* 拒收**与已存在文件重复**的上传，
   整合包的 manifest 校验也会因为 *"同一 projectID 被引用多次 / mod 文件夹里同一 mod 多份"* 直接拒绝
   （见 [CurseForge 系统拒收信息](https://support.curseforge.com/support/solutions/articles/9000205250-system-rejection-messages)）。
   我们的 bundle 与独立 jar 内容不同，不会触发"文件重复"，但**整合包同时引用两者**会触发后一条；
3. **加载器层面是否安全也不确定，而且不该赌**：JarJar 是"把 jar 塞进 jar"，玩家若又单独装了同一个 mod，
   能否自动去重取决于 FML 对"内嵌副本与独立副本是否同一来源"的判定。
   NeoForge 官方文档只把它描述成**版本协商系统**（见 [Jar-in-Jar | NeoForged docs](https://docs.neoforged.net/toolchain/docs/dependencies/jarinjar/)），
   我在本地 loader jar 里找到了 `JarInJarDependencyLocator` / `JarVersionLookupHandler` / `ModJarMetadata`
   这几个类，但**没能拿到"已存在则跳过内嵌副本"的权威结论**。→ 见 §10.5 的实测项。

### 10.3 发布策略与工作量的耦合（重要）

| 你选 | 那 P4（standalone）还要不要做？ |
|---|---|
| **模型 1（只发独立）** | **必须做**：B 要能单独跑（自带安山岩/黄铜配方）+ C 把材料换回星辉石系 |
| **模型 2（只发 bundle）** | **不用做**：所有人都有 A，B 直接引用 A 的材料即可 → **省掉 P4 的 3–6 轮** |
| 模型 3 | 要做（否则"只装 B"的人没有配方），而且白做（多数人装 bundle） |

也就是说：**"偏执玩家只装波也能玩"这条需求 = 必须发独立 mod + 必须做 standalone 配方**。
如果哪天你放弃这条需求，就选模型 2，能省下一整块工作。

### 10.4 具体怎么上传（A/B/C/D 四个项目）

**共同做法（两侧都要写依赖，缺一侧就会漏提示）**：

1. **`neoforge.mods.toml` 里写依赖**（这是加载器权威）：C → `[dependencies] A required + B required`；
   D → A required；B → A **optional**；
2. **平台版本元数据里也写一遍**：Modrinth 上传版本时填 *dependencies*（required/optional 指向对应项目）；
   CurseForge 在项目 **Relations** 里设 Required/Optional Dependency。
   CF 客户端会读 `mods.toml` 做"缺少依赖"提示，但平台关系不填就**不会**在网页/一键安装里体现；
3. **自动化**：用航空学同款的 `me.modmuss50.mod-publish-plugin`
   （在它的 `aeronautics-bundled/build.gradle.kts` 里就是 `publishMods { modrinth { ... requires("create") } }`）
   —— 一条 Gradle 任务同时发 CF/MR，把依赖关系写在脚本里，避免手填错；
4. **skiller 不建项目**：它是库、随 A 的 jar 内嵌（和 Sable 内嵌 rapier/veil 一样），
   玩家永远不会"同时拿到两份"——**这就是"库内嵌"与"内容层内嵌"的区别**，也是你担心的"重复"不适用于它的原因；
5. **A 建议沿用现有项目**（Create Ore Expansion，已有下载与评论积累），B/C/D 各建新项目，
   项目名与 `mod id` 解耦（id 保持注册命名空间那套红线）。

**C 的两种形态**（可后定）：独立项目（可被一键依赖安装、依赖检查完整）
vs B 项目下的"附加数据包文件"（少一个项目，但不会被自动安装，玩家要手动放进 `datapacks/`）。

### 10.5 一个 5 分钟的实测项（P5 时做）

拿 P5 的便利包 + 单独一份 B，同时丢进 `mods/`，看是否报 `Duplicate mod`：
- 若**不报**（内嵌副本被跳过）→ 模型 3 技术可行，但仍**不推荐**（§10.2 的平台理由）；
- 若**报错**→ 模型 3 被彻底否决，并且这条结论要写进 `AGENTS.md`，防止以后有人再试。

**最终建议：模型 1（只发 A/B/C/D 四个独立项目，不做 bundle jar）。**
理由：它让"自由搭配"这个设计目标真正成立（模型 2 会把它作废），
没有重复内容，依赖元数据语义正确，modpack 作者能按层依赖；
而"一键全装"的体验由平台依赖机制 + 首页安装指引承担——
**用依赖元数据表达"1 拖 4"，而不是用塞了 4 个 mod 的 jar**。

### 11.2 第 3 层（能量波阵学）的最终形态

用户方案（我的评判：**方向正确，三处要修**）：

| 角色 | 内容 | 依赖 | 备注 |
|---|---|---|---|
| **B：能量波阵学** | 全部波机器 + 与矿物扩展联动的那套配方 | **对 A 是 `optional`（不是 required！见修正①）** | 装了 A：天然适配，无需任何数据包 |

**三条必须修正的地方：**

1. **B 对 A 必须是 `optional`**。用户想表达的是"强烈推荐装矿物扩展"，但写成 `required` 会让
   "没装 A 时 B 也能跑"这件事**在加载器层面直接不可能**（游戏拒绝启动）。正确写法：
   `optional` + 项目描述写明"强烈建议配合矿物扩展；单独使用请加装修正包" + 平台元数据里的 optional 关系。

   两条可行路线：
   - **(i) 一套外观（推荐）**：B 的机器永远用它自己那套外观，修正包只管配方；
   - **(ii) 两套外观（可行但要加钱）**：B 自己同时带两套模型（**都在自己的路径下，无路径冲突**），

     安山岩/黄铜那套可以直接引用 Create 自带的 `create:block/andesite_casing` / `brass_casing` / 轴等贴图，
     符合"绝不自绘贴图"的红线。代价：每台机器的模型变体翻倍（16 个变体的波变器就是 32 个模型文件）。
3. **"只加载机器、配方都不加载"要如实告知玩家**：方块/物品照旧注册（不可能"不加载"），
   没有修正包时只是**没有配方、波的加工引擎没有可做的配方**——等于"仅创造模式可用"。
   建议在 B 的护目镜/Jade 上加一行灰字提示（"未检测到矿物扩展：请加装修正包以获得配方"）。

**至于用户提的第 2 层的"慢速充能机"**（让矿物扩展的工具在没有波系统时也能充能，但**很慢**，
装了波之后由能量波快速充能）：**这个设计很好**，它同时解决了"A 单独装时工具没法充能"的玩法断点，

  **不画新图**（红线：贴图是用户资产）；

### 11.3 工作区里怎么放 skiller（我的决定）

### 12.2 ⚠ 唯一必须提前知道的技术约束：**资源不能"按条件切换"**

用户把修正包描述成"资源包"，并期望它**装了 A 时失效**。这里有一条无法绕过的事实：

- **配方可以按条件切换** ✓：配方是 data，用 `neoforge:mod_loaded` / `neoforge:not` 条件即可
  （`装了 A → 用星辉石那套；没装 A → 用修正包那套`，两者互斥、必然只有一个生效）；
- **贴图/模型不能按条件切换** ✗：资源（`assets/**`）没有"条件加载"机制，而两个 jar（或内嵌 jar 与本体）
  提供同一个路径时，**谁生效取决于加载顺序**（不可测、不可控）。这正是本文 §4 R2/R3 的坑。

**因此修正包的"改材质"必须这样落地**（这也解释了为什么它不能是"纯资源包"）：

1. **B 自带两套外观模型**，各自在不同路径下（无路径冲突）：
   - 星辉石风（现有那套）——装了 A 时用；
   - 安山岩/黄铜风（修正包提供）——没装 A 时用；
   两套模型都在 B 的 jar 里（修正包内嵌），**资源恒定存在，只是有一套不被引用**（无害）。
2. **选哪一套由代码在"注册期"定死**（一处、一行）：`ModList.isLoaded("createoreexpansion")`
   → 该布尔值写进机器的 **blockstate 属性**（JSON 里两套变体都写），或改为
   `ModelEvent.ModifyBakingResult` 在 bake 期替换模型（两者都可行，前者无需客户端代码）。
3. **不触碰底层逻辑**：机器的行为、方块实体、配方类型、波系统全部不变；改的只有
   "模型引用"与"数据包配方"两件事——与用户"没有修改底层逻辑"的表述一致。
4. 安山岩/黄铜那套贴图**直接引用 Create 自带的 `andesite_casing` / `brass_casing` / 轴等**
   （或星辉石贴图的复用），**不需要自绘贴图**——符合"贴图是用户资产"的红线。

> 一句话：**修正包 = 一套备用外观资源 + 一套 standalone 配方 + 一个注册期开关**。
> 前两者是数据/资源（无逻辑），最后那个开关是唯一的一行代码。

### 13.3 Curios 改 optional 的改造清单（用户已拍板）

现状：**5 个 Java 文件直接 `import` Curios API**（`common/AllItems`、
`content/equipment/medallion/{IMedallion, BaseStressMedallionItem, NetheriteStressMedallionItem, MedallionEffectHandler}`）

1. **接口隔离**：新增 `compat/curios/CuriosBridge`（`get()` 在未安装时返回 `null`），

3. **事件监听**（若有 `CurioChangeEvent` 之类）只在 Curios 在装时注册；
4. `data/curios/**` 的标签**不用动**（未装 Curios 时是无人读取的数据，无害）；
5. **验收**：临时把 Curios 从 dev 运行时依赖里去掉，跑 `runData` 必须成功（证明"没装 Curios 也能加载"），

### 14.2 方案修订：**取消"包级搬家"**（原 P2 的一半）

原 P2 = "把代码按 `content/coe|cews|transmute` 归位 + 删除外观 + 架构断言"。
**修订为：删除外观 + 引用改指本层（P2a） + 方向断言（P2b），不做包名搬家。** 理由：

1. **包名与 Gradle 模块目录无关**：P3 拆模块时源码根变成 `cews/src/main/java/...`，
   包名保持 `com.hjmmd_8.createoreexpansion.content.charger` **完全合法** ——
   物理边界由**模块目录**提供，不需要靠包名表达；
2. 搬家要动 **200+ 个文件**（每个文件的 `package` 与全仓 import 全变），diff 巨大、合并风险高，
   而收益只是"目录好看"；
3. 方向约束用 `tools/check-layering.ps1`（**按文件路径分组** + import 方向判定）就能守住，
   不需要搬家也能挡住"COE 反向 import CEWS"这类渗透；
4. 将来真要搬，**在 P3 里顺手做最省**——那时每个模块的源码根本来就变了。

> 一句话：**边界靠"模块目录 + 断言脚本"，不靠包名。** 这一步省下的是一次高风险的大 diff。

### 15.1 实测：376 个 java 文件按模块归属

| 模块 | 文件数 | 内容 |
|---|---|---|
| **COE（矿物扩展）** | **154** | `content/{skill 37, equipment 20, grinding 16, lightning 8, crystal 4, worldgen 2, 其余}` + `common/registry/coe` + `foundation/item/skill` + `client/tool` + `integration/skiller` |

| **TRANS（机械嬗化学）** | **7** | `content/transmuting` + `foundation/TransmutationEventHandler` + `common/registry/transmutation` |
| **CORE（共享）** | **108** | `compat/jei 20`、`client/renderer 9`、`foundation/util 7`、`compat/{sable,vintage,curios,createaddition,optical}`、`data/{datagen, RecipeProvider, lang×3}`、`mixin 9`、`common/*`（配置/标签页/AllTiers/AllTags/…）、`util 5`、模组根类 |

**注意：CORE 里有一大半其实"只服务某一层"**，只是碰巧住在共享目录里——
`compat/jade/WaveJadePlugin`（CEWS）、`client/renderer/{CreateCharger, FieldController, StellarWaveTransmuter, wave/*}`（CEWS）、

真正"两边都要用"的只剩：**`util/*` 5 个 + `common/machine/*` 2 个 + 配置/标签页/数据生成基座 + mixin 插件**。

### 15.2 定稿：**4 个目录**（3 个内容层 + 1 个共享库），不是 3 个

用户希望"3 个文件夹管 3 个东西"，但实测有 **108 个共享文件**；若强行塞进 3 个目录，就必须
**把共享代码复制两份**——而其中 `common/machine/MachineInteraction`（机器交互契约）是
**跨模块 instanceof 判定**用的：两份副本 = 两个不同的 `Class` 对象 = **`instanceof` 恒假**、
Ctrl+扳手在别人的机器上失效。这类"身份敏感"的类**无法靠复制解决**。

因此定稿为：

```
workspace/
├── settings.gradle.kts      include("core","coe","cews","transmutation","all-neoforge")
├── buildSrc/                共享 Gradle 约定（mods.toml 展开 / datagen / jarJar / publishMods）
├── core/                    ★ 共享库 mod：util + 机器交互契约 + 配置/标签页/数据生成基座 + mixin 插件
├── coe/                     ★ 矿物扩展（JarJar 内嵌 skiller）
├── cews/                    ★ 能量波阵学（内嵌修正包的数据）
├── transmutation/           ★ 机械嬗化学
└── all-neoforge/            开发聚合（一个 dev 环境同时装 4 个模块，照航空学的写法）
```

**依赖矩阵（require = mods.toml 里 required，平台元数据同步填）**：

| 模块 | 依赖 | 说明 |
|---|---|---|
| `core` | create 等基础 | **单独上架**（库；可以长期不更新） |
| `coe` | **core required** + JarJar skiller | 一站式：装 COE 就有了 core 与技能内核 |
| `cews` | **core required**；**COE optional** | 只装 CEWS 的玩家 = 装 CEWS + core（平台会按 required 自动带出） |
| `transmutation` | **core required + COE required** | 与定稿一致（第 4 层强依赖第 2 层） |

**为什么 core 不 JarJar 进 COE**：JarJar 内嵌 + 玩家又单独装了同一个 mod 时，能否自动去重
取决于 FML 的实现细节（§10.2 那条"未证实"的结论）——**core 被三个模块共用，不去赌它**；
改用"required 依赖 + 平台一键带依赖安装"，既无重复也无版本漂移。

**如果用户坚持只要 3 个目录**（不要 core）：代价是 ① 把 `util/*` 与若干基类**复制两份**（漂移风险）；
② 机器交互契约改为**每层各一份 + 跨模块识别改用方块标签**（`#createoreexpansion:machine_interaction`），
这会改动交互代码（有行为风险）。→ 除非玩家对"多装一个几百 KB 的 core"极度反感，否则**不选**。

### 15.3 搬家顺序（每步都能跑三关 + 断言脚本 + generated 零差异）

| 步 | 动作 | 验收 |
|---|---|---|
| **P3a** | 只搭骨架：`settings.gradle.kts` 多项目 + `buildSrc` 约定 + 4 个**空**模块（各自的 mods.toml/gradle.properties）+ `all-neoforge`；**现有根工程照旧出单 jar** | 根工程三关照旧全绿（jar 字节不变）、各模块能各自 build |
